One run end to end: what the constructor sets up, the single prove pass and its cycle loop, the three load paths, and the deposit-mode selector every ingestion site threads.

2.1  Life of a run

The coordinator is Prover. It calls focused compiler, logical-block, hash, publication and proof-export classes through operation interfaces. Each class keeps its implementation state private. Construction delegates to ProverInitialization and only loads state — it never proves: it reads Config<Tag>.json, builds the core-expression map and anchor info (modifyCoreExpressionMap, initAnchor), precomputes the permutation/mapping caches (allPermutationsAna, allMappingsAna) the hot path needs, seeds the name counters (implCounter, existenceCounter, andCounter, orCounter, variableCounter), and sets logicalCores = std::thread::hardware_concurrency().

analyzeExpressions then runs the actual proof: load external theorems, register the CE-surviving conjectures as goals, run one proving phase — a warm-up prove() then the main prove(), on one grid with no teardown or rebuild — then walk globalTheoremList once more with headSwitchOne to populate orPairsFromHeadSwitch. After it returns, run_modes::fullRun runs the compressor (gated by skipCompression) and constructs OR theorems from the harvested pairs, then writes the two theorem files and the raw graph.

A goal can demand one missing function value

Suppose the goal is x in J and an available rule says that P(x,y) implies x in J. The value y does not appear in the goal. When this is the rule's only premise and y is its only missing argument, the prover places P(x,marker) in ordinary admission, owned by the open goal. An already proved existence can then supply y. The request itself asserts no fact, and the original rule supplies the conclusion. The rule must be available at the goal's scope or an ancestor; fixed arguments and existing construction limits are retained.

Shared operations beneath proof processing

Case handling, equivalence processing and statement deposits use small common operations for syntax, expansion, knownness queries and storage updates. The storage helpers stage the same pending notifications in the same order. They do not call back into the processing classes. Logical-block state stays in its existing memory objects.

Closing a scope removes its statement rows. The equality processor's saved position moves back by exactly the number of removed rows before it, so facts added after cleanup still receive equality substitutions. Removing the same closed scope again leaves the position unchanged.

The OR theorem builder calls the theorem publisher. The publisher records candidate completion through a separate view of the existing candidate vector and its mutex; completion marking does not invoke the builder.

Single-pass head-switch model. The prover only reasons forward, but a theorem and its contrapositive are equally provable. headSwitchOne is purely structural: scan the chain for the right-most !-premise with an empty inner bound-var list, swap the head with that premise's body, rebuild by string concatenation. Every qualifying conjecture's mirror is added before the prove pass, so the deleted bigIteration/maxBigIterations loop is not needed — there is exactly one grid, one pass.

2.2  Cycles

prove(numberIterations, bodies) is the outer loop. The counterexample filter does not share it: the filter runs its own per-conjecture pool in filter.cpp over permanentBodiesCE and never enters prove()/proveKernel. Each cycle steps every active block once — the elementary step, run as three barriered phase sweeps (§5.1) — generate hash requests (generateEncodedRequestsStatic, one function that each caller tells which already-known fact a request has to carry), match against overallHashMemory.encodedMap, fire via addStatement, push main-scope results to mailOut — then drains mail. The loop ends when a whole cycle adds nothing or the per-batch iteration cap is hit; warm-up cycles run first to bring rule cascades to steady state before the budgeted main iterations.

Shared processing before and after the hashburst

Phases 1 and 3 complete the same local processing sequence. After input mail is absorbed, hypothesis reactions add their copy equalities before class application. Existing discharge and outgoing publication process their results immediately. The call then retires closed cases, releases waiting cases and wipes closed scopes once. Phase 1 finishes this cleanup before GPU request construction. The earlier reactions can change proof timing and reveal additional theorems.

CUDA projection key storage

Before allocating the projection, the host counts the distinct key bytes and prefix transitions it needs. Each logic block shares identical key bytes among its projected tables, while each table retains its own entries, owners and membership. Reverse lookups refer to key bytes already held in the forward blobs. Construction shards still write into disjoint slices and adjust offsets when their used data is compacted.

In the projection-only measurement (28 September 2026), the largest host projection fell from 3,113.3 to 1,615.4 MiB, a 48.1 percent reduction, with identical proof files in two full runs. At that stage, the native main pool reached about 5,888–5,895 MiB of its 6,144 MiB capacity.

This reduces representation size without changing native proof tables, scope, predicate masks or result order. The counting pass uses temporary arena storage; its runtime and memory costs are measured with the full workload.

2.2.1  CUDA filter classes

In the explicit CUDA route, several processor-order request-generator calls can ask the same frozen filtering question. Equality is exact: the logical block, registry kind, iteration ceiling, whole-key mode, and statement count must all match. The host gives such calls one immutable class. The GPU filters and stably orders the statement rows once for that class, then each original call reads the same count and offset. The calls themselves are not merged: their original ordinals continue through growth, duplicate removal, provenance ordering, and the final canonical stream. Each class span is sorted independently by decoded-name rank and original statement index, both with full 32-bit width. This preserves lexical order and equal-name stability for large uploaded blocks.

Two single-threaded drains run at the cycle boundary. The first is the mail router (mailOut → recipients' mailIn, shown below). The second runs immediately after the worker pool.join() and before the router: a sorted single-threaded pass that compiles every proved implication queued during the cycle to its compact (implication<N>[…]) form and deposits it into the producer's own mailOut.statements (the channel-unification half of §3.3.2). Both drains exist for the same reason: the work mutates global state (compact-form name counters, recipient mailboxes) and must be deterministic; inline mutation from worker threads loses that guarantee. Receivers then absorb pre-fixpoint at the top of next cycle — recovered rules can fire in the same burst they were absorbed in.

2.3  How a theorem enters — and the status modes

Compiled statements reach a block through initial conjecture registration or mail absorption. Structural operators are precompiled before either path (§3.5). Both paths deposit expressions through addExprToMemoryBlock; implication products enter the rule store through addToHashMemory.

  • External theorems. The external and prior-batch theorem lists are loaded before analysis, then precompiled and broadcast after the warm-up proof iterations. Mail absorption installs their rule fuel.
  • Conjectures to prove. Each CE survivor registered via addTheoremToMemory(conj, body, 0, false, …) — the false means “goal, not given”: premises become rules, the head becomes a intToBeProved goal.
  • Broadcast / mail. A peer block's main-scope result arrives on mailIn.statements and is absorbed by addStatement (re-precompiling if needed). In an incubator batch the proved-theorem rules reach the anchor block only; the externally provided lemmas still reach every block below it.

addStatement is the central ingestion primitive. Given an expression, target block, levels, validity, and a local flag, it: (1) pushes the equality mirror (=[b,a]) for a local (=[a,b]) with a≠b (the mirror appearing in newStatements is what discharges a mirrored goal — I-9); (2) for !(=[a,b]) emits one-sided sibling inequalities (I-12); (3) deposits into intStatementLevelsMap/intKnownStatements/intEncodedStatements; (4) if local, also the intLocalEncodedStatements{,Delta} registries and the intLocalEncodedStatementsSet index; (5) appends to newStatements; (6) for "main" validity, pushes to mailOut.statements. It appends encoded rows to the caller-owned PagedVector<IntEncodedExpr> — every deposit, including cross-scope ones, rides this one channel carrying its actual scope (I-25).

Every deeper deposit site threads a 4th argument, int status — a mode selector. Picking the wrong one mis-routes the deposit — and an obviously-wrong non-compact status now trips an assert at the disintegration gate — so it is worth knowing as a reference:

The canonical door. Before any of these paths runs (and after the ancestor-known refusal of the raw text), every deposit except a goal, a positive or negated equality, or an anchor predicate is rewritten to its class-canonical form under the complete equivalence classes at the deposit's own scope, including all equalities inherited from its ancestors — normal names included, the representative being the same one the admission keys collapse onto. Only canonical forms are admitted: if the canonical form is already known at this scope or an ancestor the deposit ends there; otherwise the canonical form proceeds as this block's own derivation when one of the equalities that fired is the block's own (the rewrite is then its class product — local, visible to the goal discharge and to the mail; under purely inherited equalities it keeps the sender's status), the raw spelling keeps its producer history line (shipped down with the mail when the result is local), the canonical form gets one equality1 bridge citing the raw form and the equalities that fired, and the level run gains the equalities' levels. The class multiplication still fans the canonical form out into its variants, so a literal goal still closes. Mail rows are offered raw — the door is the one canonicalizer. Ordinary equality multiplication retains its separate application classes and required expression variants, including their proof and matching roles; those products are not restricted to canonical-only storage. Cleanup runs after multiplication closes and considers complete classes at each affected descendant scope.

The status question, always: has whoever produced this expression already disintegrated it? Routing mail from a peer → 3 (or 5 when the sender flagged it for receiver-side disintegration). This block's own body (equi-class rewrite, OR seed, revival absorb) → 1 (or 0 to force deep). A theorem to prove → 2. Picking an obviously-wrong status no longer fails silently: a non-compact statement deposited under 3 trips an assert at the disintegration gate (assert(isCompactImplication || status == 0 || status == 1 || status == 5)).

2.4  Status modes — six readings, one register

The six-row table in §2.3 lists the modes; this section explains each row with the concrete scenario it serves. The status argument is the 4th parameter of addExprToMemoryBlock, threaded through from the integration absorber and the mail-absorb path. Source check: the integer values 0, 1, 2, 3, 4, 5 are real branches in the code path.

status = 0 — local derivation, force-deep
Used when the deposit is the result of a Pass B emission whose body needs another Pass B before downstream rules can fire. Forces deep disintegration. Typical callers: OR-branch seed expansion, CE admission revival, the integration-handshake side that wants the body re-unpacked. Wrong here = the emission lands as one piece, no sub-rules see it.
status = 1 — local derivation, normal
The canonical produce-and-absorb mode. Almost every internal write goes through this path: the kernel's primary addStatement branch, the integration-revival absorb at top-of-burst, head writes, fixpoint deposits after equi-class rewrites. Disintegration runs at the normal depth; an exprOriginMap entry is recorded.
status = 2 — goal / intToBeProved insert
Used only when the deposit is a fresh goal — a CE-surviving conjecture's head, an OR branch's per-disjunct head, the inner head of an opened hypothesis block. The disintegration path is replaced by prepareIntegration (we want this expression to fire as the target of a future emission, not as a premise). The origin is a special “goal” record so the chapter walker can recognise it as a sink. A non-main goal can later close from the shallowest ancestor that already knows the same expression: that source supplies the levels and provenance, while the exact goal still determines what closes and which branch cohort is cleaned. The ancestor fact is not copied into the child.
status = 3 — external mail absorb
Mail from a peer block, and the arrivals split by shape. The rule carriers re-enter disintegrateExpr2: a compact implication (implication<N>[…]) recovers the broadcast rule it carries, a definition whose whole body is one implication (such as primeseq, whose name is its own compact form) installs its rule, and a negated compact existence !(existence<N>[…]) — a universal in De-Morgan clothing — installs its universal rule (witness-free, so it cannot mint fresh names). A plain mail fact is absorbed as a statement without disintegration — re-expanding a fact would mint fresh it_/int_/force_ names and overflow the static MAX_NAME_IDS cap. The split is enforced at the call-site gate: any other shape reaching the disintegration path under status 3 trips the tripwire assert, so the absorb path is never a silent skip. Origin is taken from the mail's exprOriginMap.
status = 4 — fast-path fact load
A statement comes in as a bare fact at grid setup (the simple-facts bootstrap). Nothing to disintegrate, no origin to record — just register the fact and the levels it lives at. Used during the CE filter's model load (§11.2).
status = 5 — flag-5 relay arrival
The receiver half of the witness relay. When a block's own disintegration of an existence compact cannot admit the products (the admission demand lives only at a descendant block — demand is strictly block-local), it mails the compact down flagged “external, may be disintegrated” on a per-statement side column, together with the witness-generation stamp its own minting would have used. A receiver seeing the flag runs the compact through the FULL disintegration — fresh witnesses minted here, at the carried generation — so a block that holds the demand admits and registers the products locally (they feed its own rule firings and mail onward normally), while an undemanded receiver just parks them under the ordinary Pass B discipline. The carrier itself registers non-local, so it is never re-forwarded — mail already reaches every descendant directly — and a mailed carrier never re-stages a relay, so there is no cascade.

A second side-column mark, “unconditional ordis”, travels with an OR that a conjecture's premise unfolds into. It keeps status 3, but a receiver that has proof work (a goal, or an active contradiction) opens the OR's case split at once, without waiting for a demand; any other receiver keeps the OR as a plain fact.

2.5  Deactivation — recursive vs unnecessary

A logic block stops stepping when its work is done. Two functions take an LB from active to inactive — they differ in scope. A third, earlier trigger fires when an induction step proves (§2.5.2):

The contradiction override. deactivateRecursively respects primedForContradiction — a contradiction LB about to discharge a contradiction (§10.6) is exempted (its prune condition carries !primedForContradiction) for one more cycle so the main/main discharge can fire. Without the exemption the block would be torn down before its stored theorem was emitted.

2.5.1  Bubble-up gating

The disable mechanism gates on the main-namescope intToBeProved only: deeper-scope residue (goals that opened under a hypothesis, OR branch, or integration scope) does not keep LBs alive once their parent's main-scope goal is reached. This avoids the failure mode where a long chain of nested hypotheticals keeps the tree alive past usefulness — and prevents over-tearing of LBs that only have descendant-scope work left.

2.5.2  Step win

When an induction step block proves its goal, its base-case (zero) block wakes. Under the working assumption that a true statement whose step is proved also proves its base case, the competing induction and contradiction attempts on that conjecture are wasted from that moment. The first step to prove therefore wins — provided its proof could publish on its own, that is, it uses every premise of the conjecture, counting the levels of the fact n ∈ ℕ once the goal block knows it. A step that leaves a premise unused switches nothing off; its base case runs as before and decides. At a win, the other variables' and kinds' step blocks, any base case an earlier uncovered step woke, and both contradiction blocks are switched off, and the remaining zero blocks never wake. The premise blocks stay alive: the goal block can prove the head, or a lemma other proofs wait for, directly and sooner than the winning base case. If the base case closes before the goal block knows n ∈ ℕ, the publication waits and is retried at the barrier where that fact arrives. An induction publishes only when its step proof, its base proof and the fact n ∈ ℕ that the induction consumes together use every premise of the conjecture — neither half has to use them all alone. A missing premise means the conjecture holds without it: nothing is published and nothing is switched off.

2.6  The diagnostic trace dump

When trace dumping is armed, the file .debug/hashburst_trace.txt captures, at every cycle boundary, the complete state of one targeted LB — encoded statements, goals, origin records, hash rules, the admission map, marker rules, mail. This is the diagnostic instrument used to investigate how a single block's state evolves cycle by cycle: by far the highest-value debug artefact the prover produces. The dump format is deliberately stable across runs so iteration-over-iteration diffs (and the diffs between a working and a failing run) read cleanly.

The entry and exit functions keep the trace counters, locking and file handling. A dedicated HashburstDumpReader writes their ordered sections through read-only access to logical-block and hash-memory state. Diagnostic access does not require public mutable storage fields and does not participate in inference.

2.6.1  What the targeted-LB chain match looks like

The dump fires only on a specific LB — identified by its full parent chain to root, never by exprKey alone. The match is a chain of equality tests on each ancestor's exprKey, terminated by the root sentinel (empty exprKey, null parent). Many LBs share the same innermost exprKey at different positions in the LB tree — without the full chain, they would all fire together and dump on top of one another.

Why dump-format stability matters. Multi-day investigations — determinism races, equality-class cycles, mail-unification regressions, mistagged OR re-integrations — all hinged on diffs of this output across cycles or across runs. The dump's identity over time is what makes it load-bearing; reformatting it for cosmetic clarity loses the diff muscle-memory built around it. Treat the format as a contract.

Consuming the induction hypothesis

A head fired by the recursion step's own induction implication carries an explicit signal through processor or GPU evaluation and internal mail. That signal selects deep disintegration: forced witnesses and their defining facts are admitted without demand; newly created algebra-side witness products are dropped. The products-of-recursion set is unchanged. The integration diagram shows how those facts feed the additional flat goal rules.

Case analysis inside contradiction blocks

An active contradiction block can run admitted OR cases even when it has no explicit goal rows. Such cases remain live rather than being treated as already complete. Opposite registered facts refute their case, whose retirement releases the next case; a contradiction at the block's main scope closes the whole contradiction block. Ordinary explicit-goal resolution, case depth limits and proof history remain in force.

Equal inputs in induction-step subproofs

Inside an induction-step logical block, this experimental search rule compares the formal input positions of each numbered implication subproof. Other blocks, including the induction base case, keep their existing behavior. Two distinct inputs may denote the same object only when that implication has their exact pair as a direct positive equality premise. Reusing one formal input remains allowed. An equality in the conclusion, inside another compound, or obtained by chaining permitted pairs does not grant permission.

The check runs before opening and again for existing subproofs after equality processing. A forbidden identification retires that subproof and its descendants through ordinary scope cleanup. It proves neither the implication nor its negation. Equalities come only from that scope and its ancestors. The rule applies to ordinary and goal-qualified implication subproofs and requires no mathematical labels for the objects.

Impossible implication premises

An implication subproof may assume premises that cannot hold together. When one fact in that scope opposes a fact there or in an ancestor, the prover records the exact goal as following from that contradiction. Normal implication closure then proves the implication and removes its temporary scope. Facts in siblings or deeper child scopes cannot supply this closure; the parent context remains available.

A refuted implication subproof is retired

An implication subproof opened by an arriving fact cannot close when its implication is false, yet it would keep working until its block ends. So beside it the prover opens a second scope, its reductio, that assumes the implication. There the implication acts as a rule on the parent's facts. When an object satisfies the premises at the parent but its conclusion is denied there, the assumption collides with that denial, and the prover records the negated implication at the parent with an ordinary contradiction step. The subproof is then retired with its subtree, its reductio leaves with it, and neither reopens.

A refutation counts only at the subproof's parent or above: one found inside a case retires the subproofs in that case, not those outside it. Subproofs opened for a goal follow that goal; blocks primed for contradiction are left alone, since their premises are meant to be inconsistent.

One conclusion, supported in each case

OR bookkeeping keeps the parent conclusion fixed and records each case’s actual fact together with its equality justification. An endpoint fact E(n), with local i = n, supports E(i) without adding another existence statement to that case. Case completion and release use the same support. Each equality stays inside its own case.

A demanded result can request a second name

The final graph head must match an existing integration admission key. If its witness is tied to a fixed value by a positive equality premise, that value can receive its ordinary second name. A visible equality is reused. The declaration stays within the compatible rule and demand scopes, and every other premise remains necessary for ordinary firing.

Introducing an OR from a conjunction

When an OR alternative is a positive conjunction, its introduction rule takes each conjunct as an ordered premise. Nested positive conjunctions unfold in place; negative conjunctions remain whole signed premises. Ordinary firing still needs every premise. Case processing retains the original alternative.

Composing implications and admitting witnesses

A producer with one or more ordered premises and a consumer with exactly one premise can produce an additional implication only when their complete sets of bound variables match one-to-one through the intermediate expression and survive in the result. A bound variable cannot become a fixed parameter or collapse into another variable. The result retains both source proofs and holds at their deepest compatible scope. Repeated results are processed once, and a cycle cannot survive without independent supporting rules.

A composition is created only when the second rule's head can serve an existing integration admission demand. Matching treats the witness as a marker while retaining the index as a bound variable. A later demand wakes already installed rules; a later rule inspects existing demands. The matching demand must also be compatible with the result's scope.

New rules enter the composition queue immediately. Their ordinary inference indexes are updated together when that queue finishes, before admission checks or inference resume.

An existing integration demand for a result can then supply ordinary admission permission for the corresponding premise witness. For an appended graph, demand for a new graph value can release the already-known old graph value. Forward inference transfers that pair; the original integration instruction constructs the target existence. Admission itself does not assert a fact backwards.

Depth limits apply to witness creation

Ordinary integration witnesses carry their construction depth. At the configured limit, disintegration still extracts independent implications and facts, but it cannot mint another ordinary integration witness. Forced routes use a separate witness class. Parked constructions retain their original assignment for later replay. See the witness and replay diagram.

Induction admission needs a clean original

An induction chain demands the missing objects of its hypothesis. When a disintegration produces such an object, the chain moves forward only if the expression being disintegrated has plain numbers, rec or rec2 (the twin partner’s predecessor, Mechanisms 4.5.4) as its arguments, none of them twice: preorder(a,a) names one object in two places and feeds no induction admission. An original that names a constructed object, such as a sequence built earlier in the block, still yields its products, but they do not advance the induction chain, and an induction demand alone does not admit a new witness for it. The arriving expression itself, integration preparation and forced construction are unchanged. This limits search; it does not refute the rejected candidate. A second rule keeps the hypothesis from feeding on itself: an object built when the hypothesis’ own conclusion is unpacked never answers the hypothesis’ demands, so the chain cannot ask for a new task about that object in turn.

Fully known premises of the induction hypothesis

When facts in the step block bind every argument of one of the hypothesis’ premises, that premise is one concrete statement, such as “p is a member of the restriction R”. GL then prepares proving exactly that statement, unless it is already known; once it holds, the hypothesis can fire. This applies to compound definitions that are not functions, relations included, in either polarity. A relation with an argument still open is not demanded, because such a demand would match every value of that argument.

Bounded host construction for GPU projection

Each GPU chunk contains complete logic-block task families. The independent GPU-host pool supplies consecutive construction windows targeting 32 MiB of column storage; an individually larger block receives its exact measured window. One set of construction threads serves the chunk. When the budget permits two windows, upload overlaps construction of the next window. Otherwise one window is reused after its upload completes. If even one window plus retained input and later output support exceeds the budget, the planner selects fewer complete families. Uploaded source ordinals and name/rule lookups remain for scheduling and sealing. The upload thread releases each window as soon as its upload and sealing copy finish; no projection image is deloaded.
