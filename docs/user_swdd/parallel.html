5 · Parallel execution

The grid runs on every core the machine has and still produces the exact same proof every time. This chapter is the mechanism that makes both true at once — and a real race that shows why it is shaped this way.

The cycle from Chapter 2 has two halves. proveKernel runs the first — stepping every active block — on a pool of worker threads, then a hard barrier, then the second — collecting and delivering results — single-threaded and ordered. That structure is the determinism guarantee.

5.1  The worker pool over blocks

proveKernel spawns logicalCores worker threads (logicalCores = std::max(1u, std::thread::hardware_concurrency()) — the old =1 hardcode is commented out; these are real threads). They share one bodies vector and pull from it with std::atomic<size_t> next.fetch_add(1) — work-stealing. Each worker runs the elementary step on whatever block it grabs and writes only its own per-core slots:

Per-core slot a worker may writeDrained by the serial phase into…
mailOut (its OWN deloadable LB outbox + private interner)its own MailLog — the shell pending bit selects claim/reload at the post-join commit barrier, then receivers PULL in phase 1
updateGlobalTuples[coreId]global theorem registry + OR-pair completion
updateGlobalDirectTuples[coreId]direct-theorem emission
pendingCompactionQueue[coreId]deferred implication compaction (§3.5.3)
inductionMemoryBlocks[coreId]activateZeroCondition
  • I-28. During the parallel phase a worker never writes cross-LB shared state (global theorem list, dependencies, OR candidates, another block's exprOriginMap). All such effects are recorded into per-core slots or mutex-guarded collectors and applied after the join. No locks are needed in the hot path because there is nothing shared to lock.

Barriered phases + the flat split pool. The elementary step is three phase helpers — performElemPhase1 (absorb incoming mail), the hashburst, performElemPhase3 (post-burst absorb) — with a join between each. Phases 1 and 3 are plain across-block work-stealing sweeps. The hashburst (phase 2) is a flat pool over every active block and every expression bucket of a split block. No block spawns its own sub-threads. After the pool joins, a per-block step concatenates and canonically sorts that block's firing records before applying them.

Phase 2 has two explicit backends. The processor route is the default of every run (a customer PC needs no GPU); main.py --GPU selects CUDA for the whole run, and a batch configuration may pin one batch to CUDA with use_gpu: true. The CUDA full-run route keeps the same three barriers and the same final deposit door, but batches the read-only block images and runs request filtering, growth, ordering, evaluation, and full provenance construction on the GPU. Every evaluated firing is retained until the shared finalization. Split blocks still use the processor stump producer to discover disjoint work branches. The device emits complete canonically ordered firing records; the host only converts their ownership and applies them. A selected CUDA route never silently falls back to the processor. Capacity-bounded chunks keep one split block's task family intact, omit structurally impossible request batches, and cover every full-run incubator and Peano/Gauss batch. The two routes have produced byte-identical proof artifacts on the FTA shortcut identity gate; the full route is additionally gated by the complete verifier count.

CUDA growth is adaptive inside the global frontier. A preparation pass builds one immutable normalised prefix and path summary for every live node in three measured fixed pools. Each prefix queries an index of possible next predicates, including their positive or negated form. The index is derived from the actual subkey and whole-key tables, including retained short subkeys; it preserves the prefix's argument-sharing pattern. Only matching predicate ranges after the original statement cursor enter candidate construction. Stable selection then lists short and long nodes in their original frontier order. The node spans are sorted by call, run, path, and candidate and scanned into one exact ordinal stream. Consecutive fixed windows cover that stream completely. Short threads and 64-lane blocks apply the cheap gates, survivors compact stably, and only survivors perform the exact key and owner probes. Pool placement, window size, and thread arrival never become ordering keys; retained semantic tokens still determine every observable order.

Frontier levels stay on the GPU. Each growth level and its children live in two pass-local device buffers of 8,388,608 nodes each. Their blocks come from a separate reservation of spare device memory beside the 4 GiB working budget, so the store never shrinks the other columns. The buffers fill that reservation rather than following the measured level, because a level larger than every earlier one would otherwise outgrow them. Without spare memory, the buffers follow the measured level inside the working budget. Only a level larger than the store moves to host RAM pages; such pages would otherwise stay resident for the rest of the batch.

Statement setup also records which iterative arguments are distinct and are not recursion products. Candidates reuse this small mask, comparing only those arguments against the current prefix. Hypothesis length and scope checks run before that comparison. The membership word grows from one to four bytes per retained statement row; all acceptance decisions and statement positions stay the same.

The scope comparison also supplies the deeper compatible scope immediately. Candidates reuse that answer; unrelated scopes still reject the combination.

Encoded statements are filtered before upload. Each logical block supplies the core name and polarity of every rule premise. Only matching encoded statements enter device memory, in their original relative order; being a goal alone does not require upload. A matching statement must also fit the argument pattern of at least one live rule premise: every fixed (u_) argument carries the same constant, repeated premise variables meet equal arguments, and the statement's scope lies on one line with the rule's scope. The processor route applies the same pattern test in its request filter, so both routes keep the same eligible statements. Argument matching, iteration limits, and frozen-branch filtering still run on the device.

Construction reserves measured input sizes. Consecutive complete logical blocks are packed against available GPU memory plus minimum execution scratch. Twelve host workers receive deterministic disjoint block assignments and reserve their measured column totals. The merge restores original block descriptor order; identical name and rule-string tables still share physical storage.

Full buffers pause and resume. Requests remain on the GPU while bounded owner and value windows evaluate them. Completed results download to RAM; a marker is retained as one complete record after its key fragments assemble. The input snapshot stays unchanged. After all retained growth levels finish, the shared CPU/GPU content comparator sorts its records in RAM before the existing final deposit.

Projection upload overlaps only independent host scheduling. Fifteen packed columns needed by filtering, growth, and ordering copy immediately. Nine columns first consumed by evaluation travel through fixed page-locked staging on a separate CUDA stream while the host builds the task and call schedules. The stream joins before the first kernel, so all 24 columns are resident before any proof calculation starts. This changes waiting time only: no table is omitted, no kernel races an upload, and the device checksum still covers every used byte.

The split is statistics-driven and expression-only. Every burst completes its deterministic retained growth levels; a storage limit never truncates it or causes discard-and-redo. At the end of an iteration, proveKernel totals each block's completed submatch work. A block whose work exceeds both the balanced per-core share and the setup break-even is marked as a straggler for the next iteration. A newly activated induction-zero block is also split on its first active burst because it has no earlier statistic.

A split block first runs one read-only producer over the whole block. It enumerates expression combinations called stumps from overallHashMemory, which is the superset from which the working and local hash memories are populated. The stumps are dealt round-robin into at most one bucket per logical core, then each bucket runs the ordinary request generator while accepting all rules. The filter and name sort are paid once per bucket. On the CUDA route the buckets join the same device pass as the unsplit blocks: the producers run first on the processor, then one projection, one device route and one finalize sweep cover every block of the iteration.

A stump named here is always a split stump — a place in the search where one worker picks up. The generator once had a second, unrelated thing by the same name, a fact it was obliged to attach to every request it produced; that one is gone, and requests now carry their mandatory facts by being checked once they are complete (§3.2.4).

A stump the producer grew may name a fact a particular bucket's rule pool has no use for, because the producer reads the superset. That bucket skips the stump: it could produce nothing there, and every larger combination reachable from it still contains the same unusable fact.

A stump is a resume point, not a filter. The unsplit request generator searches combinations by adding one statement at a time in ascending name order, so every combination is reached along exactly one path. A stump names one node of that same search. Its bucket restarts the search as if the stump had just been matched and grows it onward, taking only statements that come after the stump's last one, and the run ends exactly where the search would drop that last statement again. A bucket therefore owns one whole branch of the search and nothing else. Because every combination has a single path, different stumps own disjoint branches that together cover the entire unsplit search: the split divides the work rather than duplicating it, and a split block does exactly the work it would have done alone.

This is what makes splitting worth its cores. An earlier scheme instead attached the stump to freely grown combinations and let a bucket keep whatever contained it — which meant a combination holding several stumps was rebuilt once per stump. On the heaviest burst of the shortcut run that tripled the work, so thirty-two cores bought almost no wall-clock time. Under branch ownership the same burst runs two and a half times faster and the whole run drops from 219 to 129 seconds.

When the producer replaces a short combination level with a larger one, a short combination that can already complete a request is retained as a terminal pre-stump. Its bucket checks that combination against the actual hash memory for each request batch and sends valid requests through the same pre-evaluation and checker as every other request, but does not grow it further. The larger child stumps own all larger combinations. This is why the overall memory is enough to discover work but is never trusted as the final validity decision.

Each bucket reads the same frozen block and produces complete firing records. The processor keeps its original early-exit position. The GPU uses the original goal and contradiction predicate, retains all results in the current growth level, then stops that block's later levels. One eight-byte state per block records whether CUDA observed a discharge. Physical buffer drains never commit the stop; all seed calls at the current depth or all nodes of a frontier wave finish first. The unfinished frontier stays in the pass's GPU frontier store, with any overflow in RAM. No request identities or pending firing history are retained for early exit. Multiple firings preserve their dependency levels, disintegration signals and proof origins. Captured heads reach goal closure and discharge in phase 3. Phase 1 also completes the shared hypothesis, discharge and scope-cleanup sequence for absorbed mail before GPU requests are built.

Counterexample mode gates standard processing before the ordinary sequence: only registered and pending-head contradiction checks run, then the call returns. No mail absorb or equivalence processing runs inside that mode.

GPU counterexample filtering constructs groups of 64 independent clones. They share setup and construction workers; automatic device planning divides each group into bounded chunks. Mirror refutation still follows the complete pass.

Each candidate window launches only the covering slice of the ordered node lists. Nodes whose candidate ranges lie outside the window do not need gate workers; every candidate inside the window still receives the same checks.

Frontier transfers use five pinned blocks from the independent GPU-host pool. Larger copy pages share each transfer call; each page fits one host block, and the blocks are unpinned before release. Early exit keeps only one state word per block.

The processor is retained for the ASIC path. GPU performance may take priority over CPU matching. Valid proofs and deterministic GPU results remain required.

The RAM-side sort uses bounded initial runs and page-backed run directories. Each merge pass reads two runs and writes one sorted run, so more results require more pages and passes rather than a fixed-size cursor array.

5.2  The join barrier

When every block has been stepped the workers join. Nothing in the serial phase starts until the last worker is done, so it always sees a complete, quiescent set of per-core results — never a half-written one. This one barrier is why everything below can be applied with no locking.

5.3  Serial collectors & deferred writes

After the barrier one thread applies what the workers only recorded, each collector in a sorted order chosen so worker finish-order cannot change the outcome:

  • MailLog commit barrier + phase-1 pull. Each LB's mailOut is committed once to its retained MailLog chain at the post-join barrier. Outboxes and their private interners may already be cold; the barrier probes only an always-resident pending bit, then claim/reloads one producer before serializing and clearing it. If every block was active when the grid completed, the already-delivered blob/reference window and its global mail-id table are reset immediately before that commit; otherwise both remain for dormant catch-up. Receivers pull in phase-1: a per-(recipient, ancestor) cursor advances over un-ingested batches and MailLog::mergeBatchInto merges them per recipient — statements/implications set-wise (commutative), origins by linear de-dup. Byte-reproducible regardless of fill order.
  • Sort queues. The per-core updateGlobal* / inductionMemoryBlocks queues are sorted before anything consumes them.
  • activateZeroCondition. Drains the queued induction base/step/typing activations (touches the parent's child edges in the SimpleMapStore — an ancestor-direction write, hence deferred).
  • updateGlobal / updateGlobalDirect. Mutex-guarded; write the theorem registry and check OR-pair completion.
  • Deferred compaction. Sorted pendingCompactionQueue → compileImplicationToCompact → merged into the root's mailOut, shipped by the next MailLog commit barrier (§3.5.3).

The general rule: an ancestor-direction write from a descendant cannot ride mail (which routes downward). The accepted pattern is the deferred-action collector — a mutex-guarded vector on the analyzer, drained single-threaded post-join in sorted order:

CollectorProducer → drain action
inductionMemoryBlocksaddStatement recursion branch → activateZeroCondition
updateGlobalTuplesworker updateGlobal → registry + OR completion
updateGlobalDirectTuplesworker updateGlobalDirect → direct emission
pendingAncestorOriginsretired — never pushed; drain iterates empty

5.4  Why deferral — a worked race

Worked race — non-deterministic implication<N>
  1. Symptom. Two runs on a byte-identical theorems.txt produced different compact names — implication1359 vs implication1361 — with torn diagnostic-trace lines.
  2. Cause. compileImplicationToCompact was being called inline at the eight broadcast sites. But updateGlobalDirect also runs on the parallel addExprToMemoryBlock contradiction path, so the inline compile mutated global name state (implCounter, compiledExpressions, repetitionExclusionMap) from multiple worker threads with no synchronisation — a direct I-28 violation.
  3. Fix (Option A). The eight sites now only recordPendingCompaction into a per-core queue; a single-threaded sorted pass after pool.join() performs the compile and deposit, shipped by the post-join MailLog commit barrier. Deterministic and injective.

This is the template for every deferral in §5.3: if an effect mutates shared state, a worker may only record it; the single-threaded sorted post-join pass applies it.

That same reasoning is now embodied by the pull model: the cross-block mail seam is the single-threaded commit barrier at the post-join point (the role smashMail filled, before it was deleted), and per-block pulls read the frozen logs — there is no parallel drain to reorder. (Routing mail is also main-only by I-26 — a hypothesis-conditioned rule must not be shipped and reinstalled unconditionally; see §3.3.3.)

5.6  Per-LB mailbox geometry (retired — replaced by the pull model)

This geometry is retired. The push routing it served — every worker writing an outgoing copy into a per-core mailbox slot, then smashMail consolidating the slots into recipients' inboxes — has been replaced by the pull model: each block stores the mail it emits once in its own retained chain (MailLog on the analyzer), and a receiver pulls un-ingested batches from its ancestors' logs in its phase-1, advancing a per-(recipient, ancestor) cursor. There is no outbound copy and no per-core slot, so the contention this structure existed to avoid does not arise. Each block's mailOut is committed to its chain single-threaded at the post-join barrier; when the completed grid had no dormant block, the delivered chain window and its global id table are reset first. The parallel pull only reads frozen retained pages and writes its own cursor row. See Substrate §3.3 (the pull model).

5.7  The cycle-N rule

The deepest sentence in the parallel design is also the shortest:

An LB's cycle-N execution cannot depend on anything another LB produced in cycle N.

The mail boundary is the only cross-LB observation channel, and the boundary fires between cycles. Inside cycle N, every LB sees only what arrived at the previous boundary — i.e. the union of every LB's outputs from cycle N-1. Within cycle N, the workers cannot observe each other's progress, and must not need to for correctness.

5.7.1  What “cannot depend on” actually rules out

The rule is enforced by structure, not by check. A worker can read its own LB's state freely — that LB is uniquely owned for the duration of the step. But the worker cannot:

  • Write into another LB's local state (its intEncodedStatements, its exprOriginMap, its admission map, its mail). All such writes ride per-core slots or class-level deferred collectors and are applied after the join.
  • Read another LB's in-flight cycle state. Inherited ancestor state is fine (a tree-walk upward), because ancestor LBs are not actively being stepped by another worker on this same cycle — they belong to the ancestor chain whose cycle is the same as the descendant's, but their writes still land at boundary time.
  • Mint a globally-unique name from the singleton counters. That mutates global state (implCounter etc.) and would race; the fix is to record the pending compaction and mint at the post-join pass.
One thing the workers carefully record rather than apply is provenance. The last chapter is what that record is — and the firm rule about what it must never be: provenance.

Capacity for the connected FTA batch

The full run and development shortcut use the same fixed GPU capacity profile. Both execute FTA from the same captured input. Its accepted-event ledger and ordering arrays share a 6,291,456-event ceiling; an overflow remains a visible failure. Per-pass counts record accepted events, raw requests, and unique requests so the reservation can be checked against the complete run. Frontier and prefix buffers are also sized from the full corpus, with at least twenty percent headroom in each resized pool. All full-run batches share these limits. Each batch allocates its full reservation, so larger limits can affect earlier batches even when their proof workload is unchanged. Runtime acceptance therefore compares the existing stages as well as complete proof identity.

Reverse-owner work storage

The shared full-run and replay evaluator reserves 4,194,304 entries of eight bytes for reverse-owner expansion. A measured batch required 2,880,228 entries; the reservation occupies 32 MiB. It changes fixed storage only: matching, ordering, provenance and the assertion on overflow remain unchanged.

Allocate from the available GPU budget

The budget is the free VRAM after a runtime reserve, capped at 4 GiB by default: every chunk's plan fills the whole budget, so an uncapped budget would take nearly all VRAM whatever the chunk needs. The planner reserves measured LB input and minimum execution scratch, then fits processing buffers into reusable 2 MiB blocks. Recorded full-pipeline demand seeds the proportions; completed-batch occupancy and drains adjust them. A large LB or pending output can receive space by reducing other processing capacities. The production planner uses measured costs, is tested across simulated VRAM budgets, and allocates at completed chunk boundaries. Individual payloads retain the CPU's existing storage representation, while result collections drain through value and marker-key windows.

Measure storage before reserving it

Each GPU buffer can report its complete device size before construction, including CUDA library workspace and aligned array placement. This supplies the automatic planner's byte costs. The production controller chooses and lends these capacities at completed chunk boundaries.

Pause and resume request generation

The bounded generation component keeps each frontier level in GPU memory for the duration of one pass, the level and its children in two buffers; only the rows of a level too large for a buffer enter bounded host tails. With deload enabled, each tail keeps at most 32 MiB of row payload and spills earlier rows to disk; bounded reloads preserve the saved request identities. Counterexample filtering and resident-only batches retain the existing RAM path. CUDA processes seed, prefix and candidate windows. Cheap rejection uses the candidate buffer; the surviving indices are divided into output windows with enough room reserved before every write. Probe windows consume the remaining output space. A small tail, below one quarter of full-window capacity, pauses generation until evaluation retains all of those requests' results. Original call and premise identities remain intact. CUDA performs every semantic operation; the host schedules sizes from upper bounds and reads exact counts only when a buffer could fill. Frontier transfers prefer pinned 4,096-row pages within one host block. No early-exit request-identity pages are needed. Up to 65,536 consecutive frontier rows share one GPU preparation when their allocated columns fit. A transfer boundary does not force a new execution window. Complete pipeline runs verify theorem coverage and GPU determinism and record the transfer cost.

Repeated requests and firing results

Every request that passes generation gates reaches evaluation, including repeated premise identities. There is no request duplicate table or retained history in RAM or GPU memory. Different requests may derive the same expression in the same validity scope. Their firing records remain: dependency levels, disintegration instructions and proof origins are combined by the existing result-deposit processing.

Resumable evaluation windows

The production evaluator uses bounded windows. Request checks run once. Wide offsets describe the complete owner and rule-value expansions; each physical window fits its processing arrays. A single request or encoded hit can cross several windows without restarting its checks. The caller retains each result before reusing a window. Device-side output bounds measure every result column before allocation, and one marker's keys can be emitted in consecutive fragments. Host sealing now keeps output pages open across downloads and assembles marker keys into one complete record. Repeated fragments reuse the sealed marker header and invariant arguments. Individual payloads retain the existing CPU span representation; the automatic planner reserves one supported fragment and all result collections stream.

The output scheduler now packs complete values by measured capacity across every column, or selects the largest fitting marker-key fragment. Frontier rows cover one preparation or survivor probe, independently of the larger candidate-attempt storage. Small metadata transfers accumulate into one fitting execution batch; metadata pages do not force extra result downloads. If the smallest next fragment requires more storage, it retains its position and reports the required capacities. Production reserves the CPU-supported minimum fragment before execution; explicitly smaller component buffers keep this non-consuming scheduling state.

Sort only the meaningful path bits

Each of the eight request-path components fits in 17 bits. Their stable GPU sorts examine those bits; task, call and run components retain their full width. Every event keeps the same position and ties keep their existing order. Record sizes and memory budgets are unchanged.
