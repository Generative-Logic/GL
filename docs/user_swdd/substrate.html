3.1  Logic blocks

A logic block (LB) is the unit of execution: a self-contained hash-inference engine that owns all of its own state and reaches its neighbours only by mail. The class is Memory. The whole prover is a tree of these; the model is silicon-shaped — one block ↔ one core on the ASIC roadmap.

3.1.1  The block tree

One root, body (empty exprKey, parentMemory = nullptr). Children are created on demand, in six kinds. parentMemory walks up; child edges route down by key, held off the block in the shared, never-deloaded SimpleMapStore. Every cross-scope move follows this chain of explicit parent/child links — there is no global symbol table.

3.1.3  Lifecycle & per-core batching

Birth → registration into permanentBodies and under the parent in the SimpleMapStore → active stepping while isActive → deactivateRecursively when the goal proves or the scope discharges → teardown. Main blocks persist for the run; compressor blocks are explicitly deleted. The driver carries the grid as permanentBodies (all LBs); cross-block mail is the pull model (MailLog on the analyzer — see §3.3, the per-core boxes and the old parent→children index are deleted). The counterexample filter has the parallel permanentBodiesCE set because it uses a different request generator and budget.

3.2  Hash engine

3.2.1  Inference is a memory lookup

A traditional prover searches for a derivation. A GL block asks: does any rule I know already fire on what I have? Every implication is hashed by its premise pattern; a matching fact is an O(1) lookup. Correctness rests on canonicality — alpha-equivalent expressions must hash identically — which §3.5 guarantees.

3.2.2  The rule store — HashMemory & LocalMemoryValue

HashMemory's heart is encodedMap: a premise-pattern integer hash → a list of rule entries (LocalMemoryValue) sharing that pattern. Around it sit the admission and rejection maps (the subject of §4.2) and an owner-set existence index.

3.2.4  A local rule, non-local facts — the 5-batch fan-out

A rule a block owns may fire on facts it does not own (inherited from an ancestor scope) — correct, not a leak. Request generation fans out over five batches pairing a rule pool with a mandatory-fact source; batches 4 and 5 are deliberately broad so a freshly-installed rule still meets every visible fact, not only this cycle's.

3.3  Mail

3.3.1  The cycle-boundary protocol

Parallelism and determinism pull against each other; mail resolves it by pinning every inter-block observation to the cycle boundary. The carrier is the pull model (MailLog on the analyzer): each block stores the mail it emits once in its own retained chain, and a receiver pulls from its ancestors. Five phases: (1) cycle start — each block pulls the batches it has not yet ingested from each ancestor's log into its mailIn (walking its parent chain, advancing a per-(recipient, ancestor) cursor); (2) body — each main-scope emission pushes to mailOut; (3) after all workers join, a grid that started with no dormant block releases the delivered blob/reference window and resets the matching global mail-id table; a grid with any dormant block keeps both full history and that id table for the block's later catch-up; (4) the single-threaded commit barrier reads each block's resident pending bit, reloads only blocks with output, appends mailOut as one batch, then clears the outbox and its private interner together; (5) next start — the pull delivers (every payload arrives as a statement — atomic facts route to addStatement and compact implication forms (implication<N>[…]) route to addStatement with status=3, which recovers the rule into hash memory without re-disintegration; origins merged; positive 2-arg equality origins additionally synced into the matching EquivalenceClass.equalityOriginMap so the merge logic doesn't re-derive them into cycles), then clears it. An LB's cycle-N execution cannot depend on anything another LB produced in cycle N. Storing each emission once — instead of copying it into every descendant's inbox — is the point: the per-cycle staging storage drops from O(descendants) to O(1) (the retired push routing sendMail / per-core boxes / smashMail is deleted).

3.3.2  The two channels

Mail fieldShape
statementsset<pair<ExpressionWithValidity, levels>> — each carries its install scope. Atomic facts and compact-form implications (implication<N>[…]) share this single payload channel.
exprOriginMapmap<ExpressionWithValidity, list<Origin>> — provenance to merge

One payload field, not two. A previous design carried implications on a separate Mail::implications tuple channel (set<tuple<chain, head, args, levels, theorem>>) deposited inline at broadcast time. That channel is deleted: every implication now ships as a compact (implication<N>[…]) statement on the same Mail::statements field as atomic facts, and the receiver's addStatement recognises the compact head and routes it back into hash memory under status=3 (recover-the-rule, no re-disintegration). The unification removed an entire parallel mail path and one race the previous inline-deposit shape kept exposing — see Chapter 3.5 §3.5.3 for the compilation half of the story.

Every block has mailIn/mailOut staging for the pull model. The inbox is always-on until phase-1 absorb; the outbox is deloadable block state with one private string-id table and an always-resident pending summary. Each block also has two internal channels — sameIterationInternalMail (the integration-revival / same-step channel) and nextIterationInternalMail (cross-iteration deferral), both the same struct. 3.3.3  Main-only gate & deferred collectors

mailOut.statements is main-only by contract (I-26): a rule proved under a hypothesis is conditional on it; shipping it verbatim and reinstalling at v=main would drop the condition and fire unsoundly. A peer that needs a scoped fact re-derives it. With the implications channel deleted (§3.3.2) this gate now covers both atomic-fact statements and compact-form implications — a single rule for a single channel. mailOut.exprOriginMap is not gated — provenance for all scopes flows, so the chapter walker can resolve cross-LB chains.

Mail routes downward (parent→children). An ancestor-direction write from a descendant cannot use it. The accepted pattern is a class-level deferred-action collector: a mutex-guarded vector on the analyzer, drained single-threaded after the worker join, in sorted order (Chapter 5).

CollectorProducer → drain action
inductionMemoryBlocksrecursion branch of addStatement → activateZeroCondition
updateGlobalTuplesworker updateGlobal calls → global theorem registry + OR-pair completion
updateGlobalDirectTuplesworker updateGlobalDirect → direct-theorem emission
pendingCompactionQueueany worker that proves an implication → after pool.join(), compile it to (implication<N>[…]) compact form, allocate the next global N single-threaded, deposit into the producer's own mailOut.statements for next-cycle broadcast (the channel-unification half of §3.3.2; race-prevention rationale in Chapter 5)

3.4  Scope & validity

3.4.1  First-class scope

“Assume P, derive Q” makes Q true only under P; a case split makes each branch's facts true only there; integration and induction-typing open their own contexts. So every statement carries a validityName, and escaping a fact to its parent is an explicit audited step. A flat “is it proved?” flag would be unsound.

3.4.2  NameMap & minting

The canonical name is literally parent + "_boundary_" + payload (I-2: non-root scopes must be minted via encodePush — raw concatenation orphans the scope and corrupts depth comparison). The payload shape encodes the role, recoverable without a side table:

3.4.3  The stack, comparison & cleanup

stackOfValidity is the per-block validity-id forest — the paged, cold validityNodes reached through NameMap accessors (stackSize() and friends), not a heap vector. A scope is pushed on open and popped on discharge; a new fact is tagged with the top. comparable(a,b) is true iff one is the other's ancestor; deeperOf(a,b) returns the deeper. On export the ancestor chain is recovered by splitting the canonical name on "_boundary_" (the delimiter check is mandatory). When an implication subproof closes, wipeSubtree physically removes all per-block state at that scope and below — but it is queued (pendingWipeScopes) and run at the burst boundary, never mid-kernel (I-50), so in-flight asserts don't trip.

3.5  Compilation

Compilation is the precondition that makes §3.2's lookup bet correct: it turns expressions into compact, canonical names so semantically-identical forms hash identically. Three facets.

3.5.1  Structural-operator precompilation

precompileStructuralOperators rewrites, in place and recursively, every negated structural form into its compiled name: !(&…) → or<N>, !(>…) → existence<N>. It compiles only the negated forms: a plain top-level implication (>[]()()) is never its input and is never compiled to implication<N> on a load path — implication<N> is allocated only for implications that appear as subexpressions of a compiled definition body (plus the mail-compaction wrapper in §3.5.3).

  • I-1. Every theorem-load path must call this first. Skip it and an uncompiled or<N>/existence<N> reaches the encoder as its raw structural operator — the index then treats two semantically-identical expressions as different rules. The symptom is an assert deep inside disintegration.

3.5.2  Integer encoding & canonicality

Past precompilation, every string expression has an EncodedExpression form (head name, top-level negation, argument list with iteration/level metadata, the original string for round-trip, its validityName). NameMap::encode collapses every name to an int32_t; the resulting IntNormalizedKey is a packed (name_id, arg_ids…) array — cheap to hash, fast to compare. The string form is canonical but slow; the integer form is the hot path. This is why §3.2's lookup is O(1) and correct: two alpha-equivalent expressions normalise to the same IntNormalizedKey.

3.5.3  Implication compaction

Every proved implication that needs to cross a block boundary is compiled to a compact (implication<N>[args]) atom and deposited as a mailOut.statements element at v=main, with a paired compilation origin (original expanded implication as its sole antecedent). Compaction is now the sole path by which an implication reaches another LB: the older parallel Mail::implications tuple channel (§3.3.2) is deleted. The receiver's addStatement recognises the compact head and recovers the rule into its hash memory under status=3 — no re-disintegration, just rebuild the chain hashes from the compact atom.

  • Deferred, never inline. Broadcast sites call recordPendingCompaction to enqueue; a single-threaded sorted pass after the worker join runs compileImplicationToCompact, mints implication<N> from the global counter, and performs the deposit. Compiling inline raced the global name counters (implCounter/compiledExpressions) on the parallel contradiction path — the cause of run-to-run implication<N> drift, fixed by D-76.
  • Canonical reconstruction. Alpha-equivalent implications collapse to the same implication<N> name, and the binary stores only the first-seen body. The compilation origin row's antecedent must therefore cite the canonical body via reconstructImplicationFullBind(elements[:−1], elements[−1]), not the raw expanded form the producer happened to queue — otherwise verifier chapter-citations would not match the binary's recorded shape (I-52).
  • No defensive fallback. An enqueued implication that fails to compact asserts at its origin; it never returns an empty/sentinel string. The prover treats every unexpected state as a bug to surface at its source, not a condition to paper over. The historical “an implication may not be a constituent of another compiled expression” invariant was retired by explicit decision — a nested implication is now a recursion-stop leaf, not an assert.
  • Empty levels at deposit. Every Mail::statements entry shipping a recovered rule deposits with an empty std::set<int> for the level set (I-51). A non-empty deposit silently breaks the allLevelsInvolved discharge gate at the receiver, suppressing the rule until levels overflow — a class of bug that surfaces as a contradiction-LB latency hang far away from the wrong deposit site.
Invariant — guard at refactor time. Compaction is the on-the-wire representation of an implication, not a separate side-effect: the compact atom is the mail payload. The hash engine on the receiving side rebuilds the expanded rule from that atom under status=3 and fires from the recovered rule, not from the compact atom itself; treating (implication<N>[…]) as a directly-firing premise instead of as a rule-recovery payload would change which derivations the prover finds, and break the symmetry between the producer's expanded implication and the receiver's recovered rule.

3.6  Delta machinery — what one cycle added

Several mechanisms need to know, at the end of a cycle, what changed during that cycle — not the cumulative state. The 5-batch fan-out (§3.2.4) uses it to feed fresh local rules against fresh local facts; the deferred compaction queue uses it to know what implications need compact-form atoms; the chapter walker uses it for goal reachability. The mechanism is the delta pair: a …Delta container alongside every cumulative container, cleared at burst start, appended to on every emission.

CumulativeDelta — appended during the cycle, drained at end
intLocalEncodedStatementsintLocalEncodedStatementsDelta — feeds the locality gate inside Pass B
localHashMemorylocalHashMemoryDelta — rules installed since burst start; the “fresh rules” pool in batch 5
exprOriginMap(no explicit delta — implicit by mailOut snapshot)
The delta is what makes the 5-batch fan-out fast. Without it, every cycle would have to scan the full cumulative store to find “rules installed since last cycle” — quadratic over a long run. With it, batches 2 and 5 walk a vector of length equal to the cycle's emissions, typically a handful to a few dozen entries.

3.7  Subtree wipe — deferred to burst boundary

When a scope closes — a hypothesis discharged, an OR convergence completed, a contradiction reconstructed — every fact, rule, equivalence class, and origin entry tied to that scope or deeper must be removed from the LB's state. The function is Memory::wipeSubtree(closedScope). The catch: running it during the cycle would invalidate iterators the kernel is holding (the kernel walks the local containers as it fires).

The fix is queueing: every site that wants a wipe pushes the scope name into pendingWipeScopes; the burst boundary drains the queue and runs wipeSubtree once per queued entry. This is I-50.

A disproof feeds the same queue from outside: when a primed contradiction block proves the negation of a parent goal, the theorem drain deposits the seed on the parent's disproved-goal inbox (pendingDisprovedGoals, never-deloaded persistent memory, so the deposit works even while the parent is evicted). At the parent's next burst boundary, drainDisprovedGoals probes the seed against the parent's main goals; on a hit it erases the dead goal, queues every scope whose payload names that goal (the <goal>_subproof_ and hypothetical-disintegration shapes) for the subtree wipe, and additionally clears what a scope wipe cannot reach — the goal's preparation gates, its origin-history rows, orphaned internal-mail origins, and OR cohorts whose parent scope died. A miss is the benign twin case (the reductio twin proved the goal instead) and does nothing.

What wipeSubtree actually removes. Everything whose scope (validityName) is a descendant of the closed scope: encoded statements, hash rules, equivalence-class members at that scope or below, admission entries at that scope or below, origin entries at that scope or below. The data that lived under the scope is gone; data at strictly-ancestor scopes is untouched.
