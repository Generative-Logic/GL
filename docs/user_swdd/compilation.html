8 · Compilation & names

The prover hashes expressions. For that to be sound, two syntactically-different writings of the same idea must hash identically. This chapter is everything that makes that true: the structural-operator compile, the five name families, the counters that keep names unique, the encoder that packs a string into a 32-bit integer key, and the static memory pool the hot path lives in.

Why this chapter is separate. Compilation appears as a single subsection of §3.5 in the substrate chapter, but most of GL's soundness arguments — and most of the “quiet” bugs that have ever crossed the boundary between cycles — live here. The substrate section is the survey; this is the reference.

8.1  Two canonical forms — why compile at all

GL keeps every expression in two canonical forms simultaneously: a human form (MPL string) and a machine form (a packed integer key). The string is canonical so a maintainer can grep a proof graph; the integer is canonical so the hash engine can decide “does any known rule fire on this fact” in O(1) instead of O(|rules|). The compiler's whole job is to keep those two layers in lock-step — so the same idea always picks up the same string and the same integer key.

“Aligned” means three concrete things, all of which the rest of this chapter delivers:

  • Structural normalisation. !(&X) and the pre-compiled or<N>[X] mean the same thing — but only the second can be hashed soundly. Precompilation (§8.2) rewrites the first into the second.
  • Name stability. If two distinct runs allocate existence3 to two different logical shapes, the rest of the pipeline (chapter walker, verifier) sees a phantom theorem. Counters + the shared registry (§8.4) keep names stable across batches.
  • Cheap equality. The hash engine asks “same expression?” millions of times per second; a strcmp on a tree-shaped string would dominate. The encoded form (§8.6) makes that an integer-array compare.

Compilation uses focused components

The prover asks the structural compiler to compile an expression. Separate components prepare OR, existence and supporting rules, and ask for compact compilation when they need a new implication. A private definition registry owns the tables and name counters. Proof operations read those definitions through read-only interfaces. Persistence loads and saves the same registry formats.

Parsing, normalization, definition reuse, expansion and implication construction each keep their own operations. The recursive compilation order and resulting names stay the same.

Argument types are analyzed below compilation

The argument analyzer checks configured types and recognizes set definitions. Its parser builds the expression tree, combines free argument types, and removes variables bound by each implication. Both use read-only source definitions.

Expression syntax has its own component

The compiler asks ExpressionParser to read expression trees, normalize conjunction premises, split independent conclusions, and rename a bound compilation variable. Parsing needs no proof-block state; its recursive helpers are private. Definition registration and name allocation remain compiler responsibilities.

Reuse normalization has its own component

CompilationNormalizer constructs normalized compiler keys and argument mappings, and puts a body's premises in canonical order: sorted by operator name, and inside each same-name group in the order whose normalized form is smallest, an implication's conclusion last. Every definition therefore has exactly one reuse key, and a body written in another premise order or with other variable names finds it. The stored element order stays as compiled. It carries no prover state. Inference keeps its separate integer-key algorithm.

Reuse state is private to its owner

CompilationReuse owns normalized identities, public-name precedence, OR argument mappings and generated-name replacements. Callers request registration, lookup or retirement through operations; readers receive immutable views of the records. Definition stores remain separate.

Expansion reads definitions through a separate component

DefinitionExpansion reads source and compiled definitions, expands expressions, and transforms argument bindings. It carries no prover object. Allocation-free binding operations continue to use the caller's scratch arena; worker selection retains the same thread-local identity and lifetime.

8.2  Precompilation — I-1

precompileStructuralOperators is the first thing every theorem-load path runs (I-1). It walks the expression tree once, in place, and rewrites the negated structural forms into their compiled atomic names. The positive structural forms are left alone — they are still legitimate MPL bodies and remain meaningful as they stand.

When an existence statement and an implication are equivalent ways to define the intended relation, prefer the existence statement. Preserve the same typing, polarity and quantifier scope; an existence claim cannot replace a stronger universal requirement.

Supplied Peano helper. The input file files/supplied_conjectures/peano.txt supplies successor cancellation: s(b)=c; s(d)=e; a+c=e ⇒ a+b=d. The batch appends this obligation to its ordinary generated conjectures. This bypasses discovery of the helper, not its proof: it is not a trusted external theorem. Later batches can use it only after the prover establishes and registers it.

Canonical spelling. After compilation every conjecture is renamed to its canonical spelling: variables are numbered in the order they first occur, and each is bound at the premise that first uses it. GL's own conjectures already have this form. A supplied row may not, and a theorem registered under another spelling could not be cited through its compiled form, whose expansion always has the canonical spelling.

The FTA predicate prime[N,+,*,i1,i2,p] uses the classical definition: p ≥ i2, and each natural divisor of p equals i1 or p. Here i1 and i2 are the anchor's one and two. Additive preorder expresses the lower bound; multiplicative preorder expresses divisibility. The E2 theorem projects the lower-bound conjunct for reuse.

The E6 predicate nontrivialFactor[N,+,*,i2,n,a] exposes one factor a and binds its cofactor b existentially. One definition keeps a*b=n and both bounds i2 ≤ a < n, i2 ≤ b < n on the same pair. E6 asserts that such an a exists for every non-prime n ≥ i2. The operator has one output slot; the second factor is its witness.

The property coprime[N,i0,s,*,a,b] says that every natural common divisor of a and b is the successor of zero, hence one. The definition uses the two multiplication witnesses of that same divisor; it constructs no greatest-common-divisor object. G1 supplies the Euclidean-step implication: if a and b are coprime and a=q*b+r, then b and r are coprime. Both configurations retain this named property and its original definition.

The Bezout equation bezEq[N,+,*,i1,a,x,b,y] states a*x=b*y+i1 for given coefficients. The symmetric Bezout property bez1[N,+,*,i1,a,b] binds natural coefficients x,y and requires bezEq(a,x,b,y) or bezEq(b,y,a,x); zero coefficients are allowed. Unfolding bez1 therefore yields two cases stated with the same predicate the helper lemmas use. G2 transports the property from (b,r) to (a,b) when b divides t and a=t+r, using two supplied helper lemmas that turn one orientation for (b,r) into the opposite orientation for (a,b). Inside each case GL builds at most one new value per lemma use, so two further lemmas state the coefficient z as an existence: a use inside a case builds only the product w=q*y. Both are ordinary properties with no output slot or recursive definition.

8.2.1  The compiled-expressions registry

Every successful compile inserts (or finds) a row in compiledExpressions, the analyzer-level table mapping a compact name (or7, existence2, …) to the structural template it stands for: head shape, arity, the bound-variable signature, the original MPL body, a category label (or / existence / and / implication). An or row additionally carries its or implications: the K mutual-exclusion rules and the subset-exclusion rules of that OR, compiled once as compact implication<N>[u_…] atoms over the OR's own tokens (the K rules when the OR is registered, the subset-exclusion family at the reduced-OR closure seam) and written to the GL binary under implications — a selected exclusion firing instantiates the required rule for proof history; the complete family is not installed as runtime rules. An existence row carries its two existence implications the same way — left → !right and right → !left, the rules its negation disintegrates into, compiled once as compacts over the existence's own tokens when the existence is registered. These lists form the row's disintegration set. An and or existence row also carries an integration set: every rule integration installs for an instance of the row — its one-level rule (the elements imply the entity), for an existence the same rule with the witness given, and, for the entity as integration goal, its flat variants, the introductions of their OR premises and the flat rules of those disjuncts — compiled as compacts when the row is registered and written under integration_implications. Both lists are written for every row of their categories and loaded exactly as written; no later pass fills a list in. Every later mechanism that needs to know “what is or7, really?” reads it from this registry — never from the string.

Compaction (§3.5.3) of proved implications, run after the worker join, deposits its compact implication<N>[…] atoms into the same table. The registry is therefore the single source of truth for every synthetic operator the prover ever invented during a run.

A numbered OR with exactly two digit-valued parameter slots also carries a derived symmetry mark when exchanging those slots preserves the signed flattened alternatives. The comparison sorts disjuncts and normalizes equality orientation while preserving free slots, binding and multiplicity. The two positions are recomputed after loading, so the binary format stays unchanged. Runtime uses them only to share OR processing; original statements and proof expressions remain intact.

8.3  The five name families

Variables and witnesses are not strings drawn from an open vocabulary — every name belongs to one of five families, and the family tells every downstream machine how to treat it. The prefix is the family.

u_<k>
Universal-template variable. Appears in compiled definitions and admission-map templates. Behaves like a free variable: it is not bound by any enclosing (>[…]), and it pattern-matches anything when a rule fires. Used as the canonical placeholder in admissionMap / admissionMapIntegration keys (§4.2.3).
v<k> (no underscore)
Theorem-level bound variable. A renaming pass at theorem ingest seeds v0, v1, v2, … in a deterministic left-to-right scan, replacing whatever the conjecturer/user wrote. This is the form that appears in files/theorems/theorems.txt and in chapter rows. The deterministic naming is why two semantically-identical theorems generated by different paths still compare equal as strings.
it_<k>_lev_<L>_<S>
Pass B iteration variable, algebra side. Minted by disintegrateExpr2 to stand for an as-yet-unknown value when an implication's premise contains a structural hole. Subject to the algebra-side admission gate (isAdmitted against admissionMap, fallback isAllowedAsOperatorInput, §4.2.1).
force_lev_<level>_<serial>
Forced witness. Introduced by the established assumption and forced-disintegration routes. Exempt from the ordinary integration-depth budget and eligible for fact/rule mail under the normal scope rules.
int_<depth>_lev_<level>_<serial>
Ordinary integration witness. Its depth comes from the original outer expansion. Minting requires an eligible depth, no existing algebraic witness input in the source existence, and the applicable integration admission. Rejected constructions do not park or admit dependent descendants. Its facts and compact rules remain local; proof history can still be transported. A parked construction preserves the assigned depth for later naming.
repl_lev_<N>_<M>
Substitution placeholder. Used during anchor handling and substitution chains to mark “the M-th replacement at iteration level N.” These names are deliberately not stripped on the integration probe (the removeUPrefixFromArguments helper takes off u_ but keeps repl_), so a substitution chain crosses the template/concrete boundary intact.

A sixth marker, the _copy suffix, is not a family of its own — it is a disambiguator that can attach to a name in any family. When a hypothesis is opened or an OR branch is seeded, the new scope sometimes needs a fresh copy of a variable that already exists in the parent; _copy keeps that copy syntactically distinct from the original. Two copies (e.g. v1_copy_copy) are possible and harmless.

Reading rule. When you (future agent) see a name in a dump, the prefix already tells you what the prover thinks it is — you don't need to track back to where it was minted. it_5_lev_1_2 is an algebra Pass B witness; repl_lev_2_0 is a substitution chain at depth 2, slot 0; v3 is the third bound variable in this theorem's left-to-right scan, and so on. The five-family discipline is the single biggest cognitive win in the codebase.

8.4  Counters & the singleton registry — I-23

GL is run-deterministic: the same configuration plus the same inputs always produces the same proof artefacts. Names that look spontaneous — or7, existence2, implication1359 — are the load-bearing test of that promise. They are not random; they are minted by four monotonic operator counters and one batch-local variable counter. The shared definition registry and its compilation-state sidecar carry operator identity and all issued numbers across batches.

CounterMintsLifetime
implCounterimplication<N> — compact-form proved implications (§3.5.3)monotonic across batches; persists via the shared registry
existenceCounterexistence<N> — De-Morgan'd negated universalsmonotonic across batches; persists via the shared registry
andCounterand<N> — explicit conjunction operators created by the conjecturermonotonic across batches; persists via the shared registry
orCounteror<N> — De-Morgan'd negated conjunctions (the branching workhorses)monotonic across batches; persists via the shared registry
variableCounterv<k> — theorem bound variables, plus internal scope mintingresets at the start of every batch; the only counter that does

Public names take precedence. A loaded predicate such as preorder participates in body-based reuse as well as lookup by name. If two public predicates have the same normalized body and category, in any element order, the first registered public name is reused; both public definitions remain available. Loading registers public names alphabetically.

If a public name supersedes a numbered operator, its numbered definition is removed. All applications are rewritten with the correct argument order: existence16[a,b,c,d] becomes preorder[a,d,b,c]. The rewrite covers dependent definitions, theorem inputs, scope payloads and proof references. The numbered name remains only in the migration record; the prover does not retain it as a usable alias.

8.4.1  Why variableCounter is the odd one out

v<k> names are local to a theorem — there is no semantic reason for v1 in theorem A to mean the same thing as v1 in theorem B. Resetting per batch keeps the names compact; nothing depends on global uniqueness. The other four counters mint names that do need global uniqueness (a chapter referring to or7 means exactly the or7 registered in compiledExpressions["or7"]), so they monotonically grow.

8.4.2  The race that implCounter nearly lost

Inline calls to compileImplicationToCompact during proof — one of the eight broadcast sites — used to mutate implCounter from worker threads. Two runs on the same input minted implication1359 and implication1361 respectively. The fix (D-76, see §5.4) defers every compaction to a sorted single-threaded pass after the worker join. The race illustrates the rule the rest of this chapter rests on: names are part of the proof; they must be deterministic; therefore minting them is a serialised post-join activity, never an inline worker activity.

8.5  NameMap, encodePush, scope comparison — I-2 · I-3

The four counters in §8.4 mint operator names. NameMap mints scope names — the IDs that show up in every fact's validityName. The two systems are independent on purpose: a name like or7 is global and grows across batches; a scope ID like 17 (decoding to main_boundary_hypo_v0) is per-prover and recycled on demand.

8.5.1  The one and only mint path

NameMap::encodePush(parentId, payload) is the single function that creates a non-"main" scope. It does three things in one atomic step: returns a fresh int32_t; interns the canonical string parent + "_boundary_" + payload into the cold name table; records its parent ID and own payload sub-id in validityNodes (the scope forest) so comparable and deeperOf can answer ancestor queries by walking the parent chain. The forest (validityNodes) is paged on the block's arena and deloads with it; an ID equals its cold-table ID directly ("main" is lazily interned as ID 1 on first use — no offset).

  • I-2. No non-root scope may be created by concatenating strings. Raw parent + "_boundary_" + payload outside encodePush yields the right string but no validityNodes entry, so comparable sees the new scope as unrelated to its parent — and the mail router silently drops messages for it.

8.5.2  The reference hazard — I-3

NameMap::decode(id) now returns an owned string (the bytes live on cold pages), so it is always safe. The hazard survives only for the zero-copy views: decodeView(id) hands back a span over the cold bytes, and an element read of the paged scope metadata aliases page memory. A nested mint (or a deload) can grow or relocate a page and dangle such a view — the bug appears as garbled scope names in dumps, or a string compare that used to match failing two cycles later.

Pattern. If you (future agent) hold a decodeView span (or a paged-metadata element) and then mint another scope (or anything that might transitively mint), copy it out first — or use the owning decode. The old stackOf reference into the metadata is retired; callers use the element accessors, so no long-lived reference into paged storage escapes.

8.5.3  The scope forest and the ancestor query

The scopes form a forest: every non-root ID descends from one parent, rooted at "main". Each scope stores just its parent ID (one ValidityNode in validityNodes); the full ancestor chain is walked on demand. To answer comparable(a, b) (“is one an ancestor of the other?”) the runtime walks b's parent chain looking for a, and vice versa; deeperOf(a, b) is the same test with a different return shape. The checks are O(scope depth), which in practice never exceeds the depth of nested hypotheses inside one theorem — a small constant. There is no separate pairMap cache: it was dropped because the per-scope ancestor list already holds everything comparable needs.

8.5.4  Why the canonical string carries the chain

The runtime uses the numeric ID for every fast operation. But the canonical string — main_boundary_hypo_v0_boundary_int_lev2_boundary_orint_X — is what gets written into chapter rows and into theorems.txt. The string carries the whole ancestor chain so the exporter and the verifier can recover the scope structure without shipping the validityNodes runtime forest. Two-track redundancy: fast at runtime, self-describing on disk.

8.6  EncodedExpression → IntNormalizedKey

A compiled string is canonical for humans. EncodedExpression is the in-memory wrapper that pairs it with everything needed for the hash engine: the head name, the argument list, top-level negation, iteration/level metadata, the validityName. IntNormalizedKey is the packed integer projection of that wrapper — the actual key into encodedMap.

WrapperWhat it adds
EncodedExpressionThe full pair: original MPL string + the parsed head/args + top-level negation flag + iteration level + the validityName. Used by emit paths that need the string and the structure.
ExpressionWithValidityA lighter pair — just (expression, validityName). The currency of newStatements, of mail, and of the chapter walker.
IntNormalizedKeyA pointer+length view — numberExpressions, length, and a non-owning const int32_t* data into KeyArena — over the packed run [ headId, arg0Id, arg1Id, … ]. Cheap to hash, cheap to compare. The hot-path key.
NameMap-IdThe int32_t id (NameId) a string lives at in the active name registry. Up to MAX_NAME_IDS (1,000,000) names per registry — large enough for every spontaneous and bound name in a run.

8.6.1  Why hashing is sound on the integer projection

Two expressions that should fire the same rule must produce the same IntNormalizedKey. That is guaranteed by three properties working together:

  • Structural normalisation. !(&X) never reaches the encoder; it has been rewritten to or<N> by §8.2.
  • Deterministic bound-variable renaming. v0..v<k> are assigned by a fixed left-to-right walk, so two alpha-equivalent theorems pick the same names.
  • Single name registry. Every name passes through NameMap::encode, which returns the same int32_t for the same string — the second character of the proof.

8.6.2  The owner-set existence index

HashMemory is the umbrella that owns the firing index. Alongside encodedMap (the premise-key → fireable-rules map) it carries normalizedEncodedKeys: an existence index keyed on the same IntNormalizedKey, with no value at all — a bare key set. It is never pruned: when a scope closes only the encodedMap rules go, and a stale key's request simply misses there. The pattern is refcount-by-owner rather than naked refcount — it lets the runtime answer “does any rule for this shape still exist?” in O(1) without a full sweep.

8.7  The static-memory floor — I-95

The hot path allocates millions of small objects per second — every hash request, every fired emission, every mail message, every cold-map entry. Routing those through the general allocator (malloc / new / std::vector) means contending with mimalloc's caches, walking free-lists, and occasionally hitting the OS allocator at a millisecond cost; worse, it leaves the working set unbounded and the layout non-deterministic — neither acceptable for the silicon target, where the prover must run inside a fixed on-die store. GL's answer is to make all prover memory static: one large reservation, taken once at program start, never grown, never returned to the OS during the run.

That reservation is owned by GlobalMemoryManager — the root of the statification memory hierarchy detailed in Chapter 6. It carves the pool into equal fixed-size blocks and hands them out on demand: a per-logic-block memory manager calls acquireBlock when it needs storage and releaseBlock when its logic block deloads to SSD or is destroyed. Both run under one internal mutex, because logic blocks are processed in parallel; recycled blocks are re-granted before fresh ones, so the carve cursor tracks the high-water mark of simultaneous demand rather than total allocations.

  • I-95. Every prover allocation comes from a pool block, never the general allocator. Pool exhaustion is an assert naming the configured pool size (static_pool_bytes and its siblings), never a fallback heap allocation — a sizing problem must surface at its origin, not be papered over.
  • Deload / reload. When the pool fills, the largest idle logic block is written to SSD and its blocks return to the dispenser; the bytes are re-read on the next access. The round-trip is a pure function of logical content — physical block identity and grant order are never observable (§6.5).
  • Nothing escapes to the heap. Under MPU 0.1 all prover state is static — the cold string tables, the encoded maps, the validity forest, the cross-LB mail log, even the logic-block object shells each draw from a pool. There is no “long-lived containers use ordinary heap” tier; the only heap left is start-up scaffolding outside the proof loop.

8.8  Failure modes

Compilation is the layer where mistakes are hardest to notice — the bug is a hash that silently fails to match. The patterns below have all bitten in practice; treat them as the canonical things to check first.

“This rule never fires.”
Raw !(&…) reached addToHashMemory without being precompiled. The rule got installed under one key, the requesting expression hashes under another. Check: the load path; was precompileStructuralOperators called first?
“Two runs produced different implication<N> numbers.”
A worker thread mutated implCounter. Check: every new compaction site goes through recordPendingCompaction, not inline compile.
“The scope name string is right but comparable returns false.”
The scope was created by string concatenation, bypassing encodePush. Check: every non-main scope is minted via encodePush(parent, payload).
“A scope name in a dump is garbled.”
A reference into NameMap's internal vector survived a nested mint. Check: every decode / idToSub[] result is copied into a local std::string before any further mint.
“Wall-clock has a long tail with stalls.”
A refactor introduced dynamic allocation in the hot loop. Check: no malloc / new / dynamically-grown std::vector<char> on any per-step path.
“A chapter row references an operator the registry doesn't know.”
A spontaneous name was minted but never registered into compiledExpressions; or the registry was reseeded from the wrong shared file. Check: files/GL_binaries/GL_binary_shared.json is the canonical maxima source; counters seed from it.

Fold: interval and accumulation

fold[N,s,+,op,f,n,m,p] follows successive indices from n to m. Addition defines that interval; the separate op combines the values. The first accumulated value is f(n), and the last is p.

Anchor connection may reuse one operation in both positions. Repetition filtering checks only numeric value slots, so the same addition can define the interval and accumulate a sum. Ground arithmetic in the incubator continues to permit repeated numeric values; equality with identical operands is excluded.

The proof pages show ∑ for addition and ∏ for multiplication, with bounds and the folded function. Other operations or traversals keep explicit Fold notation. Ordinary Gauss conjecture generation continues to select summation. Fold does not introduce an empty-interval identity.

Compile direct supporting rules

For a conjunction premise not (A and B), preparation keeps one complemented part and every other part as a guard. If the owning implication is not (A and B) implies H, the compiler prepares not A and B implies H and A and not B implies H.

The original implication remains available. The intermediate guarded rules are retained only as proof derivations and are not installed. Owners with additional premises keep their guarded helpers under the existing composition boundary. No recursive support or composition closure is generated.

Direct support for concrete conjunction alternatives of admitted ORs retains its local fixed-argument path.

Prepared contrapositives

One explicit exception preserves the existing search boundary: a negated existence may refute a candidate's membership in its domain, but contraposition does not turn domain membership into negative body facts for every candidate.

A second exception concerns definitions whose whole body is one implication. When the conclusion does not mention every variable the premise binds, as in the prime-sequence property (if P(i)=x then x is prime, where the index i does not reach the conclusion), the reversed rule would leave that variable unbound. Such a definition keeps its forward rule and gets no contrapositive; rules compiled from theorems are not affected.

Forward definitions keep their separate conclusions. During compilation, implications from the same definition family with the same complete premise can also supply a grouped conclusion. Every combination covering all bound variables is prepared, including larger covering combinations.

At disintegration, the prover substitutes actual arguments into prepared templates in the source scope. Each result has its own compact statement and ordinary rule expansion, like an implication attached to an existence. This preserves its normal ownership through mail, equality rewriting and removal; the fixed domain and range remain parameters. Grouping cites every contributing implication; contraposition cites the exact grouped or original implication. The verifier checks the substitutions and scopes, and Lean replays the derivations. Facts from separate cases cannot be combined.

What an existence already says about its witnesses

Some definitions contain rules about their own witnesses. "D is the set of divisors of n from 2 to n" contains the rule "every member of D is at least 2, at most n and divides n"; "p is the least element of D" contains "p is in D". Together they say that the least divisor p is at least 2, at most n and divides n, before any witness exists. For every existence the compiler fires each rule inside it once on the facts inside it, with the bound variables as placeholders, and keeps the results as the existence's disintegration package. Each result is attached to the witness it is about. Results are never fired at again.

The package is derived from the definitions. It is computed at the same compilation steps as the prepared contrapositives, before any proof work, and is not stored in the binary. The prover uses it when it expands the existence (chapter 4).

A value belongs to a sequence

inSequence[N,p,P] means that some natural index i satisfies P(i)=p. The index belongs to the definition, so a theorem about the member value need not expose it as another parameter. Membership alone does not claim that the relation is a sequence: the separate sequence premise supplies its exact domain, totality and natural-number values.

For F8, a sequence on [0,n], its Fold product q and a member p imply that p divides q. The membership definition introduces no new prover rule.
