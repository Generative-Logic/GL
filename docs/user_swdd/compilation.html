8 · Compilation & names

The prover hashes expressions. For that to be sound, two syntactically-different writings of the same idea must hash identically. This chapter is everything that makes that true: the structural-operator compile, the five name families, the counters that keep names unique, the encoder that packs a string into a 16-bit integer key, and the static memory pool the hot path lives in.

Why this chapter is separate. Compilation appears as a single subsection of §3.5 in the substrate chapter, but most of GL's soundness arguments — and most of the “quiet” bugs that have ever crossed the boundary between cycles — live here. The substrate section is the survey; this is the reference.

8.1  Two canonical forms — why compile at all

GL keeps every expression in two canonical forms simultaneously: a human form (MPL string) and a machine form (a packed integer key). The string is canonical so a maintainer can grep a proof graph; the integer is canonical so the hash engine can decide “does any known rule fire on this fact” in O(1) instead of O(|rules|). The compiler's whole job is to keep those two layers in lock-step — so the same idea always picks up the same string and the same integer key.

“Aligned” means three concrete things, all of which the rest of this chapter delivers:

  • Structural normalisation. !(&X) and the pre-compiled or<N>[X] mean the same thing — but only the second can be hashed soundly. Precompilation (§8.2) rewrites the first into the second.
  • Name stability. If two distinct runs allocate existence3 to two different logical shapes, the rest of the pipeline (chapter walker, verifier) sees a phantom theorem. Counters + the shared registry (§8.4) keep names stable across batches.
  • Cheap equality. The hash engine asks “same expression?” millions of times per second; a strcmp on a tree-shaped string would dominate. The encoded form (§8.6) makes that an integer-array compare.

8.2  Precompilation — I-1

precompileStructuralOperators is the first thing every theorem-load path runs (I-1). It walks the expression tree once, in place, and rewrites the negated structural forms into their compiled atomic names. The positive structural forms are left alone — they are still legitimate MPL bodies and remain meaningful as they stand.

Input shapeOutput shapeWhy compiled
!(&X₁X₂…X_K)or<N>[args]De Morgan turns !(&) into a disjunction; OR is the load-bearing branching form (Chapter 4) and needs a single canonical name to dispatch against.
!(>[bound](body))existence<N>[args]De Morgan turns a negated universal into an existential. Existentials must hash by their shape, not by the names of their witnesses.
(=[a,b]) with a==b(trivial — pruned in head only, I-8)Trivial reflexive equalities clutter the index without contributing.
(>[](…)…) top-level(unchanged — never compiled to implication<N> on load)A top-level implication is the theorem itself; compaction (§3.5.3) runs after proof, never before.
I-1, expanded. The three places this fires are: (1) at the top of addTheoremToMemory on every external/conjecture load; (2) on the sender side as a logic block prepares its broadcast — every body placed into mailOut.statements is precompiled before it is mailed, never on the receiver's addStatement; (3) inside the compressor and CE-filter ingestion. A future load path that bypasses addTheoremToMemory must add the call itself — there is no central guard. The assert that catches the omission lives deep inside disintegration; by then the originating site is several stack frames removed.

8.2.1  The compiled-expressions registry

Every successful compile inserts (or finds) a row in compiledExpressions, the analyzer-level table mapping a compact name (or7, existence2, …) to the structural template it stands for: head shape, arity, the bound-variable signature, the original MPL body, a category label (or / existence / and / implication). Every later mechanism that needs to know “what is or7, really?” reads it from this registry — never from the string.

Compaction (§3.5.3) of proved implications, run after the worker join, deposits its compact implication<N>[…] atoms into the same table. The registry is therefore the single source of truth for every synthetic operator the prover ever invented during a run.

8.3  The five name families

Variables and witnesses are not strings drawn from an open vocabulary — every name belongs to one of five families, and the family tells every downstream machine how to treat it. The prefix is the family.

u_<k>
Universal-template variable. Appears in compiled definitions and admission-map templates. Behaves like a free variable: it is not bound by any enclosing (>[…]), and it pattern-matches anything when a rule fires. Used as the canonical placeholder in admissionMap / admissionMapIntegration keys (§4.2.3).
v<k> (no underscore)
Theorem-level bound variable. A renaming pass at theorem ingest seeds v0, v1, v2, … in a deterministic left-to-right scan, replacing whatever the conjecturer/user wrote. This is the form that appears in files/theorems/theorems.txt and in chapter rows. The deterministic naming is why two semantically-identical theorems generated by different paths still compare equal as strings.
it_<k>_lev_<L>_<S>
Pass B iteration variable, algebra side. Minted by disintegrateExpr2 to stand for an as-yet-unknown value when an implication's premise contains a structural hole. Subject to the algebra-side admission gate (isAdmitted against admissionMap, fallback isAllowedAsOperatorInput, §4.2.1).
int_lev_<N>_<M>
Pass B iteration variable, integration side. Same role as it_, but consumed by the integration path; admission is by isAdmittedIntegration against admissionMapIntegration, with the bare admissionSetIntegration as a fallback.
repl_lev_<N>_<M>
Substitution placeholder. Used during anchor handling and substitution chains to mark “the M-th replacement at iteration level N.” These names are deliberately not stripped on the integration probe (the removeUPrefixFromArguments helper takes off u_ but keeps repl_), so a substitution chain crosses the template/concrete boundary intact.

A sixth marker, the _copy suffix, is not a family of its own — it is a disambiguator that can attach to a name in any family. When a hypothesis is opened or an OR branch is seeded, the new scope sometimes needs a fresh copy of a variable that already exists in the parent; _copy keeps that copy syntactically distinct from the original. Two copies (e.g. v1_copy_copy) are possible and harmless.

Reading rule. When you (future agent) see a name in a dump, the prefix already tells you what the prover thinks it is — you don't need to track back to where it was minted. it_5_lev_1_2 is an algebra Pass B witness; repl_lev_2_0 is a substitution chain at depth 2, slot 0; v3 is the third bound variable in this theorem's left-to-right scan, and so on. The five-family discipline is the single biggest cognitive win in the codebase.

8.4  Counters & the singleton registry — I-23

GL is run-deterministic: the same configuration plus the same inputs always produces the same proof artefacts. Names that look spontaneous — or7, existence2, implication1359 — are the load-bearing test of that promise. They are not random; they are minted by five monotonic counters, seeded once at the start of every run and kept stable across batches by a single on-disk file.

CounterMintsLifetime
implCounterimplication<N> — compact-form proved implications (§3.5.3)monotonic across batches; persists via the shared registry
existenceCounterexistence<N> — De-Morgan'd negated universalsmonotonic across batches; persists via the shared registry
andCounterand<N> — explicit conjunction operators created by the conjecturermonotonic across batches; persists via the shared registry
orCounteror<N> — De-Morgan'd negated conjunctions (the branching workhorses)monotonic across batches; persists via the shared registry
variableCounterv<k> — theorem bound variables, plus internal scope mintingresets at the start of every batch; the only counter that does

8.4.1  Why variableCounter is the odd one out

v<k> names are local to a theorem — there is no semantic reason for v1 in theorem A to mean the same thing as v1 in theorem B. Resetting per batch keeps the names compact; nothing depends on global uniqueness. The other four counters mint names that do need global uniqueness (a chapter referring to or7 means exactly the or7 registered in compiledExpressions[7]), so they monotonically grow.

8.4.2  The race that implCounter nearly lost

Inline calls to compileImplicationToCompact during proof — one of the eight broadcast sites — used to mutate implCounter from worker threads. Two runs on the same input minted implication1359 and implication1361 respectively. The fix (D-76, see §5.4) defers every compaction to a sorted single-threaded pass after the worker join. The race illustrates the rule the rest of this chapter rests on: names are part of the proof; they must be deterministic; therefore minting them is a serialised post-join activity, never an inline worker activity.

8.5  NameMap, encodePush, scope comparison — I-2 · I-3

The four counters in §8.4 mint operator names. NameMap mints scope names — the IDs that show up in every fact's validityName. The two systems are independent on purpose: a name like or7 is global and grows across batches; a scope ID like 17 (decoding to main_boundary_hypo_v0) is per-prover and recycled on demand.

8.5.1  The one and only mint path

NameMap::encodePush(parentId, payload) is the single function that creates a non-"main" scope. It does three things in one atomic step: returns a fresh int16_t; interns the canonical string parent + "_boundary_" + payload into the cold name table; records its parent ID and own payload sub-id in validityNodes (the scope forest) so comparable and deeperOf can answer ancestor queries by walking the parent chain. The forest (validityNodes) is paged on the block's arena and deloads with it; an ID equals its cold-table ID directly ("main" is lazily interned as ID 1 on first use — no offset).

  • I-2. No non-root scope may be created by concatenating strings. Raw parent + "_boundary_" + payload outside encodePush yields the right string but no validityNodes entry, so comparable sees the new scope as unrelated to its parent — and the mail router silently drops messages for it.

8.5.2  The reference hazard — I-3

NameMap::decode(id) now returns an owned string (the bytes live on cold pages), so it is always safe. The hazard survives only for the zero-copy views: decodeView(id) hands back a span over the cold bytes, and an element read of the paged scope metadata aliases page memory. A nested mint (or a deload) can grow or relocate a page and dangle such a view — the bug appears as garbled scope names in dumps, or a string compare that used to match failing two cycles later.

Pattern. If you (future agent) hold a decodeView span (or a paged-metadata element) and then mint another scope (or anything that might transitively mint), copy it out first — or use the owning decode. The old stackOf reference into the metadata is retired; callers use the element accessors, so no long-lived reference into paged storage escapes.

8.5.3  The scope forest and the ancestor query

The scopes form a forest: every non-root ID descends from one parent, rooted at "main". Each scope stores just its parent ID (one ValidityNode in validityNodes); the full ancestor chain is walked on demand. To answer comparable(a, b) (“is one an ancestor of the other?”) the runtime walks b's parent chain looking for a, and vice versa; deeperOf(a, b) is the same test with a different return shape. The checks are O(scope depth), which in practice never exceeds the depth of nested hypotheses inside one theorem — a small constant. There is no separate pairMap cache: it was dropped because the per-scope ancestor list already holds everything comparable needs.

8.5.4  Why the canonical string carries the chain

The runtime uses the numeric ID for every fast operation. But the canonical string — main_boundary_hypo_v0_boundary_int_lev2_boundary_orint_X — is what gets written into chapter rows and into theorems.txt. The string carries the whole ancestor chain so the exporter and the verifier can recover the scope structure without shipping the validityNodes runtime forest. Two-track redundancy: fast at runtime, self-describing on disk.

8.6  EncodedExpression → IntNormalizedKey

A compiled string is canonical for humans. EncodedExpression is the in-memory wrapper that pairs it with everything needed for the hash engine: the head name, the argument list, top-level negation, iteration/level metadata, the validityName. IntNormalizedKey is the packed integer projection of that wrapper — the actual key into encodedMap.

WrapperWhat it adds
EncodedExpressionThe full pair: original MPL string + the parsed head/args + top-level negation flag + iteration level + the validityName. Used by emit paths that need the string and the structure.
ExpressionWithValidityA lighter pair — just (expression, validityName). The currency of newStatements, of mail, and of the chapter walker.
IntNormalizedKeyA pointer+length view — numberExpressions, length, and a non-owning const int16_t* data into KeyArena — over the packed run [ headId, arg0Id, arg1Id, … ]. Cheap to hash, cheap to compare. The hot-path key.
NameMap-IdThe int16_t a string lives at in the active name registry. Up to MAX_NAME_IDS (32000, near the int16_t ceiling 32767) names per registry — large enough for every spontaneous and bound name in a run.

8.6.1  Why hashing is sound on the integer projection

Two expressions that should fire the same rule must produce the same IntNormalizedKey. That is guaranteed by three properties working together:

  • Structural normalisation. !(&X) never reaches the encoder; it has been rewritten to or<N> by §8.2.
  • Deterministic bound-variable renaming. v0..v<k> are assigned by a fixed left-to-right walk, so two alpha-equivalent theorems pick the same names.
  • Single name registry. Every name passes through NameMap::encode, which returns the same int16_t for the same string — the second character of the proof.

8.6.2  The owner-set existence index

HashMemory is the umbrella that owns the firing index. Alongside encodedMap (the premise-key → fireable-rules map) it carries normalizedEncodedKeys: an existence index keyed on the same IntNormalizedKey, whose value is the set of (implication, scope) owners that installed a marker rule for that key. When a firing rule retires or is shadowed by an equivalence-class rewrite, normalizedEncodedKeys drops that owner; only when the owner-set becomes empty does the encodedMap entry itself shrink. The pattern is refcount-by-owner rather than naked refcount — it lets the runtime answer “does any rule for this shape still exist?” in O(1) without a full sweep.

8.7  The static-memory floor — I-95

The hot path allocates millions of small objects per second — every hash request, every fired emission, every mail message, every cold-map entry. Routing those through the general allocator (malloc / new / std::vector) means contending with mimalloc's caches, walking free-lists, and occasionally hitting the OS allocator at a millisecond cost; worse, it leaves the working set unbounded and the layout non-deterministic — neither acceptable for the silicon target, where the prover must run inside a fixed on-die store. GL's answer is to make all prover memory static: one large reservation, taken once at program start, never grown, never returned to the OS during the run.

That reservation is owned by GlobalMemoryManager — the root of the statification memory hierarchy detailed in Chapter 6. It carves the pool into equal fixed-size blocks and hands them out on demand: a per-logic-block memory manager calls acquireBlock when it needs storage and releaseBlock when its logic block deloads to SSD or is destroyed. Both run under one internal mutex, because logic blocks are processed in parallel; recycled blocks are re-granted before fresh ones, so the carve cursor tracks the high-water mark of simultaneous demand rather than total allocations.

  • I-95. Every prover allocation comes from a pool block, never the general allocator. Pool exhaustion is an assert naming the configured pool size (static_pool_bytes and its siblings), never a fallback heap allocation — a sizing problem must surface at its origin, not be papered over.
  • Deload / reload. When the pool fills, the largest idle logic block is written to SSD and its blocks return to the dispenser; the bytes are re-read on the next access. The round-trip is a pure function of logical content — physical block identity and grant order are never observable (§6.5).
  • Nothing escapes to the heap. Under MPU 0.1 all prover state is static — the cold string tables, the encoded maps, the validity forest, the cross-LB mail log, even the logic-block object shells each draw from a pool. There is no “long-lived containers use ordinary heap” tier; the only heap left is start-up scaffolding outside the proof loop.

8.8  Failure modes

Compilation is the layer where mistakes are hardest to notice — the bug is a hash that silently fails to match. The patterns below have all bitten in practice; treat them as the canonical things to check first.

“This rule never fires.”
Raw !(&…) reached addToHashMemory without being precompiled. The rule got installed under one key, the requesting expression hashes under another. Check: the load path; was precompileStructuralOperators called first?
“Two runs produced different implication<N> numbers.”
A worker thread mutated implCounter. Check: every new compaction site goes through recordPendingCompaction, not inline compile.
“The scope name string is right but comparable returns false.”
The scope was created by string concatenation, bypassing encodePush. Check: every non-main scope is minted via encodePush(parent, payload).
“A scope name in a dump is garbled.”
A reference into NameMap's internal vector survived a nested mint. Check: every decode / idToSub[] result is copied into a local std::string before any further mint.
“Wall-clock has a long tail with stalls.”
A refactor introduced dynamic allocation in the hot loop. Check: no malloc / new / dynamically-grown std::vector<char> on any per-step path.
“A chapter row references an operator the registry doesn't know.”
A spontaneous name was minted but never registered into compiledExpressions; or the registry was reseeded from the wrong shared file. Check: files/GL_binaries/GL_binary_shared.json is the canonical maxima source; counters seed from it.
