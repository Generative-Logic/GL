11 · CE filter & compressor

GL runs the same hash-engine machinery in three modes: main proving, counterexample filtering (before proof), and compression (after proof). This chapter is the two non-proving modes — what they reuse, what they do differently, and the budget realities (CE filtering was historically ~80% of a Gauss run, since collapsed — no longer a bottleneck).

11.1  Same engine, three modes

The hash-engine kernel (performElementaryLogicalStep + generateEncodedRequestsStatic) is a single body of code that runs in three modes determined by parameter flags. All three modes use the same logic- block tree, the same mail boundary, the same admission gate; what differs is what is fed in as fact, what is asked of the engine, and which iteration budget gates progress.

ModeInputsWhat the engine is askedWhen in the pipeline
main provingaxioms (external theorems) + CE-surviving conjectures (as goals)“derive the head of every goal”stage 3 of the pipeline (the bulk of a run)
CE filteringa finite-size model (a fact table over 5–6 elements) + a candidate conjecture“fire on the model; does anything contradict?”stage 2, before main proving
compressionevery proved theorem (as a rule) + one candidate's premises“can the candidate's head be derived from the others?”stage 4, after main proving

11.2  The counterexample filter

The conjecturer generates tens of thousands of candidate conjectures by enumerating expression shapes within the deductive neighbourhood the configuration specifies. Most are wrong. The counterexample filter is a cheap small-model test: instantiate every candidate over a finite fact table covering 5–6 elements, fire the hash engine until it stabilises, and discard any candidate whose negation gets derived. Survivors enter the main prover.

11.2.1  What's different from the main engine

The CE-mode engine is the same code with two flag changes:

  • No mandatory-fact gate. Main-prover request generation requires a known local fact to be one of the rule's matched arguments — otherwise the engine would enumerate the entire Cartesian product. CE mode drops that requirement: the model is small enough that brute enumeration is cheap, and the goal is to surface any contradiction, including ones that don't ride a known fact.
  • Same request generator, empty stump. The one generator generateEncodedRequestsStatic runs here with an obligatory-stump length of 0, so it fires every rule against every fact instead of anchoring each request on a known local one.

Apart from that, the LB tree, mail boundary, scope mechanics, and admission gate behave identically. The interpretation of “success” is inverted: in main mode a derived head is good news; in CE mode a derived contradiction is good news (and the candidate is discarded).

11.2.2  One burst per candidate, a pool over a queue

Each candidate gets exactly one hashburst (numberIterationsConjectureFiltering is 1 in every config): the single burst checks whether the candidate's negation immediately contradicts the facts. A dedicated thread pool drains a global candidate queue — each worker takes the next candidate, checks it on its own throwaway copy of the fact base, and the instant one is refuted its burst stops early and the worker grabs the next. There is no batch barrier, so no core idles waiting on a slow candidate. The historical 80%-of-wall-clock cost (roughly halved by the pool) comes from the sheer candidate count, not any individual candidate's runtime.

11.3  The j-copy trick

The fact table is not a blanket doubling of every fact. The generator always emits the anchor fact in both forms — the i0/i1 constants and their j0/j1 twins — and for the remaining facts re-emits a j-form copy to break repeated i-value arguments, so a rule that needs two textually-distinct tokens can still fire. The point is the textual distinctness, not a uniform ×2. Example for the Peano + facts: 

(in3[i4,i5,i0,+])
(in3[i4,j5,i0,+])

Both denote the same model element (the constant in slot 1 is the same number either way). The textual distinctness is the point: a hash rule that expects two structurally-different arguments would otherwise never fire on two textually-identical names, even though semantically that is exactly the case the rule is built for. The j-copies give the pattern matcher two different strings to bind, so the rule fires.

Asymmetric j-copies would silently break the filter. The generator relies on a strict symmetry: every i-form has a matching j-form. A future fact generator that emitted, say, i0 but not j0 would silently flip some rules from “fires when it should” to “never fires” — a quiet over-acceptance of conjectures. No fail-loud path catches this yet.

11.4  The compressor — independent throwaway trees

After main proving, GL holds N proved theorems. Many are derivable from each other: a commutativity step from a more general lemma, a corollary of an already-stated stronger fact, the reverse direction of an induction-proved fact. The compressor identifies and discards the derivable ones, leaving the smallest non-redundant set it can find. It does so with the same hash engine but in a third mode — one that uses one fresh, independent logic-block tree per candidate.

Why throwaway trees? A shared dependency state across candidates would make the analysis order-sensitive — and the analysis already produces an order-sensitive result by construction (the greedy elimination is a heuristic). Keeping the per-candidate LB tree fresh isolates the order-dependence to one explicit place, the Phase 2 ordering rule.

11.5  Compressor Phase 1 — per-theorem dependency graphs

For each of the N proved theorems, the compressor spawns an independent logic-block tree. Into the tree:

  • Every other proved theorem is installed as an implication rule — disintegrated through the same machinery the main prover uses, but with compressor_mode=true setting Pass B's gate so its disintegration step does not fire.
  • The target theorem's premises are seeded as “fuel”: facts to assume.
  • The target theorem's head is the proof goal.

The kernel then runs a bounded number of hash bursts (default 15) and records which other theorems were cited by which derivation step. The data structure is one CompressorNode per theorem; its graph field maps each derived expression to the theorems that produced it. That graph for the target theorem captures exactly the question Phase 2 needs to answer: “which of the other theorems must remain available for this theorem's head to stay derivable?”

11.5.1  Why the origin-record cap is different

Main-mode tracks max_origin_per_expr=1 — one origin chain per derived expression, the minimal evidence needed for the proof graph. The compressor uses compressor_max_origins_per_expr=30. The reason: the compressor cares about which theorems contributed to a derivation, not just that it derived. A larger cap lets Phase 2 see alternative dependency chains and preferentially eliminate the candidate that has the fewest unique uses across the corpus.

11.6  Compressor Phase 2 — greedy elimination

Phase 2 iterates over candidates in ascending order of usage count (least used first). For each candidate:

  1. Tentatively dead. Add the candidate to the “dead” set. Do not yet rebuild the dependency graph.
  2. Re-test survivors. For every non-dead theorem, ask: is its head still derivable from the remaining alive theorems? Use the cached CompressorNode graphs from Phase 1.
  3. Confirm or restore. If every survivor passes, the candidate stays dead. If any survivor fails, the candidate is restored to alive — it was load-bearing.
The survivor-only criterion is essential. Including dead theorems in the derivability test would let two dead theorems protect each other (each is needed only because the other is dead). The criterion guarantees no mutually-protective pair survives Phase 2 by accident.

11.6.1  What ends up compressed out

PatternTypical example
Symmetric reverse directionsIf (commute_a_b) proves by induction and (commute_b_a) proves too (now a real proof, not a fabricated mirror), one is removable.
Direct corollaries of a stronger factAn associativity over three terms when associativity over n terms exists.
Intermediate stations on a proof chainIf both endpoints of a chain are proved independently, the middle is derivable from them.

11.7  What lands on disk

Three text files carry the compressor's output. Each plays a distinct role for the rest of the pipeline.

FileContentsRead by
files/theorems/theorems.txtRaw MPL form of this batch's pruned essential-survivor theorems — the compressor's kept set, excluding externals and OR-consumed parents (the authoritative regression target — see Chapter 10's note on method-tag drift).The regression baseline; the verifier.
files/theorems/compressed_external_theorems.txtThe compressor-kept subset, in the order Phase 2 produced them. This is the file the next batch loads as “external theorems”.Next batch's main prover at startup.
files/theorems/compressed_out_theorems.txtThe compressor-eliminated subset (the theorem strings only). Each entry is recoverable from the kept set via the verifier — they are not gone, just not first-class.The verifier's theorem goal reached checker, when a kept theorem's chapter cites a compressed-out theorem.

11.8  Failure modes

“CE filter says nothing — every conjecture went through unfiltered.”
The fact-file name lookup failed silently. The path inference takes the anchor name, strips Anchor, lowercases — so AnchorPeano → peano, and the loader opens files/simple_facts/simple_facts_peano_*.txt. A typo in the anchor name yields zero file matches and no warning. Check: the fact files actually opened in the run log.
“Phase 1 of the compressor uses too much memory on Gauss.”
Phase 1 is O(N²) by construction — each of N independent LB trees loads all N theorems as rules. At Peano/Gauss scale this is fine; at FTA scale (target ≈100 K theorems per run) it is not. Check: known open scaling concern; the path forward is either pool sharing or streaming. No fix yet.
“Two runs picked different ‘minimal’ compressed sets.”
Phase 2's greedy elimination depends on a stable tie-breaking order for candidates with equal usage counts. An unstable sort would surface this. Check: the compressor's sort is std::stable_sort — if a refactor replaced it with std::sort, the output becomes flaky.
“Compressor dropped a theorem another chapter needs.”
A surviving chapter cites the dropped theorem. Check: the verifier reads compressed_out_theorems.txt for citation resolution. The theorem isn't gone — it has moved to the recoverable file.
“A CE-mode rule fires on the j-copy but never on the i-copy.”
Almost certainly: the rule was installed with a textually-distinct binding requirement that holds against j-copies but not i-copies. Check: the fact table's i/j symmetry; a missing j-form is the usual culprit.
