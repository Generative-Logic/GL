1.1  What GL is — and the bet it makes

Generative Logic (GL) is a deterministic machine for automated mathematical reasoning. From a few axioms in MPL it enumerates conjectures in their deductive neighbourhood, rejects those refuted by finite-model counterexamples, and attempts to prove the survivors by hash inference over a grid of logic blocks. All human steering is confined to the pre-start phase — choosing the MPL axioms and writing the batch configuration that carves out the region of exploration; once the run starts there are no tactic scripts and no theorem-by-theorem steering. The conjecturer supplies the goals, the prover decides them. The deliverable of a run is a corpus of theorems plus a provenance-complete, machine-checkable proof graph for each, re-checked by an independent external verifier. It is explicitly not a tactic prover in the Lean/Coq/Isabelle sense: the value is the fixed, auditable execution model and the shippable proof corpus. Current canonical results: the Peano batch (commutativity/associativity of + and *, distributivity, ≈58 theorems), the Gauss batch (the division-free summation n·(n+1)=2·Σi), and rung 1 of the Fundamental Theorem of Arithmetic ladder ({0,1} = [0,1] — the set equality of enumerated and interval forms, and the first OR-branching milestone).

The bet, precisely. Inference is a memory-access problem, not a search problem. Every implication is stored as a hash rule keyed by its premise pattern: premise_signature → conclusion_template. Every known fact is stored by its structural signature. A proof step is: form a request from known facts, hash-look it up, and if it hits, bind and fire the conclusion — the local rule lookup is O(1) amortised, with no backtracking on the step itself. Exploration is by breadth: many blocks fire in the same cycle and exchange results through mail at cycle boundaries.

That one bet forces three properties that the rest of this document keeps returning to:

  • Structural canonicality. Two expressions that differ only in bound-variable names must hash identically, or the index would treat them as different rules. Normalisation plus precompileStructuralOperators (compiling !(&…)→or<N>, !(>…)→existence<N>) guarantees it — see §3.5.
  • Explicit scope. A fact proved under a hypothesis carries a validityName; escaping it to the parent is an explicit, audited step, never an implicit flag flip — see §3.4.
  • First-class provenance. Every fire writes an exprOriginMap entry. That map is the proof graph's raw material — and is written, never read by the proving logic (§7.8).

1.2  The pipeline — artefacts and the prover's place

python main.py is the entry point; the actual per-batch driving lives in run_modes.full_run() (Python). A batch is a fixed eight-stage pipeline. Stages 1–5 run inside the C++ binary gl_quick.exe (its in-binary sub-orchestration handled by C++ run_modes::fullRun); stages 6–8 are Python, driven by run_modes.full_run() directly. Definition compilation is folded into the prover's startup, not a separate stage. This document is stage 3, the prover (prover.cpp + memory.hpp), and the machinery it stands on. Each stage's on-disk artefact is named so a claim can be checked at the file level.

Two orchestrators with the same name, different languages: Python run_modes.full_run() drives each batch end-to-end — it invokes gl_quick.exe --conjecture <tag> (stage 1), then gl_quick.exe <tag> (stages 2+3+4+5), then runs the Python stages 6–8 itself. Inside the second invocation, C++ run_modes::fullRun(anchor) is the in-binary sub-orchestrator chaining CE filter → prover → compressor → raw proof-graph emission. run_modes.full_run() also chains batches forward, threading earlier batches' theorems.txt into later ones — directly within a track (as proved theorems), and as external rules when crossing from a main batch into the next incubator. The deductive region of each batch is set by config, not by content edits.

The incubator runs a similar pipeline but with two fewer stages — no CE filter (the incubator's job is to produce the fact tables that feed CE filters, not consume them) and no compressor (its output is intentionally huge — compression would discard finite-model facts that downstream main batches still need). The resulting six-stage shape is below.

1.3  The deductive neighbourhood — what a batch explores

A GL batch does not try to prove a fixed wishlist of theorems. It enumerates the shape of every interesting expression a given configuration allows, discards those refuted by obvious counterexamples, and proves what survives. The configuration is the lever: change Config<Tag>.json and the batch turns its attention to a different deductive corner of the same underlying mathematics. The mathematics itself never changes — the axioms (MPL definitions + anchor body) are constant. Only the conjecture pool shifts.

Two controls shape the slice:

  • Anchor commitment. Picks the axiomatic context (§9.2). Peano explores commutativity / associativity; Gauss adds one further constant (i2) and the identity operator (id); Incubator widens the slot count for ground-fact harvest.
  • Shape filters. Prohibition tables in the config (prohibited_combinations, prohibited_heads) mark which expression shapes are uninteresting and get skipped. Most of a run's conjecture-time discipline is encoded here.
Why batches exist. A single batch could in principle pile every configuration into one run, but each config is sized so its conjecture pool fits a reasonable wall-clock budget. Splitting into Peano / Gauss / FTA rungs is the way GL keeps the deductive scan tractable while building mathematics layer by layer.

1.4  Artefacts on disk — main artefacts

Every stage writes a single primary artefact (sometimes a small set). The artefacts are the contract between stages — replacing a stage with a hand-edited file produces a run identical to one where the stage ran. 1.5  How to read this document

This is the GL prover reference: real data structures, real decision logic, the load-bearing rules and why they exist — presented diagram-first for a reader who wants to understand how the engine actually works rather than just what it computes. It is not a brochure and not a tutorial; it is a working architectural reference.

Conventions used throughout:

  • Code font names a real structure, field, or function you can grep for (HashMemory, sameIterationInternalMail, disintegrateExpr2). No file:line citations — symbols are stable, line numbers are not.
  • Invariant lists (like this one) state a load-bearing rule in one sentence; the matching chapter explains why and what breaks if it's violated.
  • Worked micro-examples trace one real mechanism end-to-end with concrete values (e.g. the Gauss revival in §4.2.5).
  • Diagrams lead; prose is the precise caption, not the bulk.

1.6  Quick glossary

The most-used terms in this document, defined once. Every entry is cross-linked to the chapter where it lives in detail.

LB (logic block)
The unit of execution. One Memory object; owns its own hash rules, statements, mail, scope stack, equivalence classes, origin map. Cross- LB observations only happen via mail at cycle boundaries. — §3.1
Hash burst
One pass of performElementaryLogicalStep across the LB tree — roughly “one cycle.” During a burst, every active LB has the chance to fire every rule it knows once. — §3.2.3
validityName / scope
The provenance marker every fact carries: where (under which hypothesis, in which OR branch, at main) the fact holds. — §3.4
Disintegration
Expanding a compound expression into pieces small enough for hash rules to fire on them. Pass A is structural; Pass B mints fresh variables under an admission gate. — §4.1
Admission
The gate that decides whether a freshly-minted Pass-B variable may be emitted. Two paths: map-based (authoritative) or single-input-operator (narrow standalone). — §4.2.1
Equivalence class
The bookkeeping for a set of expressions known to be equal at a given scope. Cross-scope application is one-directional (ancestor → descendant). — §4.2.4
Mail
The cycle-boundary message bus between LBs. Main-only by contract; the mechanism that lets the parallel phase be lock-free. — §3.3
Anchor
A single atomic expression at the outer position of every theorem, naming the axiomatic context. Four anchors are live; a fifth (AnchorFTA) is per FTA rung. — Chapter 9
exprOriginMap
The proof-graph raw material: per-emission record of what justified the step. Written everywhere, read only by the chapter walker and the verifier; never by the proving logic. — Chapter 7
IntNormalizedKey
The packed-integer hash key form of every expression. The hot-path canonicality is on this projection. — §8.6
Status (deposit mode)
An integer threaded through every deposit site that says “has this expression already been disintegrated?” Wrong status = silent failure. — §2.3
Hashburst dump
The diagnostic per-cycle trace of one targeted LB's full state. The prover's highest-value debug artefact; format is stable across runs so cycle-vs-cycle diffs read cleanly. — §2.6
OR branch / convergence
A case-analysis sub-scope opened per disjunct of an or<N>. Branches recombine by _orint_ (one branch proves) or _ordis_ (all converge). — §4.4
Contradiction discharge
The mechanism that turns a self-refuting branch into a positive parent- scope fact (¬(branch assumption)). — §10.6
Induction triad
The three sub-blocks a scheduled induction spawns: base, step, typing. All three must land for the theorem to be promoted with method=induction. — §4.5

1.7  What is & isn't in this doc

This reference is opinionated about scope: it covers the prover and prover-adjacent mechanisms only — the engine that turns axioms into proved theorems, plus the auxiliary modes that bracket it (counterexample filter, compressor). The other pipeline stages have their own existence in code but are out of scope here.

In scope here

  • Architectural concepts and how they fit together.
  • Real field and function names you can grep for in the source.
  • The load-bearing invariants and what breaks if they're violated.
  • Worked traces of a few real mechanisms end-to-end.
  • Failure modes that have actually been seen.
  • Diagrams as the primary surface; prose as the precise caption.

Out of scope

  • MPL grammar and language tutorial.
  • Configuration schema and per-field reference.
  • Conjecturer enumeration internals.
  • Process-proof-graph renaming and HTML export rendering.
  • Verifier algorithm internals beyond the trust-boundary discussion in Chapter 7.
  • Incubator details beyond its interaction with the prover.
  • file:line citations — symbols are stable, line numbers drift.
If you want the prover, this is the document. The exclusions above are boundaries, not deficiencies; each lives in code under a stable symbol name that you can read on its own. This reference exists to make the prover's moving parts legible.
