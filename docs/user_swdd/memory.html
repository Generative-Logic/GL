6 · Static memory (statification)

The host reservation starts on a 4,096-byte boundary so complete transfer blocks can be registered with CUDA. This physical alignment does not change pool capacity or the virtual offsets stored by the prover.

The reservation is address space only. A block is committed before use. At the end of each prover iteration, each of the four original pools keeps the first 64 MiB of its returned-block queue for reuse and decommits excess backing. A later grant recommits the same address. Live blocks, recycle order, capacity and the exhaustion assert are unchanged. The independent GPU-host pool retains its committed backing for reuse. Current commitment is reported separately from lifetime peaks. Releasing unused backing also lets later peak snapshots identify active allocations more clearly; recommitting released pages adds operating-system work when they are reused.

How the prover's per-LB containers move off the heap and onto a fixed memory hierarchy: one reservation at program start, carved into blocks, carved into fixed-size pages that per-LB containers pack their elements into, addressed by virtual page ids — and streamed to SSD between iterations in a canonical, byte-comparable format.

6.1  Why static — the MPU path and the heap ceiling

The silicon correspondence in §5.5 is a real roadmap, not decoration — and a core's on-die SRAM does not malloc. The MPU (Mathematical Processing Unit) build requires all prover memory static: every byte the prover touches must live inside a fixed reservation whose size is known before the run starts. Statification is the software half of that requirement, written so the data layout the silicon needs is already the data layout the prover runs on.

There is also an immediate, non-aspirational reason: the heap ceiling. Per-LB containers grow with the deductive neighbourhood, and at current consumption the next milestones are infeasible on realistic hardware — the run drowns in allocation long before it drowns in inference. A fixed pool turns "the run slowly eats the machine" into a single, visible sizing decision.

The migration was tier by tier: the machinery — global pool, per-LB bump arenas, arena containers, the deload format — is built once, and each tier moved one container family onto it. Tier 1 migrated the statement registry, Memory::intEncodedStatements (§3.1.2); the remaining per-LB families — the string interners (§6.7), application classes and the separate complete canonical-class view with its representative/change records and pooled dependency/comparison indexes, the hash inference engine, the goal registry, the cross-block mail log, and the logic-block objects themselves — followed across the campaign, which is now complete: all per-LB working memory is static (§6.6).

Complete-class comparison indexes follow their owning memory image. A canonical reload rebuilds them from its restored records. A raw snapshot preserves their pages and includes cache-only changes before that snapshot can be reused.

Pending comparisons use pooled postings keyed by effective scope. Repeated invalidations share one live entry; each lookup drains only its scope's entries. These queues are derived data: canonical release clears them, while raw images retain their pages and include queue-only changes.

Each canonical dependency stores its logical name/scope and record pair once, with one insertion revision and two ordered traversal links. The shared pair, lookup value and node use 44 payload bytes per live dependency, before hash slots and head maps. The revision avoids revisiting old records for a new posting. Raw images preserve this derived store; canonical reload rebuilds it.

  • One main reservation, plus three small stand-alone pools. Almost all statified storage comes from a single allocation made at program start — never freed during the run, never grown. The software model of the MPU's fixed SRAM. Three further, smaller reservations sit beside it, each with its own exhaustion assert and never depleting the main pool. The persistent pool backs the never-deloaded goal registry — keeping it always resident, so the deactivation logic can read it even when an LB's main storage has been written out to disk (removing a source of run-to-run nondeterminism). The mail pool backs the cross-block mail log, global blob ids, and transient mailIn staging. Outgoing mailOut staging and its per-block interner live in the main deloadable pool instead. The mail pool is never written to disk and plays no part in any deload decision. If every block was active when the grid completed, delivered blob/reference pages and the matching global mail-id table are reset after each cycle; if any block started dormant, full history and that id table stay available for its later catch-up. Routing, cumulative counts, and cursors remain resident in both modes, and the mail content never competes with the main pool. The LB-body pool holds the logic-block objects themselves — every block used to be a separate heap allocation; now each is placement-constructed into a fixed-size slot carved from this pool and never moved, so the many pointers between blocks stay valid for the object's whole life. It too is never written to disk, and its blocks return to the pool when a run's analyzer is torn down, so several analyzers in one process reuse it. The independent GPU-host allocator adds a fourth extra reservation, described below, for GPU-owned host storage.
  • No observable dependence on physical placement. Which physical block a container's data lands in is invisible to every proof decision and every exported artefact — the virtual-offset arena (§6.3) is what makes that claim checkable.
  • Exhaustion is an assert, not a fallback. If the pool runs out, the run stops at the allocation site with a message naming the config knob. There is no emergency heap allocation — a silent fallback would un-prove the static claim.

Shared expression records

Cleanup filters the ordered references in place. Surviving records stay where they are, without copying or another lookup in the sharing table. Only removed references release ownership; the local membership index is rebuilt and incremental processing positions are adjusted to the surviving order.

Each logic block stores one immutable copy of each identical expression record. The main, local, newly-local and external lists keep ordered four-byte references. Scope and all metadata remain part of the record; deleting one list entry does not remove another list's fact. Free record slots are reused. Canonical files still contain complete records in each list's order; raw eviction preserves the shared store and references together.

6.2  The memory hierarchy — pool → blocks → pages

Three levels — pool carved into blocks, blocks carved into fixed-size pages — and then the per-LB containers pack their elements contiguously into pages drawn from the LB's arena. The sizes are fixed compile-time constants in parameters.hpp (identical for every batch, never read from a config); isValidStaticMemoryConfig asserts that the pool is a whole multiple of the block and the block a power of two, and isValidStaticPageConfig that the block is a whole multiple of a power-of-two page (so an index resolves by one shift and one mask); initStaticMemory then makes the one reservation.

LevelSizing constant (parameters.hpp)OwnerUnit handed down
Poolstatic_pool_bytes (6 GiB)GlobalMemoryManager — one per processblock
Blockstatic_block_bytes (256 KiB, a power of two)LbArena — one per LBpage
Pagestatic_page_bytes (2 KiB, a power of two)the paged containers, via the arena's page tierelements (packed contiguously, addressed by page id)

The global manager re-grants recycled blocks before carving fresh ones, so the carve cursor doubles as a high-water mark of simultaneous demand; blocksInUse / peakBlocksInUse expose the sizing telemetry that turns the pool size from guesswork into a measured number.

Exhaustion policy. When acquireBlock finds the pool empty, the run asserts, naming static_pool_bytes — the operator's fix is one parameters.hpp edit and a rebuild. A fallback heap allocation here would be worse than the crash: it would silently convert "all prover memory is static" from an invariant into a hope, and the MPU sizing data would be fiction.

Derived hash bucket occupancy

The cold hash-map family grows its derived lookup table before three quarters of the slots are occupied, retaining a minimum of 64 slots and power-of-two capacities. Fewer bucket pages trade against longer collision chains. Stable records, exact key equality and canonical output remain unchanged. The separate fused-edge lookup keeps its own half-full policy. Pool reservations remain unchanged.

One stored dependency edge

Each posting is stored once in packed endpoint and link columns. Lookup buckets reference stable edge slots directly. Removing an edge repairs its lookup chain and reuses its slot without moving any surviving list entry. Scalar postings use 24 payload bytes per retained slot and domain-separated postings 32, before page and directory overhead. Both traversal order and insertion revisions remain exact. Pool reservations and canonical proof storage remain unchanged.

Canonical dependencies, the name-to-record links that select records after an equality change, use a smaller form. A record table and a name table keep each exact key once, with the newest dependency of that key; the record table also says whether the record is live. A dependency slot stores 24 bytes: both endpoints as small identifiers in those tables, its insertion revision, and the links of the name's list and the record's list. There are no lookup buckets: a record depends on a few names, so an exact pair is found by walking the record's own list. Closing a scope removes its keys from both tables and renumbers the survivors by walking their lists; slots, links and revisions stay in place, so selection order is unchanged.

Together these memory changes reduce identified GL-owned RAM at the matched FTA comparison state from 2301.24 MiB to 2096.92 MiB: 204.32 MiB (8.88 percent) saved. This includes directly owned retained capacity and is not a fresh peak measurement. In the measured memory candidate, all theorem and proof artifacts matched the reference byte for byte.

Prefix-packed origin strings

Origin-string identifiers and hashes stay stable while leading bytes are shared within sorted groups of sixteen keys. Each key adds an eight-byte predecessor/prefix record. Decoding writes into caller-owned temporary storage; no cache eviction can invalidate another live result. Comparisons walk suffix segments directly. Packing uses temporary full-key storage at a quiescent worker boundary and keeps the existing format when complete page costs would grow. Its containers use general worker scratch, whose existing release returns backing at worker exit. Canonical output remains full original strings. Only origin strings use this format.

Shared native keys and record payloads

Each logic block shares identical native hash-key bytes, normalized-key values, and page-contained encoded rule and owner records. Larger records retain private paged storage. Each table keeps its own identifiers, membership, ordered runs and owner lists; replacing a record changes only that table's reference. Sharing storage therefore leaves scope and inference unchanged.

After a worker finishes using borrowed views, it removes unreferenced shared payload and compacts the surviving bytes. Emptying the final table releases the shared store immediately. Canonical disk streams keep their existing format and reconstruct sharing when loaded. Raw eviction preserves the shared store and its references together. Memory reports count resident payload once; serialized size may include repeated copies.

On the measured full F3 workload (28 September 2026), two sequential runs kept all theorem and proof files identical while peak native RAM fell from 8,570–8,577 to 7,051–7,055 MiB, about 17.7 percent below the projection-only result. At that stage, the largest main-pool peak was about 4,213 MiB of 6,144 MiB. The memory object grew by 5,120 bytes to 255,336 bytes and still fits one 256 KiB slot. FTA itself showed no material RAM saving.

Key bytes shared across logic blocks

Different logic blocks also hold the same bytes: every block installs the same mailed rules and mints the same names in the same order. At the IncubatorPeano1 peak, 698 MiB of string and key pages held only 7.5 MiB of distinct content. One dictionary per batch run, kept in the never-deloaded LB-body pool, now holds such bytes once; on the full pipeline this lowers the peak from 4,066 to 3,715 MiB (−8.7 %), every batch lower, with identical output. A block's string tables and its native-key pool keep their own identifiers, tables and order; a row only points at the dictionary entry instead of holding its own copy.

The dictionary changes only at the end-of-iteration barrier, while no worker and no paging thread runs: payloads that at least two rows reported at the end of phase 3 become entries. Blocks then replace their copies at their next maintenance point and give the freed pages back; a new key finds an existing entry at once. Entries stay until the run ends, so evicted raw images keep valid pointers. Disk images still hold the full bytes, so proof output and canonical files are unchanged.

6.3  The page tier — virtual page ids, the determinism device

Addressing large containers with small pages

Container directories grow only when needed: a single page has no directory, then one and two directory levels serve larger containers. Above 262,144 data pages (512 MiB with 2 KiB pages), a third level addresses more pages without enlarging the pages or the main pool. Promotion retains the old root and payload; shrinking returns empty branches. The first promotion adds 6 KiB of directory storage. Signed element and slot counts remain separately bounded, and serialized logical contents are unchanged.

Small containers share pages. On a logic block's own arena, a container whose content fits half a page does not take a whole page: it takes one slot of 64, 128, 256, 512 or 1,024 bytes carved from a page that holds other slots of the same size. It moves to the next slot size as it grows and to a whole page once it outgrows the largest slot; a small hash-bucket table takes a slot the same way. A slot is addressed as its page's id plus a byte offset, so moving and reloading pages works unchanged. Free slots of each size are kept in a list threaded through the slots themselves; compaction gives a page back once none of its slots is in use, and an eviction to a raw image keeps the lists, because the image restores every page at its id.

Containers never store physical pointers. They store virtual page ids (vids) and a within-page index. The arena carves its blocks into fixed-size pages; allocPage() returns a vid naming a page, and pageAt(vid) translates it to a physical page on each use. A container splits an element index into page = i >> shift, within = i & mask — one shift and one mask, because the page size is a power of two — then reads the slot inside the resolved page. The only free is freePage (LIFO: a freed page returns to the free-list, and freeing the tail rolls the page cursor back). Interior gaps left by other deletes are holes that the in-place page compaction (§6.5) reclaims by packing the live pages onto the low blocks — the one operation that ever rebinds a vid to a different page. Workers check for this reclamation after phase 1 and after phase-3 cleanup, before releasing their exclusive ownership. The check keeps the existing fragmentation threshold; returning a pool block first makes it reusable. The end-of-iteration trim can then return excess physical backing to the operating system while keeping the virtual reservation.

This indirection is the determinism device of the design. Block grant order under the global mutex is a race between worker threads, and a reloaded LB (§6.5) may land in entirely different physical blocks than before — both are fine, because no observable behavior may depend on physical block identity or grant order. Everything the prover, the exporter, and the verifier can see is phrased in virtual page ids and logical element order.

  • Resolve at every access. pageAt(vid) translates a vid → physical page on each use and asserts residency. A resolved pointer must not be stored across any call that could deload or compact the LB.
  • No per-LB lock. Per-LB state is mutated single-threaded by the phase model: the parallel phase 2 only reads LB statement containers; all mutation sites sit in phases 1 and 3. The only cross-thread touch is the global manager's mutex inside acquireBlock.
  • A two-level page directory, shift-and-mask. A directory of page ids indexes the data pages, so operator[](i) splits i into a page index and a within-page slot — all shift-and-mask, no division on the hot path — then one pageAt. The directory is adaptive: inline, then a single directory page, then — for a large container — two levels, so the index itself spans several pages (a root page of directory-page ids, each holding many data-page ids). Overflowing even two levels is a loud assert naming the next level, never a silent out-of-bounds write — the same loud-failure contract as pool exhaustion, and the fix for a corruption that hid for days. The directory lives in the arena's own pages (not the heap) and is rebuilt on reload, so its depth never reaches the deload image — the on-disk bytes are identical whatever the shape.
  • Deliberately narrow API. PagedVector<T> offers a std::vector subset — push_back, size, operator[], index-form erase, clear, release, copy-assign — and pointedly no data(), no iterators, no swap: a single contiguous data() is impossible across pages, and its absence makes the compiler enumerate every consumer still assuming flat storage. Element references are stable while the LB is resident (an element never moves under a growing container); they die at deload, clear, release, or the page compaction.

Large variable-record runs still move each tail once. The cold blob maps keep a dense two-level index over one dense byte pool. A replacement that fits one scratch block is written from a contiguous buffer; a larger replacement is streamed from replayable record spans directly into the same paged gap. The byte-pool tail and its blob-index tail are each shifted once, rather than once per record. Both doors produce the same dense index and byte stream, so deload images and proof artifacts do not depend on which write door was used.

Variable-length byte keys keep a short hash tag in static memory. Each key's page-backed location record is 8 bytes: its byte offset, its length and a 18-bit tag of its 64-bit digest. A lookup hashes the probe once and rejects candidates with a different tag before resolving the byte pool; a matching tag still requires the full length and byte comparison. Rebuilding the lookup index recomputes each stored key's digest from its bytes. This is not a heap-side cache and does not add an on-disk field: canonical deload still writes only lengths and logical bytes, and reload reconstructs each tag from those bytes.

6.4  LbMemory — the growable aggregate

The aggregate includes one OR source store. Original source scopes, ordered leaves and levels, and pending work share the block's deloadable arena. A clone receives an independent copy; closing a scope removes its source records and pending work while preserving ancestor sources.

The OR matching foundation keeps one entry per canonical form and effective scope, using the same equality machinery as negations and proof goals. Every stored spelling of a fact with that form is a carrier of the entry and shares its one lookup key, the way rejected sources keep both their key and their parked source in canonical form. An equality change reaches only entries whose canonical form, or one of whose spellings, names a changed argument token. A child equality creates a child view; the parent view keeps its original reach. Whether the equalities rewriting a spelling are the block's own is read when a reduction considers that spelling. Selected reductions continue through the ordinary proof-history and internal-mail paths.

These lookup caches belong to the block and count toward its live memory. Raw eviction preserves them. A canonical reload or clone reconstructs them from the retained source data; closing scopes clears derived views once while keeping valid ancestor sources. Discharge releases both source state and lookup caches.

An OR becomes a source only after statement admission has settled its actual arguments, scope and levels. This includes inherited statements. Collecting a possible disintegration product records intent; a rejected product creates no active source. Relevant fact and equality changes queue work for the matcher.

Newly watched signed predicates share one initialization scan of known facts. Later changes use their exact queued keys. Matching combines comparable scopes; sibling scopes remain separate. Retiring a source removes all of its leaf lookups, and fact indexes are released when their last watcher disappears.

The matching index owns complete updates: a moved canonical form moves every user of its entry to the entry of the new form, lookup links included, and removing the final user releases its token links. Facts, OR leaves and pending source evaluations have explicit, distinct roles.

All leaves of one OR share its canonicalized parent expression. Flattening that parent gives the lookup keys, including rewritten equality disjuncts. This takes one canonicalization per OR and scope. A known OR fact with the same canonical form shares that entry while keeping its own whole-expression lookup key.

Each LB owns one LbMemory: a struct bundling the LB's LbArena (declared first, so the arena-backed members destruct before the arena whose blocks back them) with every statified container, keyed against an append-only ContainerTag registry. The tag is the container's on-disk identity — tags are never renumbered, reordered, or reused. visitContainers (const and mutable overloads) enumerates the members in ascending tag order and is the single source of container enumeration: the deload writer, the reload reader, and every future bulk operation walk the same visitor.

The growth contract is the point of the shape: adding a future container to the static regime is one member + one appended tag + one line in each visitContainers overload. Nothing else moves — the deload file format is self-describing per tag (§6.5), so old machinery never restructures when a new container joins.

Memory holds the aggregate as lbMemory plus a reference alias — intEncodedStatements binds to the member inside the aggregate — so the registry's many access sites keep their body.intEncodedStatements spelling unchanged through the migration. The alias carries no state of its own; its one side effect is making Memory non-whole-assignable by design — teardown swaps individual members, and a statified container's teardown idiom is release().

Why a visitor and not a serializer per container. The deload format's stability across tiers hangs on one discipline: format knowledge lives in one place, and containers only declare themselves. A per-container serializer would drift; a per-container tag plus a shared element-streaming visitor cannot.

6.5  Deload / reload — the canonical SSD round-trip

Nothing is written until the pool forces it, and RAM is treated as a cache of the working set — the logic blocks being processed right now plus the next few about to be processed. The order in which GL processes its logic blocks is fixed, so "the working set" is simply a sliding window over that order.

The steward — a background planner thread plus a small pool of I/O executor threads (one executor per eight workers, between two and eight) — maintains that window in every one of the three kernel phases (they are all equivalent here; no phase pre-loads everything) and across the between-iterations seam: the single-threaded mail-distribution work that runs between one iteration and the next reloads blocks too, so it gets the same treatment — its linear sweep carries its own cursor, the scattered mail-delivery work runs under a window anchored at the start of the next iteration's order (whose head is exactly what will be needed first), and every reload passes through the same one-line handshake, so the paging machinery always sees a consistent picture and keeps evicting while the seam churns. While a phase runs, the planner watches its work cursor and plans two kinds of work onto two fixed-size queues: prefetches of the window ahead of the cursor (reloading any LB that sits on disk) so a worker finds its LB ready, and evictions that keep a small reserve of free blocks by paging out the LBs whose next turn is furthest away. The executors drain the queues and do the actual disk work in parallel — loads first, except when free blocks fall below the emergency floor, where evictions jump the queue (they must never starve behind reloads that have no room to land in). One serial evictor could not match thirty-two workers' memory consumption against the fixed cost of a file write per eviction; the pool is what lets the eviction stream keep pace. Every queued job re-checks its window when it finally runs and simply drops if the world moved on — the planner re-plans continuously, so a dropped job costs nothing. An eviction holds the LB and its memory until its disk image is complete, only then frees the blocks and marks the LB paged out — no one can ever observe a half-written eviction. A worker that reaches an LB still on disk simply loads it itself into the reserve's free room (a one-line handshake so worker, planner, and executors never collide). An LB being processed is never touched, and a worker is never interrupted mid-LB. The kernel decides what to discharge at its single-threaded iteration barrier (deterministic, order-and-numbers based); the steward executes while the next iteration already computes — the discharge dump itself stays on the planner thread. The barrier also queues a one-shot head prefetch: loads for the first window's worth of the next iteration's blocks, so no iteration cold-starts its first phase waiting on disk. Queued prefetch loads are always budgeted below the reserve — they are the one kind of work with no relief valve of its own, so what is pending must always fit in the free room the reserve guarantees — and at the very end of a proving run the queue is simply discarded (there is no next iteration left to warm).

The draining follows one rule: keep a free-block reserve, and pay for it with the LBs whose reload is furthest away. Each maintenance pass, while the free blocks are below the reserve and an eligible victim exists, the steward evicts one LB and looks again; the pass ends the moment the reserve is met — or the moment nothing is left to evict, in which case the stream simply pauses (never a silent stall). The victim it picks is the farthest-next-use LB behind the work cursor. GL sweeps its logic blocks in a fixed cyclic order, so the block just behind the cursor was processed most recently and will not be needed again until the next full sweep — the textbook Belady choice — while the blocks just ahead are needed within moments and are kept. The selection is two-tier: the steward first skips tiny LBs (a size floor — each eviction costs a fixed file write regardless of size, so evicting a tiny block pays the whole cost to reclaim almost nothing), but when the reserve is breached and nothing above the floor is left to evict, a second scan runs in the same farthest-next-use order with the floor dropped: survival beats per-eviction efficiency, because early batches consist almost entirely of tiny blocks and a floor-only drain would find no victim at all while the workers keep consuming memory. The consequence the design leans on: a run whose memory never dips below the reserve evicts nothing, therefore reloads nothing, therefore runs exactly as it did before — full speed, zero disk traffic. The current 12 GiB cap gives the heavy incubator batches ample resident headroom; historical 8 GiB comparison runs kept the pager mostly idle. If the working set itself cannot fit the pool, that is a genuinely too-small pool and the run stops at a loud assert on the next block request — never a silent wait (a dedicated stuck-detector also turns any unexpected worker wait longer than thirty seconds into an assert). In a genuine squeeze — free blocks below a small emergency floor (half of the reserve) — every worker handshake, not just one that needs a reload, may evict one block inline; a counted event the telemetry reports so a steward that cannot keep up shows up as an alarm, not a wall. The same floor guards every block request: a request that would drop below it first evicts one idle block behind the cursor, so workers that grow their blocks quickly are slowed to the speed of the SSD instead of running the pool empty.

An LB that was deactivated this iteration is the one special case: deactivation is permanent (no path ever reloads or reactivates it), so it takes the discharge protocol — its membership records are captured into tiny RAM sets (what the post-prove readers actually ask), its statement containers are emptied, and a reshuffle returns its statement blocks to the pool on the spot with zero I/O (the tables the chapter export reads — the cold string tables of §6.7, the hash memories and the origin history — survive). It then joins a pending-discharge queue. In a main batch the steward writes those survivors as one canonical image in the background right after that barrier, returns the blocks and releases their physical memory: a finished block never holds RAM again, and the chapter export reads it back. In an incubator batch, whose memory peak this early write did not lower, the queue waits for pool pressure and the chapter export reads the blocks where they are. Two blocks stay in RAM after their discharge because later barrier mail is still merged into them: the root and, in an incubator batch, the anchor block. A run that discharges nothing and never comes under pressure writes zero deload files.

There are two dump formats, chosen by what the image is for. The canonical format streams the aggregate's containers to .deload/ — element by element, in logical order, containers in tag order — then returns all blocks to the pool and marks the LB deloaded. Its byte stream is a pure function of logical content: two LBs with the same elements in the same order produce identical files, regardless of how their arenas were fragmented or which physical blocks they sat in. The dump is the canonical "straightening" of any fragmentation — and it makes these images byte-comparable across runs and hosts. This is the format the discharge drain and the chapter-export reads use, where that comparability matters.

GPU execution pages through SSD like the processor. Both routes keep the default allow_ssd_deload permission and page through the working-set steward. The GPU route runs a chunk of logic blocks at a time: each block notes its size figures at the end of its first phase, while it is still in memory, so the chunks are planned without touching any block; the route then reads each block under a claim while it projects and schedules the chunk, and keeps the steward's window open while the device output grows the memory pool, so idle blocks can be written to SSD at any point. Only the counterexample filter's short-lived clones stay resident. (allow_ssd_deload: false in a configuration pins a batch resident.)

The working-set pager's evictions — the hot loop above — instead use a raw arena image: a near-memcpy byte copy of the LB's live memory pages, plus a small map of which pages are live. Because every deloadable container (statements, the cold maps, even the throw-away hash index) packs its pages into the one LB arena, and the containers' small bookkeeping lives in the never-evicted LB shell, a page image is a complete record: reload binds the same page ids to freshly-packed pages and reads the bytes straight back — no element walk, no index rebuild, one copy. The measured element-by-element reload was the eviction loop's bottleneck; the raw image replaces it with memory-copy speed. The price, accepted deliberately: raw image bytes are not reproducible (arena fragmentation leaks into them), so they are not byte-comparable like the canonical format — but the restored logical state is identical, which is all the proof output depends on. A raw-evicted LB that is later discharged simply writes a canonical image next time.

The raw images share one file, held open for the whole batch. Opening, truncating, and closing a fresh file per eviction cost a fixed ~50 milliseconds — nearly independent of the image size, and dominated by filesystem metadata and the virus scanner's scan-on-close of each new file — times thousands of tiny-LB evictions a phase. So instead GL preallocates a single data file and gives each LB a fixed slab inside it (the smallest power-of-two multiple of a pool block that fits the image). A re-dump of the same LB overwrites its slab in place — a single positioned write into the already-open file, at memory-copy speed with no per-eviction open or close; only an LB that outgrows its slab is moved to a bigger one. Because the dumpers work on different LBs at disjoint places in the file, every I/O thread holds its own file handle and writes at its own offset with no lock — the only shared state is the tiny slab bookkeeper, touched a handful of times per LB. The file's slab offsets are not reproducible run-to-run (allocation order varies), but — like the raw bytes themselves — offsets never reach the proof output, so nothing about the result changes. The whole file is emptied and its slabs recycled at the start of each batch. This drops the per-eviction cost from tens of milliseconds to a couple, turning the eviction stream from metadata-bound back into copy-bound.

6.5.1  The file format — self-describing, fixed-width

The payload splits into chunks of at most the block size — one file per repacked block, _n_of_N in the name; an empty aggregate writes one header-only file. Every file is self-describing: magic GLDL, version, the kind (base or tail), a per-LB deload ordinal (the file's identity), part n/N, the block byte size, a per-tag directory (tag, element size, element count), the full LB chain verbatim, then the chunk. All fields are fixed-width little-endian. loadLbMemory asserts every header field — magic, version, the ordinal, the verbatim chain (the real identity check), part numbering, block bytes, cross-part directory consistency, element sizes against the compiled-in types. A mismatch is a corrupted or foreign file, stopped at its origin.

File names. LB chains contain characters that are illegal in file names (>, *) and routinely exceed path-length limits, so a file cannot simply be named after its LB. Instead each LB is assigned a deload ordinal — a plain counter — and the name is lb<ordinal>_<n>_of_<N>.bin (tail sets add a t<k>_ component). A counter is provably unique, so two files can never collide — unlike the hash it replaced, whose collision risk, though astronomically small, was real. The ordinal is assigned once and reused for every later dump of the same LB, so a base image and its tails share one identity. The full chain lives in the header verbatim, and registry.txt (one ordinal → chain line per LB, ascending) lets a human map a file back to its LB — reload never reads it, only the file set the LB recorded at dump time.

6.5.2  Reload — enumerated touch points only

ensureLoaded is a defined no-op on a resident LB; on a deloaded one it asserts the recorded chain still matches the LB's position in the tree, then rebuilds every container element by element onto a fresh consecutive arena — the reloaded LB starts at offset 0 and bumps up, regardless of the offsets it had before. The main reload sites are the next iteration's phase-1 entry, the steward's prefetch (claim-protected, so it never races a worker for the same LB), and the post-prove readers — the visualizer walking equality nodes, and the chapter export reloading a discharged LB read-only, after prove() returns. Any other code path that touches cold storage hits the residency assert — absence of a reload site is a bug surfaced at its origin, not a degraded read.

The directory is purged at batch start only. purgeDeloadDirectory runs once, before the first iteration (and asserts the directory name contains "deload" before recursively deleting anything). End-of-run images deliberately survive the run — the last iteration's deload files and registry.txt stay on disk as an inspectable record of every LB's final statified state.

6.6  Scope — what is static (the campaign is complete)

Honesty about residency. The prover runs barriered sweeps (§5.2): every active LB is touched in every phase of every iteration, so active LBs stay resident for the whole iteration — the deload/reload win applies to LBs that sit idle across iterations, not to the working set inside one sweep. A background custodian (the steward) pages idle LBs continuously, holding the resident set to the working set. The statification campaign is closed: every per-LB container family is static, and what remains is the accepted boundary below.

Static (the whole campaign)

  • The statement registries — four ordered per-block reference lists sharing immutable expression records on that block's arena.
  • The full hierarchy: pool, blocks, pages, the per-LB arena, virtual page ids, the in-place page compaction.
  • The deload/reload round-trip with the canonical byte format.
  • The growth contract — future containers join by tag, the format never restructures (the string tables of §6.7 joined exactly this way).

Accepted boundaries

  • The arena's own block/page lists — once the last heap carve-out here — are now pool-backed too: each is a small-buffer directory that keeps a tiny arena's table inline (no pool block at all) and spills only a large one onto pool blocks. A logic block's own tables live in the spare room of its shell, so only an exceptionally large logic block spills. So "all of the LB goes static" now holds for the per-LB arena bookkeeping. What stays on the heap by design is the global pool's recycle queue (one process-wide root that hands out the pool) and the compaction's transient scratch — O(blocks), not O(payload), and outside any one LB.
  • Mail content is interner-id form. Inter-LB messages carry integer ids, not std::string. Each outgoing mailbox uses its own per-block interner and deloads with that block. The single-threaded commit translates those private ids into the process-wide global id table on the mail pool; committed blobs and mailIn use the global ids. Internal same-LB mail keeps its existing local ids.
  • Per-phase deload / per-LB pipelining — active LBs stay resident for the whole iteration.

Pool sizing follows the telemetry, not folklore: peakBlocksInUse after a representative run is the measured high-water mark. An undersized pool asserts loudly at the exact allocation that crossed the line (by design); an oversized one merely wastes commit charge until the number is dialled in.

6.7  String statification — scratch, sealed, cold

Strings were the last large heap population inside the prover: every replace/parse chain in the firing check churned heap temporaries, and the per-LB interner backings — names, scope payloads, templates, values, origins, rules, LB-state — grew outside the pool's bound and outside deload. The strings campaign sorts every such string into one of three classes by lifetime, and each class gets memory shaped for exactly that lifetime.

One backing pool, distinct allocation lifetimes. Cold per-LB storage and per-worker scratch use LbArena (§6.2). Small sealed handoffs lease exclusive slices from shared pool blocks; larger contiguous records use private arena blocks. Cold content deloads and compacts. Scratch and sealed allocations retain stable pointers until their respective release boundaries. Each task owns its sealed payload and poisoning range, and a shared backing block returns only after its last live slice is released.

The cold tables are ordinary tagged containers of the aggregate (two tags each: string lengths in id order, then the concatenated bytes), so the SSD round-trip carries them with zero format changes. They survive discharge: a finished LB hands back its statement blocks but keeps its string bytes, which is what lets the chapter export reload a discharged LB read-only and still decode its full proof history. Decoded views are borrowed, never stored — the stored form is always the id.

Two deliberate residuals remain. Committed mail content uses a process-wide global interner because per-block ids are not portable. That global table, retained log windows, routing edges, cursors, and transient inboxes live on the dedicated mail pool. Producer outboxes and their private id tables deload with their blocks in the main pool. Delivered blob/reference pages and the global id table roll only for a grid that began fully active; dormant grids keep full history and the matching id table. The LB identity skeleton — the tree key, the routing map, the deload chain and file list — stays on the heap because it must remain readable while the LB itself is deloaded.

Static memory done: the motivation, the hierarchy, the page tier, the aggregate, the SSD round-trip, the scope boundary, and the string classes. The compilation-side static floor, ChunkPool (§8.7), predates the strings campaign and stays as is. Next: provenance.

Request frontiers can spill to disk

When a GPU frontier level exceeds device storage, the host retains at most 32 MiB of row payload in each of two tails. Earlier rows move to ordered disk prefixes and return through bounded transfer buffers. Stable pruning removes stopped calls without reloading the whole level or regenerating requests.

This storage is separate from logic-block paging. It follows the same deload permission; counterexample filtering and explicitly resident-only batches keep their existing behavior. File errors stop the run, and so does a deload that would pass 50 GiB (the request spill and the logic-block extent together): a runaway stops before it fills the disk. Request disk traffic and resident storage are measured separately from GPU-to-host transfers.

Bounded host construction for GPU projection

Each GPU chunk contains complete logic-block task families. The independent GPU-host pool supplies consecutive construction windows targeting 32 MiB of column storage; an individually larger block receives its exact measured window. One set of construction threads serves the chunk. When the budget permits two windows, upload overlaps construction of the next window. Otherwise one window is reused after its upload completes. If even one window plus retained input and later output support exceeds the budget, the planner selects fewer complete families. Uploaded source ordinals and name/rule lookups remain for scheduling and sealing. The upload thread releases each window as soon as its upload and sealing copy finish; no projection image is deloaded.

Shared canonical dependency edges

One stored dependency connects an exact scoped member to an exact scoped record. Both traversal directions point into the same recyclable edge node; its insertion revision preserves the order in which changed dependencies are revisited. Deletion unlinks both directions before reuse. Logical proof records, scopes and equality observations stay unchanged.

Exclusive sealed slices share backing blocks

Each sealed output retains its own immutable record chain and lifetime. Small outputs lease separate slices of the same physical block; the block returns to the main pool when its last slice is released. Larger contiguous allocations keep their ordinary private blocks. No peer may read, overwrite or poison another output's slice.

Share immutable rule value bytes across independent maps

Independent hash memories retain their own rule membership and owner lists. Byte-identical page-contained records share immutable payload; replacing a record changes only the writer's reference. Larger records stay in private paged storage and retain the full size contract. Collection removes only unreferenced shared data and obsolete private payload.

Dissecting one resident-memory snapshot

Ordinary runs retain process peaks and phase counters. The old per-structure iteration aggregate and its report writers are retired. Detailed reports use one explicit mode per run: GL_PEAK_MODE=scan locates the position, GL_PEAK_MODE=capture captures it, and leaving the setting unset disables both. Neither mode starts a second run automatically.

A diagnostic first run records peak RAM and an execution position. A second run captures the state at that position. The two footprints may differ: the report names the first peak X and the captured size Y separately. Every structure in the ownership tree is measured against Y.

The collector waits for background writers without releasing their retained buffers. It saves resident pages before walking container metadata, so inspection cannot add its page faults to the captured total. The external collector briefly holds the batch threads still, records their stacks, and can retain a raw memory dump for later inspection. Directory and data-page observation runs only during the armed capture traversal; ordinary page reads perform no observer work. Named structures take precedence over the pools and heaps backing them. Exact byte ranges split a Windows page between different structures when necessary. The retained dump and matching structure layouts allow later inspection of the same state, including inline fields and retained scratch storage. The tree distinguishes exact arithmetic from identified ownership. An explicitly unresolved remainder keeps the totals exact while showing where the owner is still unknown. Saved live task buffers and exclusive sealed slices can also be decoded later, without rerunning the proof or counting borrowed storage twice.

Independent GPU-host pool

The GPU-host allocator provides its own 4 GiB address-space reservation, with 256 KiB blocks and 2 KiB pages. Memory is committed when used, and returned blocks stay available for reuse. Its ownership directory counts against the same budget. Large contiguous column leases and paged request storage can share this reservation without consuming logical-block pool capacity.

Live ranges never move. Transfer registration ends before a lease returns to its pool. Projection windows, construction scratch, retained lookups, schedules, GPU task directories and output downloads use this reservation. The planner counts simultaneously live storage, including block rounding and scratch directories. It first tries two upload windows, then one, then fewer complete logical blocks. A single block that does not fit stops with an assertion. Output download storage starts after upload windows have returned their leases. Final proof records retain their existing storage. Request-frontier disk spilling keeps its own permission and cache policy; projection windows never spill.
