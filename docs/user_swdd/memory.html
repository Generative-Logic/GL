6 · Static memory (statification)

How the prover's per-LB containers move off the heap and onto a fixed memory hierarchy: one reservation at program start, carved into blocks, carved into fixed-size pages that per-LB containers pack their elements into, addressed by virtual page ids — and streamed to SSD between iterations in a canonical, byte-comparable format.

6.1  Why static — the MPU path and the heap ceiling

The silicon correspondence in §5.5 is a real roadmap, not decoration — and a core's on-die SRAM does not malloc. The MPU (Mathematical Processing Unit) build requires all prover memory static: every byte the prover touches must live inside a fixed reservation whose size is known before the run starts. Statification is the software half of that requirement, written so the data layout the silicon needs is already the data layout the prover runs on.

There is also an immediate, non-aspirational reason: the heap ceiling. Per-LB containers grow with the deductive neighbourhood, and at current consumption the next milestones are infeasible on realistic hardware — the run drowns in allocation long before it drowns in inference. A fixed pool turns "the run slowly eats the machine" into a single, visible sizing decision.

The migration was tier by tier: the machinery — global pool, per-LB bump arenas, arena containers, the deload format — is built once, and each tier moved one container family onto it. Tier 1 migrated the statement registry, Memory::intEncodedStatements (§3.1.2); the remaining per-LB families — the string interners (§6.7), equivalence classes, the hash inference engine, the goal registry, the cross-block mail log, and the logic-block objects themselves — followed across the campaign, which is now complete: all per-LB working memory is static (§6.6).

  • One main reservation, plus three small stand-alone pools. Almost all statified storage comes from a single allocation made at program start — never freed during the run, never grown. The software model of the MPU's fixed SRAM. Three further, smaller reservations sit beside it, each with its own exhaustion assert and never depleting the main pool. The persistent pool backs the never-deloaded goal registry — keeping it always resident, so the deactivation logic can read it even when an LB's main storage has been written out to disk (removing a source of run-to-run nondeterminism). The mail pool backs the cross-block mail log — the record of which block sent what to whom: it too is never written to disk, and being stand-alone it plays no part in any deload decision, so the mail content never competes with the main pool. The LB-body pool holds the logic-block objects themselves — every block used to be a separate heap allocation; now each is placement-constructed into a fixed-size slot carved from this pool and never moved, so the many pointers between blocks stay valid for the object's whole life. It too is never written to disk, and its blocks return to the pool when a run's analyzer is torn down, so several analyzers in one process reuse it. They are the only three sanctioned extra reservations.
  • No observable dependence on physical placement. Which physical block a container's data lands in is invisible to every proof decision and every exported artefact — the virtual-offset arena (§6.3) is what makes that claim checkable.
  • Exhaustion is an assert, not a fallback. If the pool runs out, the run stops at the allocation site with a message naming the config knob. There is no emergency heap allocation — a silent fallback would un-prove the static claim.

6.2  The memory hierarchy — pool → blocks → pages

Three levels — pool carved into blocks, blocks carved into fixed-size pages — and then the per-LB containers pack their elements contiguously into pages drawn from the LB's arena. The sizes are fixed compile-time constants in parameters.hpp (identical for every batch, never read from a config); isValidStaticMemoryConfig asserts that the pool is a whole multiple of the block and the block a power of two, and isValidStaticPageConfig that the block is a whole multiple of a power-of-two page (so an index resolves by one shift and one mask); initStaticMemory then makes the one reservation.

LevelSizing constant (parameters.hpp)OwnerUnit handed down
Poolstatic_pool_bytes (8 GiB)GlobalMemoryManager — one per processblock
Blockstatic_block_bytes (256 KiB, a power of two)LbArena — one per LBpage
Pagestatic_page_bytes (8 KiB, a power of two)the paged containers, via the arena's page tierelements (packed contiguously, addressed by page id)

The global manager re-grants recycled blocks before carving fresh ones, so the carve cursor doubles as a high-water mark of simultaneous demand; blocksInUse / peakBlocksInUse expose the sizing telemetry that turns the pool size from guesswork into a measured number.

Exhaustion policy. When acquireBlock finds the pool empty, the run asserts, naming static_pool_bytes — the operator's fix is one parameters.hpp edit and a rebuild. A fallback heap allocation here would be worse than the crash: it would silently convert "all prover memory is static" from an invariant into a hope, and the MPU sizing data would be fiction.

6.3  The page tier — virtual page ids, the determinism device

Containers never store physical pointers. They store virtual page ids (vids) and a within-page index. The arena carves its blocks into fixed-size pages; allocPage() returns a vid naming a page, and pageAt(vid) translates it to a physical page on each use. A container splits an element index into page = i >> shift, within = i & mask — one shift and one mask, because the page size is a power of two — then reads the slot inside the resolved page. The only free is freePage (LIFO: a freed page returns to the free-list, and freeing the tail rolls the page cursor back). Interior gaps left by other deletes are holes that the in-place page compaction (§6.5) reclaims by packing the live pages onto the low blocks — the one operation that ever rebinds a vid to a different page.

This indirection is the determinism device of the design. Block grant order under the global mutex is a race between worker threads, and a reloaded LB (§6.5) may land in entirely different physical blocks than before — both are fine, because no observable behavior may depend on physical block identity or grant order. Everything the prover, the exporter, and the verifier can see is phrased in virtual page ids and logical element order.

  • Resolve at every access. pageAt(vid) translates a vid → physical page on each use and asserts residency. A resolved pointer must not be stored across any call that could deload or compact the LB.
  • No per-LB lock. Per-LB state is mutated single-threaded by the phase model: the parallel phase 2 only reads LB statement containers; all mutation sites sit in phases 1 and 3. The only cross-thread touch is the global manager's mutex inside acquireBlock.
  • A two-level page directory, shift-and-mask. A directory of page ids indexes the data pages, so operator[](i) splits i into a page index and a within-page slot — all shift-and-mask, no division on the hot path — then one pageAt. The directory is adaptive: inline, then a single directory page, then — for a large container — two levels, so the index itself spans several pages (a root page of directory-page ids, each holding many data-page ids). Overflowing even two levels is a loud assert naming the next level, never a silent out-of-bounds write — the same loud-failure contract as pool exhaustion, and the fix for a corruption that hid for days. The directory lives in the arena's own pages (not the heap) and is rebuilt on reload, so its depth never reaches the deload image — the on-disk bytes are identical whatever the shape.
  • Deliberately narrow API. PagedVector<T> offers a std::vector subset — push_back, size, operator[], index-form erase, clear, release, copy-assign — and pointedly no data(), no iterators, no swap: a single contiguous data() is impossible across pages, and its absence makes the compiler enumerate every consumer still assuming flat storage. Element references are stable while the LB is resident (an element never moves under a growing container); they die at deload, clear, release, or the page compaction.

6.4  LbMemory — the growable aggregate

Each LB owns one LbMemory: a struct bundling the LB's LbArena (declared first, so the arena-backed members destruct before the arena whose blocks back them) with every statified container, keyed against an append-only ContainerTag registry. The tag is the container's on-disk identity — tags are never renumbered, reordered, or reused. visitContainers (const and mutable overloads) enumerates the members in ascending tag order and is the single source of container enumeration: the deload writer, the reload reader, and every future bulk operation walk the same visitor.

The growth contract is the point of the shape: adding a future container to the static regime is one member + one appended tag + one line in each visitContainers overload. Nothing else moves — the deload file format is self-describing per tag (§6.5), so old machinery never restructures when a new container joins.

Memory holds the aggregate as lbMemory plus a reference alias — intEncodedStatements binds to the member inside the aggregate — so the registry's many access sites keep their body.intEncodedStatements spelling unchanged through the migration. The alias carries no state of its own; its one side effect is making Memory non-whole-assignable by design — teardown swaps individual members, and a statified container's teardown idiom is release().

Why a visitor and not a serializer per container. The deload format's stability across tiers hangs on one discipline: format knowledge lives in one place, and containers only declare themselves. A per-container serializer would drift; a per-container tag plus a shared element-streaming visitor cannot.

6.5  Deload / reload — the canonical SSD round-trip

Nothing is written until the pool forces it, and RAM is treated as a cache of the working set — the logic blocks being processed right now plus the next few about to be processed. The order in which GL processes its logic blocks is fixed, so "the working set" is simply a sliding window over that order.

The steward — a dedicated background thread — maintains that window in every one of the three kernel phases (they are all equivalent here; no phase pre-loads everything). While a phase runs, the steward watches its work cursor and does two things: it prefetches the next few LBs (reloading any that sit on disk) so a worker finds its LB ready, and, once memory is tight, it drains everything outside the window back to disk — biggest LB first. A worker that reaches an LB still on disk simply loads it itself (a one-line handshake with the steward so the two never collide) and, to make room, deloads the biggest out-of-window LB in exchange. An LB being processed is never touched, and a worker is never interrupted mid-LB. The kernel decides what to discharge at its single-threaded iteration barrier (deterministic, order-and-numbers based); the steward executes while the next iteration already computes.

Three thresholds shape the draining (all simple fractions of the pool, easy to retune). Below half the pool: nothing happens — the steward is parked, no LB is evicted, so none ever needs reloading. Cross half: the steward wakes and does a one-for-one exchange — each LB loaded is paid for by deloading the biggest out-of-window LB — draining the resident set down to a 40% floor before it parks again (the 50→40 gap is a hysteresis band, so it never oscillates at the wake mark). Past three quarters: the synchronous hard water — a worker that needs a block while the pool is this full does the swap itself rather than wait for the steward, which above this mark mass-evicts. The consequence the design leans on: a light batch whose memory stays under three quarters force-deloads nothing, therefore reloads nothing, therefore runs exactly as it did before — full speed, zero disk traffic. If the working set itself cannot fit the pool, that is a genuinely too-small pool and the run stops at a loud assert — never a silent stall (a dedicated stuck-detector also turns any unexpected worker wait longer than thirty seconds into an assert).

An LB that was deactivated this iteration is the one special case: deactivation is permanent (no path ever reloads or reactivates it), so it takes the discharge protocol — its membership records are captured into tiny RAM sets (what the post-prove readers actually ask), its statement containers are emptied, and a reshuffle returns its statement blocks to the pool on the spot with zero I/O (the cold string tables survive for the chapter export — §6.7). It then joins a pending-discharge queue whose only remaining job is one final near-empty record image, which the steward writes in the background. A run whose memory never crosses the thresholds writes zero deload files.

A dump streams the aggregate's containers to .deload/ — element by element, in logical order, containers in tag order — then returns all blocks to the pool and marks the LB deloaded. The byte stream is a pure function of logical content: two LBs with the same elements in the same order produce identical files, regardless of how their arenas were fragmented or which physical blocks they sat in. The dump is the canonical "straightening" of any fragmentation — and it makes deload images byte-comparable across runs and hosts.

6.5.1  The file format — self-describing, fixed-width

The payload splits into chunks of at most the block size — one file per repacked block, _n_of_N in the name; an empty aggregate writes one header-only file. Every file is self-describing: magic GLDL, version, the kind (base or tail), a per-LB deload ordinal (the file's identity), part n/N, the block byte size, a per-tag directory (tag, element size, element count), the full LB chain verbatim, then the chunk. All fields are fixed-width little-endian. loadLbMemory asserts every header field — magic, version, the ordinal, the verbatim chain (the real identity check), part numbering, block bytes, cross-part directory consistency, element sizes against the compiled-in types. A mismatch is a corrupted or foreign file, stopped at its origin.

File names. LB chains contain characters that are illegal in file names (>, *) and routinely exceed path-length limits, so a file cannot simply be named after its LB. Instead each LB is assigned a deload ordinal — a plain counter — and the name is lb<ordinal>_<n>_of_<N>.bin (tail sets add a t<k>_ component). A counter is provably unique, so two files can never collide — unlike the hash it replaced, whose collision risk, though astronomically small, was real. The ordinal is assigned once and reused for every later dump of the same LB, so a base image and its tails share one identity. The full chain lives in the header verbatim, and registry.txt (one ordinal → chain line per LB, ascending) lets a human map a file back to its LB — reload never reads it, only the file set the LB recorded at dump time.

6.5.2  Reload — enumerated touch points only

ensureLoaded is a defined no-op on a resident LB; on a deloaded one it asserts the recorded chain still matches the LB's position in the tree, then rebuilds every container element by element onto a fresh consecutive arena — the reloaded LB starts at offset 0 and bumps up, regardless of the offsets it had before. The main reload sites are the next iteration's phase-1 entry, the steward's prefetch (claim-protected, so it never races a worker for the same LB), and the post-prove readers — the visualizer walking equality nodes, and the chapter export reloading a discharged LB read-only, after prove() returns. Any other code path that touches cold storage hits the residency assert — absence of a reload site is a bug surfaced at its origin, not a degraded read.

The directory is purged at batch start only. purgeDeloadDirectory runs once, before the first iteration (and asserts the directory name contains "deload" before recursively deleting anything). End-of-run images deliberately survive the run — the last iteration's deload files and registry.txt stay on disk as an inspectable record of every LB's final statified state.

6.6  Scope — what is static (the campaign is complete)

Honesty about residency. The prover runs barriered sweeps (§5.2): every active LB is touched in every phase of every iteration, so active LBs stay resident for the whole iteration — the deload/reload win applies to LBs that sit idle across iterations, not to the working set inside one sweep. A background custodian (the steward) pages idle LBs continuously, holding the resident set to the working set. The statification campaign is closed: every per-LB container family is static, and what remains is the accepted boundary below.

Static (the whole campaign)

  • The statement registries — all four per-LB statement vectors, element payloads packed into pages in the LB's arena, in every LB.
  • The full hierarchy: pool, blocks, pages, the per-LB arena, virtual page ids, the in-place page compaction.
  • The deload/reload round-trip with the canonical byte format.
  • The growth contract — future containers join by tag, the format never restructures (the string tables of §6.7 joined exactly this way).

Accepted boundaries

  • The arena's own block/page lists — once the last heap carve-out here — are now pool-backed too: each is a small-buffer directory that keeps a tiny arena's table inline (no pool block at all) and spills only a large one onto pool blocks. So "all of the LB goes static" now holds for the per-LB arena bookkeeping. What stays on the heap by design is the global pool's recycle queue (one process-wide root that hands out the pool) and the compaction's transient scratch — O(blocks), not O(payload), and outside any one LB.
  • Mail content is interner-id form. Inter-LB messages carry integer interner ids, not std::string. The portability problem — a per-LB id means nothing in another LB — is solved with a global interner: cross-LB routing mail uses one process-wide id table (on the mail pool, §6.1), so an id denotes the same expression at the sender and at the receiver; internal same-LB mail keeps the cheaper local per-LB ids. A message is minted to global ids only at the single-threaded commit seam and decoded back to text at the read boundary. The storage is off-heap on the mail pool, never deloaded.
  • Per-phase deload / per-LB pipelining — active LBs stay resident for the whole iteration.

Pool sizing follows the telemetry, not folklore: peakBlocksInUse after a representative run is the measured high-water mark. An undersized pool asserts loudly at the exact allocation that crossed the line (by design); an oversized one merely wastes commit charge until the number is dialled in.

6.7  String statification — scratch, sealed, cold

Strings were the last large heap population inside the prover: every replace/parse chain in the firing check churned heap temporaries, and the per-LB interner backings — names, scope payloads, templates, values, origins, rules, LB-state — grew outside the pool's bound and outside deload. The strings campaign sorts every such string into one of three classes by lifetime, and each class gets memory shaped for exactly that lifetime.

One allocator underneath. The scratch per-worker arena, the sealed-page handoff, and the cold per-LB store are the SAME arena (LbArena, §6.2) — one management code, no duplication. Cold per-LB content deloads and compacts; the scratch arena (per-worker, released back to the pool at each task's end) and the sealed pages (per-task, freed the moment a task's records are consumed) never do either, so a freshly allocated pointer stays valid until its scope ends — which is why the scratch and sealed views can hold raw pointers. The three classes below differ in lifetime, not in the page mechanics.

The cold tables are ordinary tagged containers of the aggregate (two tags each: string lengths in id order, then the concatenated bytes), so the SSD round-trip carries them with zero format changes. They survive discharge: a finished LB hands back its statement blocks but keeps its string bytes, which is what lets the chapter export reload a discharged LB read-only and still decode its full proof history. Decoded views are borrowed, never stored — the stored form is always the id.

Two deliberate residuals remain. Mail content stays in string form — interner ids are not portable across LBs, so strings are the cross-LB common space — but its storage is already cold on the dedicated mail pool (§6.1): off-heap, never deloaded, so only the message form is residual, not its residence. The LB identity skeleton — the tree key, the routing map, the deload chain and file list — stays on the heap because it must remain readable while the LB itself is deloaded.

Static memory done: the motivation, the hierarchy, the page tier, the aggregate, the SSD round-trip, the scope boundary, and the string classes. The compilation-side static floor, ChunkPool (§8.7), predates the strings campaign and stays as is. Next: provenance.
