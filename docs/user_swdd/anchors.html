9 · Anchors & types

An anchor is GL's way of saying “this run is about this mathematics, not arbitrary algebra.” It binds the symbols a theorem may use to specific axiomatic roles, and it carries types that the prover and verifier both read. This chapter is the user-side view of anchors, slot types, anchor handling, and the variable-port discipline that ties them together.

9.1  What an anchor is

Every theorem in a GL run carries an anchor atom at the outermost position of its body. The atom names the axiomatic context the theorem speaks in: which symbols are constants of the theory, what relationship those symbols are committed to. Two theorems sharing the same anchor are about the same mathematics; a theorem without the anchor is meaningless — there is no fixed vocabulary.

Architecturally, the anchor is a single atomic expression. The body of the anchor (defined in files/definitions/Anchor*.mpl) unfolds into the axiomatic claim. For Peano:

Why this matters for the prover. The prover never asserts the anchor body itself as a derived fact — the body is given, by the anchor's presence. What the prover does do is treat any expression citing an anchor slot the same way it treats a defined operator: a stable name with a known type. That treatment is what the rest of this chapter unpacks.

9.2  The four current anchors

Four anchors are live in the codebase; a fifth (AnchorFTA) is specified per FTA-ladder rung. They differ in slot count and in which kinds of mathematics they commit to.

AnchorSlotsWhat it commits to
AnchorPeano6 — [N, i0, s, +, *, i1](N, i0, s, +, *) satisfy the Peano axioms; i1 is the successor of i0. Drives the first batch.
AnchorGauss8 — [N, i0, s, +, *, i1, i2, id]Extends Peano with two more constants (i2, id). Drives the Gauss summation theorem and intermediate algebra.
AnchorIncubator814 — [N, i0, s, +, *, i1, i2, id, i3, i4, i5, i6, i7, i8]The widest anchor (the original AnchorIncubator, renamed when the incubator anchor was split). Used by the wide incubator batches to produce ground-level facts. Many slots are unused in any individual theorem but available to the conjecturer's enumeration.
AnchorIncubator39 — [N, i0, s, +, *, i1, i2, id, i3]The narrow incubator anchor (Gauss plus i3). Used by the AI3 incubator batches and the FTA-rung-1 batch, whose shorter successor chain generates only the i0–i3 facts it needs and so avoids saturating the int16 name-id cap.

9.2.1  Free vs bound anchor slots

An anchor slot may appear in a theorem's outer >[…] bound list or not. In the example body of §9.1, every anchor slot — N, i0, s, +, *, i1 — is bound, in occurrence order: the theorem reads as “for any N, i0, s, +, *, i1 satisfying the Peano axioms, the conclusion holds.” The conjecturer binds every non-u_ variable, including every anchor argument, in the outer >[…] at its left-most mention — there is no longer a “bind only the body-referenced subset” carve-out.

History of the binding rule. Two earlier shapes existed and were unified. (a) An even earlier version forbade anchor-slot names from appearing in inner >[…] lists at all: binding them inner would have turned “for the Peano integers” into “for arbitrary structures.” (b) A later sparse rule had theorems bind only the anchor slots that occurred at least twice in the body, while every other implication bound all of its non-u_ variables — two inconsistent shapes the verifier had to special-case. The 2026 inversion folded both into one rule: every non-u_ variable, anchor or not, binds at its left-most premise, everywhere (reconstructImplication collapses to a thin forwarder around reconstructImplicationFullBind). The reformulation chapter (§10) covers the equivalent mechanic for non-anchor variables.

9.3  Slot types — the (1) / P(1) / P(x(1)(1)) lattice

Each anchor slot has a fixed type declared in Config<Tag>.json's definition_sets table. The type is a string in a small, regular grammar.

TypeMeansAnchor slots that have it
(1)An element of the base domain (a natural number)i0, i1, i2, i3, …
P(1)A set over the base domain (a subset of ℕ)N
P(x(1)(1))A relation over pairs, used as a unary functions (successor), id (identity)
P(x(1)(x(1)(1)))A relation over triples, used as a binary function+, *

9.3.1  Reading the type grammar

The grammar is small and regular:

  • (1) — “element of the base domain.”
  • P(T) — “predicate / set over T.”
  • x(T₁)(T₂) — “tuple of T₁, T₂.”

So P(x(1)(x(1)(1))) reads, right-to-left, “tuple of (number, tuple of (number, number)), set of” — i.e. a set of triples (a, (b, c)), which is exactly the shape of a binary function written as a ternary relation. GL avoids built-in “function” types because the prover's hash engine sees relations more naturally; the type system reflects that choice.

9.4  Anchor handling — prehandleAnchor

Anchor handling is the runtime stage that resolves raw bound-variable indices (the conjecturer emits 1, 2, 3, …) to axed-anchor shapes that the proof graph can render. It runs once, at the top of analyzeExpressions, before the first prove cycle.

9.4.1  The trace-variable filter

Not every (1)-typed slot of an ancestor anchor gets axed at every descendant LB — only those whose original argument actually appears in the chain of LB exprKeys between the anchor LB and the current one. The function collects the chain's variables into a traceVariables set as it walks upward, and the slot-replacement step skips any slot whose original argument isn't in that set. The effect is that the axed expression is minimally specialised — adding fresh x-names only for slots the current LB actually mentions.

9.4.2  The recursion-LB special case

A recursion LB (an induction-hypothesis stub) gets an early return: prehandleAnchor does not register the axed-anchor expression as a statement on a recursion stub. Reason: an induction hypothesis must not see the axed variables as derivable facts; the induction would over- or under-fire. But the history entry must still travel. Without an exprOriginMap entry, an implication firing inside the recursion LB and citing the axed form as an antecedent leaves the chapter walker with no origin to chain to — buildStack asserts.

The mechanism: prehandleAnchor records the history line with a single addOriginEncoded to the local map on the producing LB. The standard cycle-boundary mail propagation carries that history line into descendants — including the recursion stub — so the recursion stub ends up with the origin recorded but the statement never installed.

9.5  The _copy machinery

When the prover needs a fresh distinct copy of an integer anchor slot — distinct in identity but constrained to equal the original — it mints an x- prefixed name during proof. x5 means “a fresh copy of i1.” Stage 6 (the proof-graph processor, process_proof_graphs.py) renames x<N> to <digit>_copy where the digit is the integer slot's own index (i0→0, i1→1). Two copies of the same slot become 0_copy and 0_copy_copy (no observed three-level nesting in practice).

9.6  The anchor handling proof-graph row

Each chapter contains at most one anchor handling row. The row is the bridge between the original anchor expression (with its declared slot names) and the axed form (with _copy rewrites). Example: 

(AnchorPeano[N,0_copy,s,+,*,i1])    main    anchor handling    (AnchorPeano[N,i0,s,+,*,i1])    main

Read: the expression on the left (axed: 0_copy in slot 2, i0's slot) was derived by anchor handling from the original (right). The verifier's check_anchor_handling validates three things:

  • Shape. Both sides must be anchor atoms whose head matches.
  • Type consistency. Every substitution must respect the slot's declared type (see §9.3 / §9.7).
  • Uniqueness. At most one anchor-handling row per chapter.

Following an anchor handling row, zero or more anchor handling trace rows record one step of the _copy substitution chain each. The verifier counts these but does not deeply validate them — they exist for human auditability.

9.7  Variable-port type consistency — I-29

The hash engine wires expressions together by argument position. Within a single chapter-row expression, a variable that appears in argument slot 2 of in3 and in argument slot 1 of in2 is the same variable: the two operator atoms share that port. I-29 says that every such shared port must carry the same declared type everywhere it appears in that expression. The scope is exactly that one expression — two same-named variables in alpha-distinct >[…] scopes are independent ports, and I-29 never reaches across that boundary.

Why I-29 was added. Before D-41, the verifier did not cross-check type labels at port boundaries. A misconfigured operator (an in3 declaration saying its second slot is P(1), while the rest of the codebase treats it as (1)) would produce technically-valid chapter rows whose underlying semantics had silently shifted. I-29 is the verifier-side check that makes the discrepancy observable. The producer side (the operator declarations and the conjecturer's enumeration filters) is not yet self-validating; the in-flight check is the load-bearing safeguard.

9.7.1  Where the types come from

The single source of truth is Config<Tag>.json's definition_sets field. Every operator declaration in files/definitions/ must agree with it; every chapter row inherits its port types from it via the operator's signature; every variable inherits its type from the ports it touches. The verifier's definition set consistency meta-check is the catch-all.

9.8  Cross-anchor theorems & the FTA bridge

A theorem can reference two anchors. Specifically, the cross-anchor bridge theorem 

(>[N,i0,s,+,*,i1]
    (AnchorGauss[N,i0,s,+,*,i1,i2,id])
    (AnchorPeano[N,i0,s,+,*,i1]))

expresses the trivial-but-load-bearing claim “any structure satisfying the Gauss anchor also satisfies the Peano anchor” (via the shared first six slots). The bridge lets a Gauss-batch proof cite a Peano-batch theorem as a given: the Peano theorem's premise AnchorPeano is discharged by the bridge from the Gauss context.

This bridge is an externally-supplied direct theorem, not conjecturer output, so its outer binder need not follow the full-bind rule of §9.2.1 — i2 and id stay free even though they appear in the AnchorGauss premise.

9.8.1  Anchor vs scope — not the same thing

A common confusion (worth stating sharply): the anchor is a content commitment (which mathematics); the scope (a.k.a. validityName) is a provenance marker (where a statement is asserted). A theorem under AnchorGauss is still proved at v=main by default — the anchor does not open a scope. Scopes open for hypothetical reasoning (§3.4); anchors fix axiomatic content.

9.9  Failure modes

“buildStack asserts at validity=main, exprKey=(in2[rec0,7,3])”
Most often: an axed-anchor expression reached a recursion LB without the history entry propagating. The addOriginEncoded write in prehandleAnchor, carried to the stub by mail, is the fix; if the history line never reaches the stub, the recursion chain breaks. Check: the producing non-recursion LB records the origin in its local map.
“Verifier reports anchor handling row count = 2 in chapter X”
The chapter has two distinct anchor-handling expressions — almost always a bug in stage 6's Priority 2.5 rename or in the prover's prehandleAnchor. Check: every chapter has at most one anchor-handling target.
“A theorem under AnchorGauss is silently treated as AnchorPeano”
Anchor detection in the verifier and stage 6 is a substring search for "Anchor". If an unrelated string happened to contain the substring, the dispatcher misroutes. Check: no MPL definition introduces an operator name containing Anchor outside the designated anchor atoms.
“Adding a new anchor (FTA) — one of the hardcoded sites missed”
Anchor slot count is implicit across about a dozen places: conjecturer filters, verifier logic, rename priorities, stage-6 anchor rename, several prover sites. There is no single source of truth. Check: the recipe in the project's anchor-change reference; every site that hardcodes the count must change in the same commit.
“Type mismatch silently passes”
If the operator definition file says (1) in a slot the config says P(1), and a chapter row uses the variable there, the verifier's definition set consistency meta-check should fail — but only checks the in-flight artefact, not the producer side. Check: Config<Tag>.json's definition_sets table against every operator's slot signature.
