# Core concept — String statification cookbook `[DRAFT]`

> You have a heap `std::string` (or a `std::map<std::string,…>`, a `std::set<std::string>`, an `ExpressionWithValidity`, an `OriginLine`) inside the `standardProcessing` tree and Rule 28 says it must come off the heap — and stay off. Strings are almost always **"a span or an id"** — so unlike the container cookbook [`09b_statification_cookbook.md`](09b_statification_cookbook.md), this is **not a type-indexed table**. The interesting content is the DECISIONS (which arena, `decodeView` vs `copyFrom`, add a door vs cascade a signature vs STOP) and the TRAPS. Find your decision, copy the shape from the cited commit, reuse the existing `str_ops` primitive.
>
> **The one rule:** no heap `std::string` survives in the tree. The compiled-definition layer — `compiledExpressions`, `coreExpressionMap`, and the string `Instruction` integration working form's remaining heap islands (the `ce::` calls, the `EncodedExpression` parse boundary) — is still on the heap, but that is an OPEN violation to statify, NOT a sanctioned island (the disintegration WORKING form is entirely the arena `WorkInstruction`: the cycle-interface batch deleted the `disintegrateExpr2` → `disintegrateExprCore2` `std::vector<LogicalEntity>` bridge, and the cycle-innards batch retired `disintegrateExprCore2`'s per-hit `entityAt` materialization (it reads the `WorkInstruction` span accessors directly) plus the `expandSignature` / `listLastRemovedArgsLE` span-run overloads, so no string `LogicalEntity` survives on the disintegration path) (the rule: in `performElem1/2/3` the only permitted heap is `hashburst_trace.txt` generation). While it remains, its read side is fenced by the two accessors `ExpressionAnalyzer::compiledEntity(StrSpan)` / `coreConfig(StrSpan)` (transparent `std::less<>` maps, `nullptr` = defined miss, zero-allocation span probe — [`I-137`](../30_invariants.md#i-137)), so even the compiled-definition point reads no longer materialize a probe `std::string`. Everything else — decoded names, substitution maps, origin records, mail keys, statement buffers — becomes a span or a dense id. This file is the string→span/id companion to [`09b`](09b_statification_cookbook.md) (whose row 64 is where the span doors themselves are catalogued); the campaign that produced it (`standardProcessing` interior, ~60 commits, byte-clean) is [`I-138`](../30_invariants.md#i-138) — **complete**: the roots batch flipped the two last-remaining `false` inventory rows (`standardProcessing` itself and `applyEquivalenceClassToAdmissionMapIntegration`) to `true`, so the whole `standardProcessing` tree now reads 0% heap. ONE documented OPEN violation remains: the compiled-definition layer above. (The `IntInstruction` working-struct boundary — a `std::vector` inside a user struct, a CodeQL blind spot — was eliminated by the follow-on batch's four heap-free `ArenaIntegrationMap` doors, so no `IntInstruction` / `IntLogicalEntity` struct is constructed on the tree.)

## The bar — 0% heap, measured by the inventory

Read [`09b`'s Definition block](09b_statification_cookbook.md#definition-statified-means-0-heap-read-this-first) first — it governs this file too. In short: a function is *statified* iff `statification/inventory.md` marks it `true` — **0% heap**, no owning `std` container as a local/temporary AND none taken/returned by value (`const std::string&` / `StrSpan` params are fine). The two mechanics ([D-192](../40_decisions.md)):

- **The boundary copy lives in the still-heap caller** — statified A takes spans/ids, the heap caller B does the `std::string`↔span copy; never inside A.
- **No static→heap→static walk-around** — a caller already holding a `ScratchString`/`StrSpan`/arena value calls the statified function directly, static→static; converting to `std::string` only to reach a heap function and back is deleted, not tolerated.

"Convert the interior, keep the `std::string` boundary" is NOT statified. Materialize a `std::string` only in a not-yet-statified caller/sink.

## Step 0 — the string decision (this is not the container table)

For a container, [`09b`](09b_statification_cookbook.md) tells you *which cold type replaces it*. For a string, the type is nearly always foregone — a `StrSpan` (non-owning view) or an interner id. What is NOT foregone is four decisions, taken in order:

1. **Is it a DECODED name, a FRESH concatenation, or a COMPILED-definition key?** A decoded interner name → Section 1 (`decodeView`/`copyFrom`). A freshly-built string (`(=[x,y])`, `base+"_integration_goal"`) → Section 4 (fresh-string builder). A compiled-definition key (`ce::extractExpression(...)` into `compiledExpressions`) → currently **LEFT on heap**, but that is an OPEN violation to statify, NOT a sanctioned exception (the rule: in `performElem1/2/3` the only permitted heap is `hashburst_trace.txt` generation).
2. **Does a callee force the `std::string`?** If a sink or helper takes `const std::string&` only to slice/encode it, give it a span door instead of feeding it a materialized copy → Sections 2 (helper doors) and 3 (sink doors).
3. **Is the string's iteration ORDER observable?** A `std::set`/`std::map<std::string>` whose walk order reaches an artifact → Section 5 (decoded-lex index). Order-free membership → a `ColdHashSet` (that is [`09b`](09b_statification_cookbook.md) row 50, a container, not this file).
4. **Where does it dangle?** Every span conversion is a lifetime question — the whole correctness risk is Section 1's `decodeView`-vs-`copyFrom` split and the Pitfalls.

If a value is consumed by an out-of-scope subsystem (a not-yet-statified sink, a `std::tuple<std::string,int>` drain), the materialization is done in **that heap consumer**, never inside the function you are statifying — which returns spans/ids, 0% heap. "Materialize at the edge" is the consumer's copy, not a licence to keep a `std::string` in your own return type or body. The cross-LB heap-`Mail` wire is NOT a legitimate permanent edge: it is an OPEN statification target (the rule — in `performElem1/2/3` the only permitted heap is `hashburst_trace.txt` generation). Everything OWNED inside the tree is a target.

## The two arenas

String statification rides the SAME per-slot scratch registries as the container campaign, but the string tier and the page tier are **kept apart on purpose** ([I-124](../30_invariants.md#i-124); [`09b`](09b_statification_cookbook.md) pitfall 3):

- **`scratchArenas`** — the STRING-tier, byte-bump-only arena (`scratch_arena.hpp`). Hosts `ScratchString` fills and per-call string windows. **Never** put a page container (`PagedVector` / `ColdHashSet`) here — a `ScratchScope` rewind frees its pages; and never byte-bump it with raw container fill — that muddies the `ScratchString` liveness tripwire.
- **`genScratchArenas`** — the page-tier + byte-bump arena for containers AND for struct scratch. A decoded-lex INDEX (`int32_t[]`, Section 5) is byte-bump scratch and rides HERE; the string it decodes rides `scratchArenas`. The two tiers coexist on one arena (byte-bump `alloc` and page `allocPage` use separate block tables — [`09b`](09b_statification_cookbook.md) pitfall 2).
- **Slot handle, everywhere:** `const unsigned slot = (Memory::g_currentCoreId >= 0)? Memory::g_currentCoreId: <registry>.slotCount - 1;` then `<registry>.forSlot(slot)`. **Per-registry derivation:** the `-1` fallback comes from the `slotCount` of the registry BEING INDEXED — the two registries differ by one slot (`scratchArenas` has a dedicated reserved slot, `genScratchArenas` does not), so a slot derived from one must never index the other; a site touching both registries computes both slots (`G-57`). Both registries are released per worker task at `performElem2` exit.

## 1. `decodeView` vs `copyFrom` — THE decision (and the #1 bug source)

Both read a name off an interner. The choice is a **lifetime** question, and getting it wrong is the campaign's single largest source of silent divergence.

- **`decodeView`** — `NameMap::decodeView(id) → StrSpan` (twins on `ValueInterner::decodeView` / `TemplateInterner::decodeView` / `ColdStringTable::view`). Zero-copy: the span aliases the interner's cold `PagedVector<char>` bytes. Use when **NO mint into that SAME interner** falls between the decode and the span's last use.
- **`ScratchString::copyFrom`** — `ScratchString::copyFrom(scratchArenas.forSlot(slot), view.ptr, view.len)` ([`scratch_string.hpp · ScratchString`](../../GL_Quick_VS/GL_Quick/src/memory_infra/scratch_string.hpp)). An arena copy on the STRING tier. Use when a mint into the source interner DOES intervene.

**Feasibility is universal on the read side.** Every interner exposes a non-minting `decodeView` (`NameMap` / `ValueInterner` / `originInterner` / `TemplateInterner`, plus `NameMap::decodeSubView` for validity-stack payloads, and `Memory::exprKeyView` over the process-wide never-deloaded `skeletonInterner`), so a decode site can ALWAYS become a span. The `exprKeyView` migration is the LB-identity case: every in-tree `exprKey` caller (`getGlobalKey`, `dischargeToBeProved`'s `(in2[rec` prefix probe via `startsWithSpan`, `dischargeContradiction`) reads the span form — `exprKeyView` bytes == `exprKey` and `skeletonInterner` is frozen through the parallel phase (D-186), so no walk mints it and no `copyFrom` is needed; `getGlobalKey`'s heap `std::vector<std::string>` return became a caller-fill `StrSpan* out` run (09b row 87), its owning form retained as the twin oracle. The gaps are only on the write/probe side and are filled additively when a caller needs them (Section 2): `NameMap` and `ValueInterner` already expose `encode(StrSpan)` + `lookup(StrSpan)`; `TemplateInterner` had string-only `encode`/`lookup` (the one real gap the campaign closed).

**Why a wrong call dangles.** A mint (`nameMap.encode`, `encodeExpression`, `mintOriginKey`, or a nested `addStatement` / `emitNew` that mints) can grow the interner's byte pool onto a fresh page, and a deload frees pages outright — a `decodeView` span taken before then points at moved/freed bytes. This is [I-3](../30_invariants.md#i-3). The `ScratchString` copy rides a DIFFERENT arena than the interner, so it survives the mint.

**Decision procedure.**
1. Find the span's LAST use.
2. Between the decode and that last use, does any statement mint into the **source** interner (the one you decoded from)? Count nested calls — `addStatement`, `emitNew → addStatement`, `mintTemplateKey`, `resetResentExpressionRegistries`.
 - **No source-interner mint** → `decodeView` (zero-copy).
 - **A source-interner mint** → `copyFrom` onto `scratchArenas`.
3. A mint into a **different** interner is SAFE for `decodeView`. This is the common "there's a nearby mint but it's fine" case: the equi-class hooks stage into an arena `ColdHashSet` (a different interner) while holding NameMap `decodeView` spans, and DEFER the NameMap-minting drain past the whole span walk ([`09b`](09b_statification_cookbook.md) row 55 / [`prover.hpp · applyEquivalenceClassToRejectedMapIntegration`](../../GL_Quick_VS/GL_Quick/src/prover.hpp)).

```cpp
// decodeView — no source-interner mint before last use (span-only uses)
const StrSpan canon = nameMap.decodeView(canonId);
// … getArgsSpans / compareSpans / replaceKeysScratch / arena-interner mint …
//   (the NameMap-minting drain is deferred past this point)

// copyFrom — a source-interner mint intervenes before last use
const unsigned slot = (Memory::g_currentCoreId >= 0)
    ? Memory::g_currentCoreId : scratchArenas().slotCount() - 1;
ScratchArena& sa = scratchArenas().forSlot(slot);
ScratchScope scope(sa);
const ScratchString classVal =
    ScratchString::copyFrom(sa, view.ptr, view.len);
// … the apply* hooks + applyEquivalenceClass MINT NameMap here …
someHook(StrSpan(classVal), …);   // valid: rides sa, not the NameMap
```

**Precedent — `prover.hpp · applyEquivalenceClassToAdmissionMap`:** the batch's founding `copyFrom`. Its per-call `std::map<std::string,std::string>` substitution map became a contiguous `StrReplacement` run on the gen-scratch arena, with each member / canonical name copied onto the string-scratch arena via `ScratchString::copyFrom` so the span **outlives its `ScratchString` local AND any later NameMap growth**; the substitution runs through `replaceKeysScratch`, the byte-exact greedy-longest twin of `ce::replaceKeysInString`.

**The apply-tree audit split** (recorded in the recipe files): `decodeView` is SAFE — provably — for `elem` / `ra` / `av` / `vExpression` / `stmtOriginal` (the nearby mint is either after the last use, or into a DIFFERENT interner); `copyFrom` is MANDATORY for `exprOriginal` / `exprValidityName` / the `applyEquiClasses` `classValidity` anchor (a NameMap mint intervenes), and for the S9 `isAdmitted` gate's per-tuple `keyVec` / `remVec` (each `valueInterner.decodeView` copied onto the string arena because `updateAdmissionMap`, called inside the loop, mints the SAME `valueInterner`). Many of the "owned copy (I-3)" comments the campaign found were **conservative** — `decodeView` removes the heap copy once you have proved no source mint intervenes; prove it in the commit body. **`dischargeContradiction` (pre-cycle rump) is the fullest split in one function:** `theorem` stays `decodeView` (proved: NO NameMap mint between the decode and its `SealedString::copyFrom` — the intervening cleanOp/mbKey work reads the frozen skeletonInterner + slices spans, and `addOriginEncoded` mints `originInterner` only); `expr` / `validityName` / `recursionPremise` are `copyFrom` onto the per-iteration `sArena` (the `nameMap.encode(negation)` and `addStatement` NameMap mints intervene before their last uses — via `origin.deps`); `negation` is a `negateScratch` span on `sArena` (a DIFFERENT arena than the NameMap, so it survives every NameMap mint — a bare `StrSpan`, safe only because nothing rewinds `sArena` below it and the vacuous branch's `dcRowScope` marks ABOVE it); `mbKey` / `cleanOp` are zero-copy `exprKeyView` sub-spans (frozen skeletonInterner, D-186); `negCleanOp` is a fresh explicit-length `"!"`-prefix build on `sArena` (09c Section 4). The per-iteration `ScratchScope iterScope(sArena)` at the loop top is load-bearing — every `continue` (no-contradiction) and every `return` (discharge) rewinds it, reproducing the heap version's per-iteration RAII free (its batch-8 `exprKeyView` / `decodeToBeProvedSorted` migrations preceded this).

## 2. Span doors — additive overload, outright cascade, or STOP

When a callee takes `const std::string&` only to slice or encode the bytes, give it a `StrSpan` form so the caller stops materializing. Three shapes, chosen by blast radius:

- **Additive overload (default).** Add `X(StrSpan)` beside `X(const std::string&)`; keep BOTH (the string form still serves out-of-tree callers and not-yet-converted sites). Byte-identical by construction — the span twin runs the same encode/lookup on the same bytes; Rule-18 twin-test asserts it. Examples: `prover.hpp · classifyOrScopeView` (`classifyOrScope` gains the zero-copy `classifyOrScopeView(const NameMap&, int16_t, StrSpan& orExprOut, StrSpan& branchBodyOut)` twin — out-params alias sub-table cold bytes, valid only to the next mint into that sub-table, [I-3](../30_invariants.md#i-3)); the packed-key splitters `decodeTemplateKeyView(int32_t, const TemplateInterner&, const NameMap&, StrSpan& templateOut, StrSpan& validityOut)` and `decodeOriginKeyView(int64_t, const ValueInterner&, StrSpan& exprOut, StrSpan& validityOut)` (out-params replacing a returned `std::pair<StrSpan,StrSpan>` / `std::pair<std::string,std::string>` — the by-value `std::pair` was itself the flagged heap; each caller mints into a DIFFERENT arena interner or copies in the same statement, so `decodeView` is I-3-safe; `decodeOriginKey`'s owning form is KEPT for the visualizer + twin oracle); the L7 foundation twins `NameMap::strictAncestorNames(StrSpan)` and `lookupOriginKey(StrSpan, StrSpan)`. Most probe helpers mirror in ONE line because they only forward `nm.lookup`/`nm.encode`: `lookupStatementFlags` / `lookupStatementLevels(StrSpan, StrSpan)`, `deeperOf(StrSpan, StrSpan)`, `NameMap::decodeSubView`, `TemplateInterner::lookup(StrSpan)`, `chooseCanonicalId` (returns the id, so the caller `decodeView`s it). This "trivial mirror" set is what unlocks a cluster's `decodeView`/`copyFrom` conversions (Section 1) without touching the callee's body.
- **Outright signature cascade.** Retype `const std::string&` → `StrSpan` **in place, no overload, one all-or-nothing commit**. Use when a BOUNDED cluster passes the same value among themselves and will not compile half-converted. `prover.hpp · addStatement` (L6): the statement param threads `StrSpan` across six functions at once — `addStatement` / `addEquality` / `addNegatedEquality` / `updateEquivalenceClasses` / `applyEquivalenceClassToNegatedEquality` / `updateWeakVariables` — because "won't compile incrementally". `prover.cpp · addEquality` (L3 S6): the origin pass-through param `const OriginLine&` → `const TransientOrigin&` across `addExprToMemoryBlock → addStatement → addEquality`/`addNegatedEquality`/`updateEquivalenceClasses` (five functions, one commit).
- **STOP where you are not converting in this pass — and mark why.** When the cascade reaches PERVASIVE machinery — the compiled-definition layer, or a callee shared with out-of-kernel callers — do NOT chase it in a string batch: the still-heap CALLER/sink materializes ONE `std::string` at the edge, while the function you are statifying still takes/returns spans (0% heap — the STOP is never a `std::string` kept in your own signature or body). But distinguish the two: a callee shared with OUT-OF-KERNEL code (dump, tests, load-time) is a genuine boundary; the compiled-definition layer is an OPEN statification violation you are DEFERRING, not a legitimate permanent heap boundary (the rule: in `performElem1/2/3` the only permitted heap is `hashburst_trace.txt` generation). The L7 `validityName` sweep stopped at `checkForEquivalence` / `prepareIntegration*` (they kept `const std::string&`), but the cycle-interface batch reopened them: `checkForEquivalence` gained an additive `checkForEquivalence(StrSpan, StrSpan, Memory&)` overload (the string form now delegates to it; twin `check_for_equivalence_span_matches_string`) so a span-native caller reaches it 0% heap, and the `prepareIntegration*` cluster's by-value strings were spanned / its heap delegator deleted in the same batch. The sweep's third stop, the `cleanUpAdmissionMap*` sweep pair, has since been deleted as dead code. L9 Item 3 (`prover.cpp · addExprToMemoryBlock`) materializes a single `exprStr` / `validityNameStr` **past the status-4 return** for the compiled-definition + prover doors still on heap (open violations), while the span-native fast paths above it materialize nothing. **The test:** is the callee the tree's interior (convert / cascade) or the compiled-definition layer / shared out-of-tree (stop, materialize once)? The S9 `isAdmittedIntegration` interior is span-native (its rename via `prefixNonMarkerArgumentsWithUScratch`, the `"in"` gate + args via `extractExpressionUniversalSpan` / `getArgsSpans`, `lookupTemplateKey` / `cleanAdmissionMap` / `valueInterner` via span doors). **S10 closed its two former edges** (the ledgered `S10 EDGE` sites are gone): `prepareIntegrationCore2`'s `std::map<std::string,std::string>` param became a `StrReplacement` run (the one-pair `"marker" -> "u_"+var` builds on the caller's held arena), and `ArenaIntegrationMap::sortedIndices`'s heap `std::vector<int32_t>` became a caller-fill `(out, cap)` run.

**A compiled-definition walker CAN get a span twin — the `ce::` twin (09b row 90).** The STOP above defers the compiled-definition *map probes* (`compiledEntity` / `coreConfig`), but a `ce::` walker that only *slices its input* is converted the same way any other function is: author a coexisting static twin, migrate the in-tree callers, leave the heap `ce::` for out-of-tree callers + the twin-test oracle. `ce::disintegrateImplicationSpans` (`compiler.hpp`) is the first: a `template <TripleSink>` visitor replaying `disintegrateImplication`'s iterative layer-peel with `headOut` + each triple's `(keySpan, bvSpans)` as `StrSpan`s INTO the caller's stable input — zero fresh bytes, no `std::set<std::string> leftArgs` (get<2>, never read in-tree), no `DisintCache`, no `coreExpressionMap`. The four in-tree callers (`findDigitArgs` / `multiplyImplication` ×2 / `addExprToMemoryBlock` / `addToHashMemory`) copy the spans into their own heap at the edge; the sink fires synchronously so it never stashes a `StrSpan` ([I-116](../30_invariants.md#i-116)). Byte-twin test `disintegrate_implication_spans_matches_heap`.

**Mint-order rule — load-bearing, never violated.** `encode(StrSpan)` must mint the SAME id as `encode(std::string)`: same bytes, same argument-evaluation order. **Never reorder mints when converting.** Interner ids are first-seen order ([I-84](../30_invariants.md#i-84)) and the id→string map reaches the `.deload/` stream, so a reordered mint changes deload bytes even when no theorem or verifier byte moves. `prover.hpp · addStatement` keeps the mirror push where it is precisely because "nothing mints between the current push site and `addEquality`'s mirror registration"; removing a transient `EncodedExpression` "changes no id order" only because the struct path did no NameMap mint. Prove the mint sequence unchanged in the commit body.

## 3. Sink doors — the convergence point

A sink that takes a heap STRUCT (`ExpressionWithValidity`, `OriginLine`, `AdmissionMapValue`) forces every caller to BUILD that struct just to deposit. A span/id door on the sink lets the whole upstream cluster drop its transient structs at once — the **highest-leverage** door type (one door retires many builds), which is why the campaign landed sink doors early and cascaded callers cluster by cluster.

The four canonical sink doors:

- **Internal mail** — `memory.hpp · insertInternalStatement` / `addInternalMailOrigin` (L4): `insertInternalStatement(ColdMail&, NameMap&, StrSpan original, StrSpan validityName, const std::set<int>&)` and `addInternalMailOrigin(ColdMail&, ValueInterner&, StrSpan, StrSpan, …)`. Callers stop building a transient `ExpressionWithValidity` to key a mail deposit; they pass spans over stable `std::string` / `ScratchString` inputs. At L4 only the KEY is spanned; the origin RECORD stayed string until L3.
- **Origin record** — `memory.hpp · encodeOriginSpans` (L3 foundation): `struct OriginDep { StrSpan original; StrSpan validity; }` (a stack antecedent) + `encodeOriginSpans(OriginTag, const OriginDep*, int, ValueInterner&) -> IdOrigin` + five span-RECORD doors — `addOriginEncoded` (cold `TypedColdBlobMap<int64_t,IdOrigin>` + heap `IdOriginMap`), `MergeClassAccum::addOriginEnc`, `addInternalMailOrigin`, `addRoutingMailOrigin`. Each takes `OriginTag tag + const OriginDep* deps + int depN` instead of a heap `OriginLine`. `encodeOriginSpans` is the byte-twin of `encodeOrigin`: the tag is passed directly (interned by neither path), the deps mint via the `mintOriginKey` span twin in positional order, the D-49 cap-full preference fires identically. **Batch 6 pushed this one level deeper:** every origin door BODY (`addOriginEncoded` heap/cold, `addInternalMailOrigin`, `addRoutingMailOrigin`, `MergeClassAccum::addOriginEnc`, both the span-antecedent and the EWV/`OriginLine`-antecedent overloads) drops its `encodeOrigin` / `encodeOriginSpans` call and mints the dependency keys straight into a `kMaxOriginDeps` stack buffer (`mintOriginDepsInto` / `mintOriginDepsFromEWVInto`), then feeds the POD `serialize*To` / `addOriginId` / `addMailOriginRecord` overloads — no `IdOrigin` / `IntMailOrigin` heap vector materialized. Doors are KEY-FIRST (mint the origin key, then the deps): the single-expression `addOriginEncoded` doors' old `addOriginId(map, mintOriginKey(...), encode…(...), cap)` had MSVC-unspecified key-vs-deps evaluation order; the explicit statements pin it deterministically under the user's byte-identity waiver (only the gitignored `.deload/` id VALUES may reassign — `files/` is id-value-independent). `encodeOrigin` / `encodeOriginSpans` / `decodeOrigin` survive as retained twin oracles.
- **Central add door** — `prover.cpp · addExprToMemoryBlock` (L9 Item 3): `addExprToMemoryBlock`'s `const std::string& expr` / by-value `std::string validityName` both → `StrSpan`. The span-native fast paths (Site F/H ancestor-dedupe, axed-var scan, status-4) now materialize NOTHING — the win over the old by-value `validityName` copy paid on EVERY call.

The upstream effect is dramatic: L4's mail door let `ordisMerge` drop two `addExpression.toStdString` + two `std::string(mergeParentView…)` builds per convergence; L3's origin doors retired ~35–40 `OriginLine` constructions feeding ~57 door calls; the `TransientOrigin` carrier (`prover.cpp · addEquality`) threaded the last one down the five-function chain with a `present==false` sentinel reproducing the empty-`OriginLine` case exactly (so an empty origin never reaches `encodeOrigin`'s `originTagFromString("")` assert).

## 4. Fresh-string builders

When the value is NOT a decoded name but a freshly-CONCATENATED string — `(=[x,y])`, `"!("+…+")"`, `base+"_integration_goal"`, a `u_`-stripped form — build it on the STRING tier (`scratchArenas`), never on the heap, disjoint from the target interner.

**Recipe.**
1. One `ScratchScope` on the slot arena.
2. **EXPLICIT length.** Compute the exact byte count, `arena.allocBytes(n)`, fill byte-by-byte, `ScratchString::wrap(arena, buf, n)` — OR use a `str_ops` builder that computes its own length in a first pass (`replaceKeysScratch` / `replaceUSubstringsScratch`, and the prover twin `removeUPrefixScratch`). `assert(at == n)` after a hand fill (the exact-length doctrine — `replaceKeysScratch` runs two passes, length then fill, off one shared scan, so they cannot diverge).
3. **Disjoint arena.** The builder writes `scratchArenas`; the door mints into the interner's OWN cold pool, so the fresh span survives the mint (the same guarantee `prover.hpp · applyEquivalenceClassToAdmissionMap`'s `copyFrom` relies on).
4. **Hold it named.** Keep the result as a NAMED `ScratchString` local so its span stays live across the (possibly paired) door calls; multiple fresh spans coexist under ONE `ScratchScope` because `allocBytes` byte-bumps.

**Precedents.** `addEquality` / `addNegatedEquality`'s `(=[a1,a0])` mirror on the string arena (`prover.hpp · addStatement`); the `mergeTwoEquivalenceClasses` `equality2` `(=[X,Y])` antecedents (L3 stage 2); `prepareIntegration`'s `goalOf` concat lambda for `base+"_integration_goal"` (explicit `sizeof-1` suffix length, `allocBytes` byte-bump so several spans coexist under one scope); the `u_`-stripped antecedents reusing `removeUPrefixScratch` (dropping the `.toStdString` heap copies); `str_ops.hpp · deduplicateBoundVarsScratch` (the `(>[...]` bound-var-list dedup — single-pass copy-or-remove into a worst-case `allocBytes(impl.len)` buffer since the output only shrinks, exact-length `wrap`, per-list dedup via a bounded stack `StrSpan seen[64]`; the deleted file-static heap `deduplicateBoundVars`'s oracle is kept TEST-LOCAL per the ce-twin survivorship rule). The S10 integration fresh-expression builders are the fullest example — `negateScratch` (slice-or-`prefixBang`), `stripUPrefixASTScratch` (`collectExprTokens` + `u_`-strip-slice `StrReplacement`), `reconstructImplicationForIntegrationScratch` / `expandSignatureForIntegrationScratch` / `buildIntegrationInstructionScratch` (arena category builds + the reused `reconstructImplicationFullBindScratch`), all mint-free, each byte-twin-tested against its retained heap oracle (`integration_builder_scratch_twins`); the J1 ruling makes the RESULT strings arena builds too, heap only AT the `addToHashMemory` boundary. `prover.cpp · expandSignature` is a whole-function example of the caller-owns-the-arena discipline: its AND / existence / implication / OR De-Morgan build plus the `u_`/`it_`/`int_`/`c_` renaming all ride the CALLER's string-tier arena with NO internal `ScratchScope`, so the returned span AND every intermediate `current` / `c_` byte survive into the two `disintegrateExprCore2` door sites (`addOriginEncoded` / `addRoutingMailOrigin`), whose interner mints never touch that arena (I-3). For a fresh value SET whose members must mint in decoded-lex order, `encodeValueSpanSetSorted` ([`memory.hpp`](../../GL_Quick_VS/GL_Quick/src/memory.hpp)) is the span twin of `encodeValueSetSorted` — dedup in a scratch `ColdHashSet`, `compareSpans`-sort, mint in that order (byte-identical id vector).

**Never `StrSpan(rawArray)` without an explicit length** — the #1 fresh-string trap (Pitfalls). The explicit-length discipline exists for exactly this.

## 5. Ordered consumption — the decoded-lex index

When a `std::set<std::string>` / `std::map<std::string,…>` / sorted `std::vector` had an OBSERVABLE iteration order — drain order, rule-firing order, interner mint order, dump/chapter order — the id-form replacement must REPRODUCE that order byte-for-byte. Interner ids are **mint order, not lex order** ([I-84](../30_invariants.md#i-84)), so you cannot iterate ids raw.

**Recipe.** A decoded-lex INDEX: allocate a contiguous `int32_t idx[n]` on the `genScratchArenas` byte-bump tier, fill `idx[k]=k`, `std::sort(idx, idx+n, cmp)` where `cmp` decodes each element's key(s) and compares with `compareSpans` (== `std::string::compare`, byte-lex). Iterate `idx` in place of the former sorted container. The sort does pure reads (no mint), so `decodeView` spans stay valid across the whole `std::sort` ([I-3](../30_invariants.md#i-3)).

```cpp
// Reproduce std::sort under ExpressionWithValidity::operator< over id rows.
const int32_t n = rows.size();
int32_t* idx = static_cast<int32_t*>(
    genArena.alloc(n * sizeof(int32_t), alignof(int32_t)));   // byte-bump tier
for (int32_t k = 0; k < n; ++k) idx[k] = k;
std::sort(idx, idx + n, [&](int32_t a, int32_t b) {
    const int c = compareSpans(nm.decodeView(rows[a].originalId),
                               nm.decodeView(rows[b].originalId));
    if (c != 0) return c < 0;                                 // primary: original
    return compareSpans(nm.decodeView(rows[a].validityId),
                        nm.decodeView(rows[b].validityId)) < 0; // tie: validity
});
// consume rows[idx[0..n)] — the former sorted order, byte-for-byte
```

Two crux precedents:

- **`sortStatementRows`** ([`memory.hpp`](../../GL_Quick_VS/GL_Quick/src/memory.hpp); the L5 foundation) — reproduces `std::sort` under `ExpressionWithValidity::operator<` from a `PagedVector<IntEncodedExpr>`: `compareSpans(decodeView(originalId))`, then on a tie `decodeView(validityId)`. Byte-identical because `IntEncodedExpr.originalId == nm.encode(original)` and `compareSpans == std::string::compare`. **`sortToBeProvedKeys`** ([`memory.hpp`](../../GL_Quick_VS/GL_Quick/src/memory.hpp)) is the same index for a MUTATE-DURING-WALK consumer: it returns the goal registry's PACKED KEYS (stable `int32_t` `packStatementKey` pairs on the arena byte-bump tier) in the identical `(original, validityName)` order, and the caller edge-materializes each row's two strings FRESH per key (09c pitfall 5) since `checkNecessityForEquality` mints and inserts/erases goals mid-walk — the packed keys survive because NameMap only appends. It replaces the owning `decodeToBeProvedSorted` in the tree (kept as the hashburst-dump helper + twin oracle).
- **`originLineLessId`** ([`memory.hpp`](../../GL_Quick_VS/GL_Quick/src/memory.hpp); the L8 S0 crux, a SEPARATE and later helper than `sortStatementRows`) — reproduces `OriginLine::operator<` = `std::pair<std::string, std::vector<ExpressionWithValidity>>::operator<` EXACTLY. **THE SUBTLETY:** the justification tag compares as a **STRING** — `compareSpans(originTagName(tag))` — **NOT** as the `OriginTag` enum order, which differs. Its unit test deliberately includes a tag whose string order disagrees with the enum order, so an enum-order regression fails the test. On a tag tie the antecedent vectors compare lexicographically under `EWV::operator<`, shorter-run-first (`std::vector::operator<` semantics). Getting this wrong changes the `.front` origin chosen per statement AND the `exprOriginMap` merge/cap outcome — both are verifier-walked process documentation (the project conventions).

**Keep a CROSS-ROW index even when the merge is per-key-independent.** L8 keeps a `decodedOriginKeyLess` cross-row index alongside the per-run one so the `originInterner` re-mint order matches the former EWV-key-sorted build byte-for-byte — full byte-identity INCLUDING the `.deload/` stream. Dropping it is a valid optimization only with explicit "byte-identity waivable" authorization; the default is to keep it. A single templated comparator serves both the per-LB `NameMap` id space and the global `mailInterner` space via the `mailIdView` dispatcher. The `.front` / `std::lower_bound` idiom becomes a **direct key lookup + min-scan** (min-of-run == front-of-sorted-run), no re-sort.

## Pitfalls

Each cost a gate cycle. Fix forward, never revert an incomplete arena rewrite (the project conventions).

1. **`StrSpan(rawCharArray)` without an explicit length — dangling temporary.** `StrSpan` has a `(const char*, int32_t)` ctor and a `(const std::string&)` ctor but NO bare `const char*` ctor, so `StrSpan(buf)` binds the `std::string` ctor, builds a temporary `std::string`, and the span dangles past the full expression. It masked a whole batch as a **Peano `isInt` divergence** ([`09b`](09b_statification_cookbook.md) pitfall 4). Always `StrSpan(buf, len)`; the fresh-string builder's explicit-length rule (Section 4) exists for this.
2. **A span held across a mint into its OWN interner** — the [I-3](../30_invariants.md#i-3) `decodeView`-vs-`copyFrom` bug (Section 1). The mint must be into the SAME interner to dangle; a mint into a DIFFERENT interner is safe. When unsure, `copyFrom`.
3. **String-tier vs page-tier arena confusion** ([I-124](../30_invariants.md#i-124)). A `ScratchString` rides `scratchArenas`; its decoded-lex index `int32_t[]` rides `genScratchArenas` byte-bump. Never a page `ColdHashSet` on the string arena (a `ScratchScope` rewind frees its pages); never raw byte-bump the string arena (it muddies the `ScratchString` liveness tripwire).
4. **The `ScratchString` liveness tripwire does NOT fire through a raw `StrSpan`** — a FUTURE-REGRESSION blind spot. `ScratchString` carries generation + cursor stamps that assert on escape ([`scratch_string.hpp`](../../GL_Quick_VS/GL_Quick/src/memory_infra/scratch_string.hpp) `assertLive`); a `StrSpan` built from it carries NONE ([I-116](../30_invariants.md#i-116) — a span has no lifetime machinery). So a `StrSpan` that outlives the `ScratchScope` of the `ScratchString` it aliases reads poisoned / refilled bytes with **no assert**. The contract is stack discipline: never let a `StrSpan` cross the rewind that reclaims its backing `ScratchString`. This is why fresh strings are held as NAMED `ScratchString` locals (stamped) and spanned only at the synchronous door call.
5. **The reused-per-drain-buffer edge for a `std::string`-owning door.** When a sink temporarily stays `std::string` (its door not yet converted, e.g. `addExprToMemoryBlock` before its L9 door, or the mail-absorb drain feeding it — L8 S1), the honest residual is a REUSED per-drain `std::string` (or per-row `ScratchString`) materialized from `decodeView` at the edge — materialize-at-the-edge, NOT an O(n) snapshot. A raw `decodeView` span would dangle at the door's mint, so it must be a fresh copy per row. Flag the residual explicitly; do not silently expand scope to statify the off-limits door (`prover.cpp · addExprToMemoryBlock` later retired those two reused buffers once the door itself went span-native).

## Verifying a string conversion

- **Per function — the CodeQL inventory row is the objective gate.** Not done until `statification/inventory.md` shows the function `true` (or gone from the `standardProcessing` tree) after a full Tier-1 regeneration (a Python-only Tier-2 rerun reflects no source change). No other row may flip `true→false`. Never edit the inventory generator to move the bar — verifier-class.
- **Per commit — the differential twin.** Every span door / builder / comparator ships a Rule-18 byte-twin unit test: build the artifact BOTH ways — the retained `std::string` / `OriginLine` / `EncodedExpression` / `std::sort` **oracle** (deliberately KEPT even after the span path replaces it in production) vs the span/id form — and assert byte-identical state. The pattern is pervasive: `canonicalize_under_classes_subst_twin` (test_str_ops.cpp), `encode_origin_spans_twin` / `add_origin_encoded_cold_spans_twin`, `internal_mail_statement_span_door_twin` / `internal_mail_origin_span_door_twin`, `sort_statement_rows_matches_std_sort_ewv`, `origin_line_less_id_matches_std_sort_originline` (with the tag string-vs-enum-order disagreement case), `namemap_strict_ancestor_names_span_matches_string`, `encode_value_span_set_sorted_byte_identical` (test_memory.cpp), `classify_or_scope_view_twin` (test_str_ops.cpp). Per-commit gate = build-clean + `gl_quick.exe --unit-tests` green.
- **Whole-hook conversions have no standalone twin.** The 300-line apply\* / discharge hooks mutate admission / rejected / levels maps + interners + mails, so no single byte-twin is feasible — the reusable PRIMITIVES carry the twins, and whole-hook byte-identity is proved only by the batch gate. Signature-preserving span-door swaps carry no NEW test surface; they ride the door's existing twin.
- **Batch gate — ONE `main.py` + `verifier.py`.** After a batch lands: `theorems.txt` and ALL proof artifacts BYTE-IDENTICAL to the pre-branch baseline (`git status files/` clean), verifier 0 failures across every tag, Gauss summation present, no pool-exhaustion assert. Byte-identity by construction is the design contract; the ONLY string-conversion divergence tolerated is a mint-order reorder (a documented determinism fix, gated separately) — which the Section-5 cross-row index deliberately AVOIDS, so string batches gate on strict byte-identity. Multi-commit refactors build-only per intermediate commit and run the full gate ONCE after all land, bisecting on failure.
- **The two proof levels.** The per-commit differential twin is the byte-proof for each door / builder / comparator; the full-pipeline `main.py` + `git status files/` run is the definitive byte-identity gate that proves the whole batch.
