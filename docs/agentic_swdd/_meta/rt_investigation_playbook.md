> **Agent-oriented documentation.** This document is written for AI agents working with the GL codebase. Human readers: see the [paper](https://arxiv.org/abs/2508.00017) and the [README](../../../README.md). The document is intentionally dense, cross-linked, and weakness-explicit — agents thrive on that, humans usually don't.


# Runtime investigation playbook

Use this workflow when a restored lemma or other requested workload may crash or cause a runtime explosion. Diagnosis does not authorize a fix. Keep the task's existing root `ledger/` record current; its latest approval boundary governs implementation.

## Establish a comparable reference

1. Record the exact branch, commit, worktree, supplied statements, configuration, native/build inputs and executable fingerprint. Preserve the current input before restoring the requested lemma. Restore only that lemma; preserve the other statements and their order.
2. Prefer the newest completed dump-free run whose code, executable and workload match the current pre-change state. Verify its completion and fingerprints. A saved run remains a saved observation, not a new measurement. Document verified line-ending differences separately from content changes. If no comparable reference exists, obtain a baseline run before interpreting the candidate.
3. Use an isolated Windows worktree and the current repository execution protocol. Claim the shared slot through its conforming controller before builds, tests or runs; an empty queue is not a lock. If the controller is unavailable, report it and complete independent preparation without starting execution. Never kill another owner's process.
4. Reuse a matching executable only when all native input/output paths resolve to the intended worktree. Current `project_paths.cpp`, `projectRoot`, derives that root from the deployed executable and is covered by a relocation regression. Older executables derive paths from compiled `__FILE__` and cannot safely be copied across checkout paths even when their source hash matches. Rebuild these at the intended path or use a validated relocatable binary. Native source, headers or build-input changes require the prescribed normalized Windows `MSBuild -t:Rebuild`; input/configuration/Python/documentation-only changes with an appropriately located matching binary do not themselves require rebuilding.

## Measure without dump overhead

1. Check that every sacred `isTargetLB` branch has an impossible innermost key and retains its complete parent chain. Retarget only the matcher; preserve dump format, sections, sinks and calls. Confirm zero trace bytes in the completed reference and candidate.
2. A changed supplied conjecture needs `main.py --GPU` to regenerate the full input capture. A subsequent diagnostic may use `main.py --shortcut --GPU` only after its normal fingerprint gate accepts the matching capture. Never invoke the native prover directly to reproduce a pipeline crash.
3. Use a unique descriptor, dedicated logs and one completion-driven watcher. Follow the shared primary checkout's Rule 29 transport protocol: retain a persistent native helper/session across tool timeouts, subscribe before checking the unique completion file and reconnect to that same event wait. An in-process watcher that dies with its tool call cannot promise later notification. Do not poll processes or logs unless the maintainer explicitly requests monitoring. Preserve executable/input/code fingerprints before and after, pipeline/native exit status, completion record, diagnostics, `.rt` files, trap file and all available matching registries/proof artifacts. The controller keeps ownership through all pipeline children and releases on success or failure; retries rejoin the queue.
4. Report full wrapper elapsed time, each affected batch's `Runtime prover`, summed batch prover time, phase-barrier wall time, exclusive worker-seconds, available processor/GPU work counters and peak memory separately. Do not interpret worker-seconds as elapsed time or operating-system processor execution time.
5. Compare the requested added-lemma workload against the unchanged reference. State explicitly that the workload changed. Show affected-batch ratios even if an all-batch total looks acceptable. Use the task's existing investigation signal; for the F3 restart it is 125 percent. Do not invent an automatic stop rule or lower a threshold to pass.

## If it crashes

Preserve the failed executable, inputs, available graphs, compiled registries, logs, runtime data and exact assertion/exception. Record the last completed stage and the incomplete stage. Locate the failure in current source and reconstruct the complete owning logic-block chain. Do not infer that the block with the last log line caused the failure without evidence. Read existing evidence first; if another run is necessary, reproduce through the same pipeline and unchanged assertion. The sacred full-chain dump is the first logic-block instrument; any necessary temporary trap uses . Retain and disclose diagnostic instrumentation when the task ends without an approved fix.

Report what violated the contract, the supporting statements/scopes and the remaining uncertainty. A failed run has no completed batch time; a long last burst is evidence about that burst, not a completed runtime ratio. Propose repairs separately and await explicit approval before changing behavior.

## If runtime explodes

1. Rank the completed run's `[RT-LB]` records by summed time for each exact full parent chain and show phase 1, 2 and 3 separately. Also identify the longest individual call/burst. Aggregate labels describe whole-batch call trees; a per-block `.rt` snapshot can be overwritten by a later call or phase and cannot establish a run total. On CUDA, keep device and finalization timing separate from processor tracker rows.
2. Reconcile the slowest chain's phase totals with `.rt/_aggregate_<tag>.log` and the phase-barrier wall lines. Dissect the expensive phase into exclusive section time and call/work counts. An inclusive function total equals its exclusive row plus descendants; overlapping inclusive totals must never be added. The `wall~s` column is a uniform-parallelism estimate, not a measured per-function wall duration. For one block's per-call split, run dump-free with `GL_RT_AUDIT_CHAIN` set to the block's chain exactly as its `[RT-LB]` row prints it (no rebuild, no matcher edit; rows in , rendered by `.scripts/rt_audit_tree.py`, optionally restricted to a burst range). Take section splits only from such a dump-free run: the dump inflates the tracked sections of its block about 2.5 times, and `GL_FTA_BLOWUP_TRACE`'s admission observers inflate implication installs further, so a dump run's sections serve only for proportions and counts.
3. Derive the selected block's complete `parentMemory` chain from current creation sites, including the empty-key/null-parent root. Routing keys can differ from `exprKey`; match the latter. Retarget the sacred matcher to that exact chain, rebuild for the matcher change and obtain a separate diagnostic run. Preserve the fixed dump immediately under the run descriptor. Dump time is excluded from the reference and regression ratios.
4. **Dump a reference block as well.** An anomaly is visible only against a known normal. From the same ranking choose a reference block that is much faster than the slowest block (it need not be near the average) but still does comparably complicated proof work: same batch, similar goal and premise shape, and the same kinds of activity (induction, integration witnesses, OR cases, equality classes, subproofs). Record why it was chosen. In a separate diagnostic run, retarget the sacred matcher at its complete chain, replacing the slowest block's target; never dump two blocks in one run. For a block of the last batch the shortcut run is allowed once the full capture exists. Dissect it like the slowest block (per-section split, per-burst frames), then read both dumps side by side. For each quantity where the slowest block stands out (statements, origins, scopes, classes, OR cohorts, goals, admission and rejection keys, mail volume, section time per unit of work), give the reference block's value. Work that both blocks do in proportion is normal; work that only the slowest block does, or does far out of proportion, is the anomaly candidate for the steps below.
5. Index ENTRY/EXIT frames and correlate burst numbers with runtime. Inspect the implicated structures and scopes: goals, known/encoded statements, equality classes and canonical identities, admission/rejection keys and values, compiled rules, parked sources, OR bookkeeping, mail and origin history. Decode numbered predicates against that run's own registry. Never combine facts from sibling scopes.
6. Look for repeated no-op maintenance, oscillating canonical forms, duplicated witness/rule/source growth, repeated admission/rejection replay, stale scope ownership, disproportionate key/index expansion, repeated equality work and work that persists after its goals close. Quantify any anomaly by frame/section/chain, retained versus new objects and the source loop or predicate responsible. These are investigation questions, not presumed causes.
7. Distinguish raw application classes, derived complete canonical classes and empty scope buckets when counting equality state. Count no-op selections separately from selected records and unique facts. A stale snapshot is a last observation, not a final duration. Extra timers or printing can change overhead and how far a bounded diagnostic advances; do not call an observed loop the cause of an earlier unobserved interval without matching evidence.
8. A large count or mostly empty selection result does not explain a still-unobserved long interval. Read the full enclosing timed source block: one label may include several sequential functions. If snapshots stop refreshing, obtain actual native worker stacks with the exact block chain and matching symbols, then quantify the implicated queue and candidate product from preserved state. Distinguish duplicate `(source, scope)` events from distinct source-to-descendant expansion, and static candidate opportunities from executed calls. Preserve progress samples to distinguish slow finite work from a proved cycle; do not end the investigation merely because a plausible anomaly was found.
9. Report the measured slowest chain, runtime breakdown, specific dump evidence, source-grounded mechanism and open hypotheses. Separate diagnostic I/O from logical work. Suggest bounded fixes with acceptance criteria; implement only after the maintainer approves them.

## Preserve the outcome

Check the exact restored supplied statement in native theorem output, then its processed certificate/connected Lean disposition if the full run reaches them. Pipeline exit zero and unchanged theorem counts do not establish that this lemma is proved. Preserve old theorem sets and proof evidence; counts alone do not show equivalence. Record the result, evidence paths, pending approvals and exact next action in the existing task ledger, then commit and push the coherent requested-input/documentation milestone under the repository rules.

See [runtime instrumentation](rt_measurement.md) for timer semantics, [the prover](../10_pipeline/04_prover.md) for block ownership and [the MPL cookbook](../03b_mpl_cookbook.md) for supplied-input and full-capture requirements.
