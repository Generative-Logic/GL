Generative Logic · Hardware track

MPU 0.1 — The Mathematical Processing Unit

Mapping today's Generative Logic onto silicon — what the machine actually is in hardware terms, and an estimate of what it would cost to build. The lineage is CPU → GPU → TPU → MPU: a processor whose native workload is not arithmetic, not graphics, not tensors, but deductive inference.

Version 0.1 — a starting point to build on, not a finished part. Sizing from the live prover; prices dated, refreshed only at release.

This is a record of where GL-on-silicon stands today, written for the engineer who would build it — not a pitch. Every number comes from the running system or is flagged as a rough, dated estimate; the problems are stated as plainly as the wins.

The whole argument, on one page

A proof engine has exactly two ways to run out of road. It runs out of memory — the state of a hard problem no longer fits — or it runs out of time — there are more deductions to make than one machine can make before you lose patience. The MPU is the claim that both ceilings are now architectural, not fundamental, because the GL prover was rebuilt into a shape that lifts them:

The MPU is a force multiplier, not a product on its own. Put the value as:
value  =  (1 + N)  ×  (does GL do real math?)
GL on its own is the 1 — it runs today, without any of this. The MPU adds the N: the same engine, accelerated. So the ASIC is not make-or-break for GL; it takes a working engine from 1 to 1 + N. Both terms are gated by the second factor: if GL cannot do real mathematics the whole thing is zero, and the Fundamental Theorem of Arithmetic (FTA) campaign is the test that decides it. This document estimates N and says nothing about the second factor; that one is settled in proofs, not here.
One commitment up front — no surprises later The cores' working memory is SRAM — many small macros, one per 256 KiB block (block == SRAM). Each block has its own port, so thousands of concurrent accesses run at the same time and access bandwidth scales with core count. And the SRAM need not hold the whole multi-GB working set: deload streams blocks between SRAM and SSD in the background (§3), so the SRAM holds only the resident window the cores are working on — drastically smaller than the working set, and a tunable knob. That is the whole point of building deload: decouple SRAM size from problem size. SSD is the bulk tier (virtually unlimited), streamed and prefetched — never the cores' random-access path. Cheapness is not the goal; being alive is — and a small-window all-SRAM design is alive and affordable.
Why this is the right time to map it The recently-completed statification campaign moved all per-block prover memory into fixed pools with virtual-offset addressing, a working-set pager, and a two-format SSD deload path (a byte-identical canonical format for archival images, a near-memcpy raw format for the eviction hot loop). It was undertaken for the Fundamental Theorem of Arithmetic campaign — the next milestone — whose memory and runtime demands exceed those of prior work and require a bounded, fixed-size memory model. That model is, by construction, what a dedicated GL processor also requires: a memory hierarchy, single-level address translation (an MMU), and a cache controller. The two needs are the same steps, taken once and combined — the software the FTA campaign requires and the data layout silicon requires coincide. Since then a second campaign statified the transient side as well: every working structure inside the proof kernel — string scratch, admission and rejection state, equivalence-class processing, origin records, the disintegration and integration working forms, the mail absorb — now runs on the same virtual-offset substrate, and the result is compiler-verified: a semantic call-graph inventory over the built binaries shows zero heap-using functions on the kernel's compute paths. Removing the allocator traffic alone made the software ~13% faster on the regression workload — before any silicon. MPU 0.1 is therefore a transcription of the running system rather than a forward proposal: the design already runs, in software, on the machine you have. It is a starting point to build and iterate on, not a finished part.

1 · What GL computes, in hardware terms

Forget theorem-proving for a moment and look at the workload as a hardware engineer would. GL is a machine that does one thing in a tight loop: it takes known facts, looks up rules whose pattern they match, and writes down whatever those rules conclude — then repeats until nothing new appears. Crucially, the match step is a hash lookup, not a search: every rule is stored under the signature of the premise it needs, every fact under its own structural signature, so "does any rule fire on what I know?" is answered by indexing a table, not by exploring a tree. Inference is a memory-access problem.

That single design choice fixes the datapath, and the datapath is friendly:

32-bit
symbol & scope ids (the working width). 64-bit packed statement keys; 64-bit hash digests.
0
floating-point operations on the proof path. None. (The whole prover has one FP compare, and it only picks how to split work.)
352 B
one statement line (IntEncodedExpr) — a fixed, all-int32 record. The natural SRAM line / register width.
FNV-1a
the hash — a per-byte XOR-then-multiply. A few gates, one pipelined multiplier.

A statement line is a fixed-capacity record: a name id, a handful of flags, and up to 16 arguments (MAX_ARITY), each a 32-bit id — all int32, 176 bytes, identical shape for every fact in the system. A hash key holds up to 8 sub-expressions of those. There are no variable-length structures and no pointers in the hot record: the engine compares ids, tests set membership and subset, looks up a packed key, and folds an FNV-1a digest. That is the entire arithmetic vocabulary of the inner loop. No multiplier array, no FPU, no transcendental units — the silicon a TPU spends on matrix math, the MPU does not need at all.

Determinism is the feature, not a footnote

GL is fully deterministic: the same inputs produce byte-identical outputs across runs, across thread counts, and across machines. This is enforced as a project-wide doctrine — every cross-run or cross-host deviation is treated as a bug — with physical addresses and parallel scheduling order never observable in the outputs. It survives all the way down to the archival on-disk deload images, which are a pure function of logical content (element order in, bytes out). The eviction hot-loop images are the one deliberate exception — a fast raw memory copy whose bytes are not reproducible but whose restored state is, so the proof output (which depends only on the state) stays byte-identical.

Why a hardware designer should care Determinism without floating point removes the single hardest thing about parallel accelerators: reproducibility. There is no FP-rounding skew to reconcile across lanes, no run-to-run drift to chase. A result computed on one core, a thousand cores, or a farm of chips is bit-identical, so the external verifier can re-check any proof exactly, and a multi-chip run needs no consensus protocol to agree on an answer — they cannot disagree. For an ASIC this is worth a great deal: validation, replay, and scale-out all get simpler at once.

2 · The Logic Block = one core

The unit of execution in GL is the Logic Block (LB). An LB is a self-contained reasoning context: it owns its own hash rules, its own known statements, its own scope/validity stack, its own equivalence classes and provenance map, and its own mailboxes. LBs never reach into each other's memory; the main thing that crosses between them is mail. The remaining cross-block effects — induction activation, deferred ancestor admissions, global-rule updates — travel through analyzer-level deferred-action collectors drained single-threaded at the cycle boundary, off the parallel hashburst rather than through any shared-memory access during it. One LB maps to one core. A GL run is a tree of LBs (a goal spawns sub-blocks for hypotheses, case splits, induction), and the prover sweeps the whole active set each cycle. MPU 0.1 is built with 32 LB cores — a one-to-one map of the 32 logical cores GL runs on today. We map what we have: the ~1,757 active LBs of a heavy batch (IncubatorPeano1 — the booklet's own measured peak, appendix A; not reproduced from a committed run log) stream through those 32 cores 32-at-a-time, just as they do across 32 CPU threads now, with deload (§3) paging the rest.

The elementary step — what the engine does each cycle

The engine's job is "fire every rule that can fire on what is currently known, once." Concretely, per cycle it generates requests (candidate premise-patterns assembled from known statements), looks each up in the rule table by its FNV key, and for every hit binds the rule's variables, checks an admission gate, builds the conclusion, and emits a firing record. The lookup is O(1) amortised and there is no backtracking on the step itself — the breadth comes from many LBs firing in the same cycle and exchanging results through mail at the cycle boundary. In silicon terms it is a streaming match-and-emit pipeline over a hash table, not a recursive search machine.

Three phases, and why the split matters for hardware

  • Phase 1 — absorb. Pull mail from ancestors, fold it into local rules and facts so this cycle's request generation sees it. A goal that mail just closed can deactivate the block here.
  • Phase 2 — hashburst. The compute-heavy part, and strictly read-only on the block. It captures firings as records and mutates nothing shared. This is the property that lets phase 2 run on many compute units at once (§5) and is the hard contract behind the runtime lever.
  • Phase 3 — commit. Single-threaded per block. The captured firings are merged and applied first — concatenated and sorted into a canonical order (so the result is independent of how phase 2 was parallelised) in a per-block finalize the moment the parallel units join, at the tail of phase 2; commit proper then flushes mail, discharges/deactivates finished goals, sanitises, and wipes closed scopes.

The read-only phase 2 is the linchpin. Because the heavy work touches no shared state, you can throw cores at it freely and merge deterministically afterwards — which is exactly what §5 turns into the runtime lever.

3 · LB memory & its management

This is the part of GL that was rebuilt to be silicon-ready, so it is the part a hardware reader should study most. Essentially all of the prover's per-LB working state — every per-LB payload and the whole mail system — now lives inside fixed reservations made once at start-up, never grown, never freed during the run (the bounded exceptions are in the note below). There is no malloc in the hot path; exhaustion is a loud assert that names the knob to raise, never a silent fallback. Four reservations, each a candidate for a physical memory bank:

PoolSize (provisioned)BlockBacksDeloads to SSD?
Main12 GiB256 KiBall per-LB working containers (the bump arena)yes
Persistent1 GiB32 KiBthe goal registry — kept always-resident so deactivation logic can read it while a block is coldno
Mail2 GiB256 KiBthe cross-block mail log (who sent what to whom)no
LB-body2 GiB256 KiBthe block objects themselves (fixed slots, never moved)no

Total program-start reservation: 17 GiB, fixed. These are ceilings, not consumption — the sizing knob you would tune for a real part is the measured peak, which §7 puts (from the booklet's own dated figures) at roughly 1 GB for the named theorem batches and ~4–5 GB for the heaviest exploration batch. The "provisioned vs. measured" gap is the whole reason the cost story has a hot tier and a cold tier.

The hierarchy is pool → block → page → per-LB arena

The virtual-offset arena is a tiny per-LB MMU

Containers never store a physical address. They store a 32-bit virtual offset, and a resolve step turns it into a pointer on every access: 

physical = blocks[ offset >> 18 ] + ( offset & 0x3FFFF )
                       └ which SRAM macro ┘  └ address within that 256 KiB SRAM ┘

One shift, one mask, one add — because the block size is a power of two. This is exactly an MMU's page-table-walk collapsed to a single level, and it buys two things at once: determinism (the offset is a pure function of allocation order, so nothing observable depends on which physical block the data landed in) and relocatability (a block can be written to disk and reloaded anywhere without rewriting a single stored offset). In hardware this is a small adder and a register holding the block-base table — cheap, and replicated per core.

And in the MPU each block is one small SRAM macro — block == SRAM. The resolve above is a (macro-select, intra-macro-address) decode. The cores random-access only these macros, and because each block has its own port, accesses to different blocks happen at the same time — that concurrency, scaling with core count, is the whole basis of the runtime lever (§5). And the SRAM holds only the resident window: the pager (below) keeps the macros the cores are working on, and deload streams the rest from SSD, so the physical SRAM is far smaller than the 4 GiB pool — the working set lives on SSD; the SRAM is just the hot window.

One core addresses many macros, and the count flexes with the problem. A core's arena is not a single fixed SRAM — it spans as many 256 KiB macros as its LB currently needs, and the resolve's macro-select field picks among them. Macros are granted on demand (acquireBlock) as an LB grows and returned when it shrinks or discharges, so a trivial LB holds one or two while a fat one (the heavy Gauss blocks reach ~13 MiB ≈ dozens of macros) holds many. The macros are a shared pool the steward apportions across the 32 cores by live demand — so the SRAM-per-core adjusts to problem complexity dynamically, rather than a fixed per-core partition. One core handles trivial and hard problems alike; it just draws more macros for the hard ones.

The pager is a cache controller

RAM is treated as a cache of the working set — the blocks being processed now plus the next few. A background steward thread maintains that window every cycle: it prefetches the blocks about to be needed and, when memory gets tight, evicts the rest to SSD, biggest first. A worker that reaches a block still on disk loads it itself and deloads the biggest out-of-window block in exchange. The policy is pure watermarks on pool occupancy:

  • Below 50% full — the steward is parked. No eviction, so no reload. A light batch runs at full speed with zero disk traffic.
  • Cross 50% — the steward wakes (asynchronously) and drains: each reload is paid for by evicting the biggest out-of-window block (one-for-one), pulling occupancy down to a 40% floor before it parks again. The 50%→40% gap is a hysteresis band, so it never oscillates at the wake mark.
  • Above ¾ (75%) — the synchronous hard water: a worker that needs a block while the pool is this full does the swap itself — load its block, evict the biggest out-of-window block — rather than wait for the steward, which above this mark mass-evicts.
  • Working set itself won't fit — that is a genuinely too-small pool, and the run stops at a loud assert. A 30-second stuck-detector turns any unexpected wait into an assert too.

For the MPU this is the cache controller between the SRAM hot tier and the SSD cold tier. The eviction timing can vary with load, but — by construction — the proof output never does: what to discharge is decided at a single-threaded barrier from deterministic block state, and the pager only moves bytes, never changes them.

SSD deload / reload is the cold tier

Blocks move to and from SSD in two formats, chosen by purpose. The eviction hot loop — the pager cycling live blocks in and out under memory pressure — uses a raw arena image: a near-memcpy byte copy of the block's live memory pages plus a small map of which pages are live. Because every container (including its throw-away hash index) packs its pages into the one block arena, and the tiny per-container bookkeeping lives in the never-evicted block shell, the page image is a complete record: reload binds the same page ids to freshly-packed pages and reads the bytes straight back — no element walk, no index rebuild, one copy. This is what makes the cold-tier stream run at memory-copy bandwidth, which the block-granular datapath (and the optional DRAM L2 below) is sized for. The price, accepted deliberately: raw image bytes are not reproducible (fragmentation leaks into them), so they are not byte-comparable — but the restored logical state is identical, which is all the proof output depends on.

The discharge / archival path (a block that leaves the working set for good, and the read-only proof-export reloads) instead uses the canonical format: containers streamed element by element, in logical order. Its byte stream is a pure function of logical content — two blocks with the same contents produce identical files regardless of fragmentation, so these images ARE byte-comparable across runs and machines. The format is self-describing (a GLDL magic, a version, a per-block ordinal as the filename, a per-tag directory, the block's full identity chain verbatim, then fixed-width little-endian payload). Reload rebuilds the containers onto a fresh, compact arena and is allowed only at a handful of enumerated touch points; touching cold storage anywhere else is an assert, not a degraded read. This SSD cold tier is the lever that makes memory virtually unlimited: an SSD is cheap and enormous.

Optional, not in the current design: a DRAM L2. The current design is two tiers — SRAM (L1), the cores' working window, and SSD (L3), the cold backing store. A DRAM L2 could sit between them as a deload-staging cache: the steward pre-uploads the next blocks from SSD into DRAM and parks just-deloaded blocks there before they trickle out to SSD, hiding SSD latency on the streaming path. It would be block-granular and off the cores' random-access path — staging whole 256 KiB blocks as they move between SRAM and SSD, never serving a core's random access. A future option; MPU 0.1 is SRAMs + SSD.

What is not static — the complete accounting

Stated plainly The first campaign moved all per-LB persistent state — including the mail system — into the static pools; the second statified the kernel's transient scratch: each worker's working memory is two per-worker arenas drawn from the same pool and released whole at the end of each task, so a core's scratch is a fixed, enumerable SRAM budget, not an open-ended allocator. Mail is static: the cross-block log, global ids, and transient inboxes live on the dedicated mail pool; each outbox, its private interner, and the internal channels live on the LB's deloadable main-pool arena (§4). None is on the malloc heap. Within the block-memory subsystem, two things genuinely remain on the ordinary heap:
  • The global pool's recycle queue — one process-wide root that hands out blocks — and the compaction's transient scratch. O(blocks), not O(payload), and outside any one LB. (Each arena's own list of which blocks/pages it holds — once the last per-LB heap carve-out — is now pool-backed: a small-buffer directory that keeps a tiny arena's table inline at zero pool cost and spills only a large one onto pool blocks. So the per-LB arena bookkeeping is now static too.)
  • Transient mail strings — each deloadable outbox stores int32 ids from its own private interner; commit translates them into global mail-interner int32 ids for the retained log and receiver inbox. The persistent log bytes are static; the absorb/pull side now decodes the frozen blob bytes straight into the receiving block's static columns with no heap working form at all. What still touches the heap is the short-lived encoding at the single-threaded commit and load seams — a bounded, per-cycle residue off the parallel compute path.
What this means for silicon. The persistent state — payloads, mail, and the per-LB arena bookkeeping — is static, and the per-worker working scratch is itself drawn from the statified pool and returned per task; the only ordinary read/write heap a host process keeps is the global pool's recycle queue, the compaction's transient scratch, and a staging area for mail serialisation at the single-threaded seams. The heap residue is bounded and per-cycle, not per-LB growth — so "mail is on the heap" would be wrong; only its transient encoding is. (In the proof kernel — performElem1/2/3 — the ONLY heap permitted is generating the hashburst_trace.txt debug dump, which is off the compute path and not silicon-mapped; the kernel's production paths are compiler-verified heap-free. The compiled-definition (config) layer remains the one data-on-heap residual — read through zero-allocation probes during the burst, and on silicon that layer is ROM. So the precise claim is "the kernel's compute paths are heap-free; the config layer is heap-resident data behind static read fences; transient heap encoding survives only at the single-threaded commit and load seams," not "zero heap process-wide.")

4 · The mail system — a pull over shared RAM (the tree is logical)

LBs do not share working memory; they exchange results through mail at cycle boundaries, and mail is, logically, a tree: a block reads only mail authored by its direct ancestors (parent, grandparent, …, root) — never a sibling, never upward, never an unrelated subtree. That tree is a software access pattern, not a connectivity property of the silicon: it does not make the interconnect any sparser.

Physically, mail is random-access reads into a shared log pool: a receiver reads its ancestors' logs at arbitrary addresses, and the interconnect must be able to reach every address — because the LB tree is built at run time (blocks spawn as goals split), each log lands at an unpredictable address (blocks are granted in nondeterministic order under the pool mutex, so different LBs' batches interleave anywhere in the pool), and the root, as everyone's ancestor, is read by all. Connectivity cannot be narrowed to a graph that does not exist until run time and whose logs sit at unpredictable addresses. The tree only bounds which cells a given receiver touches, not what the hardware must address — it is random access either way.

The mux is a pull over retained log windows

Concretely: each block writes the mail it emits once, into its own retained chain, at a single-threaded commit point each cycle. A receiver, in its phase 1, walks its ancestor list and pulls the batches it has not yet ingested from each ancestor's log, advancing a private per-(receiver, ancestor) cursor. There is no outbound copy and no shared inbox to contend on — the parallel readers only read frozen logs and bump their own cursor cells. That is the mux: select-and-merge at the receiver — but the selection is by memory address (which ancestor logs to read), over a shared pool the core can address in full.

Retention is chosen once when the run-time LB grid is complete. If every block is active, the post-phase-3 barrier recycles the delivered blob/reference pages before resetting the matching global mail-id table and opening a fresh window at the next commit. If any block is born dormant, the complete history and id table remain so that block can catch up when activated. In both modes the ancestor routing edges, cumulative producer counts, and receiver cursors stay in always-on RAM. For silicon this turns the common incubator case into a bounded rolling mail working set without changing the provisioned pool, address fabric, or mail protocol.

Three mail channels — which SRAM is always-on

This split tells you exactly which memory must stay powered and resident:

ChannelHomeAlways-on?
routing inbox (mailIn)the mail poolyes until phase-1 absorb; blocks then returned
routing outbox + private ids (mailOut)the block's main-pool arenano — deloads after phase 3; pending blocks reload one at a time for commit
cross-block retained window + global id table (the mux)dedicated mail poolyes — never deloaded; both may be recycled at the safe seam
internal one-step channelsthe block's deloadable arenano — pages out with the block

A mail message carries proved statements (including compact rule forms) plus provenance lines; on large batches provenance dominates. There is exactly one cross-block path that is not the ancestor pull — a point-to-point deposit addressed from the root to one tree node — and effects that travel up the tree are not mail at all (single-threaded collectors drained after the join). Net for the floorplan: an any-to-any memory interconnect to the shared pools, plus a small always-on mail SRAM — not a crossbar of message links, but not a sparse tree either. What the tree does buy is access locality (a receiver reads only its ancestor chain, not all N logs); what it does not buy is cheaper wiring. In this shared-memory model the real scaling limit is memory bandwidth and contention on hot cells (the root log, the shared pools), not interconnect topology — the caveat §5 and §7 carry into the runtime lever.

The mux, in hardware: a banked crossbar

That any-to-any memory access is a standard banked crossbar (a network-on-chip at larger scale): the SRAM macros are independent banks, and an N-port crossbar lets all 32 cores reach memory in parallel as long as they hit different banks; two cores hitting the same bank serialize — a bank conflict. This is not exotic — it is exactly how GPU shared memory works (32 banks; a warp's lanes run in one transaction unless they collide on a bank, where an n-way conflict serialises into n). The hot cells of §5 (the root mail log, read by every block) are that bank-conflict case by another name.

It exists off the shelf as IP, not a discrete chip. On the FPGA prototype you drop in a configurable non-blocking crossbar — e.g. AMD/Xilinx LogiCORE IP AXI SmartConnect (product guide PG247); for the ASIC, a mesh NoC such as Arm CoreLink CMN-700 or Arteris FlexNoC. A fully non-blocking crossbar costs ~O(N×M) area — trivial at 32 ports (GPU territory); at thousands of macros you group them into banks or move to the NoC, which trades the guaranteed-parallel crossbar for near-parallel routing with occasional internal blocking.

5 · LB split = scaling runtime across cores

This is the runtime lever. Before the static rebuild, a hard calculation lived inside a single block (or a couple) and ran at the speed of one thread — the work of one LB's hashburst was a sequential lump. LB split breaks that lump across cores: because phase 2 is read-only on the block (§2), the candidate-firing work can be partitioned, run on many compute units at once, and merged deterministically. A heavy LB is partitioned by expression search, not by rule owner: one read-only producer enumerates expression stumps over the whole LB, deals them into at most one bucket per logical core, and each bucket accepts every rule while generating only requests that contain one of its stumps. A block therefore spreads across min(expression buckets, cores available). The larger headroom belongs to the whole workload's flat task pool across all active blocks, not to a single block.

The expression partition matters for silicon because it divides one irregular search without adding a block-memory write port. A recordable short combination that would disappear when the producer advances to a larger level is retained as a terminal pre-stump: one bucket validates that combination through the normal request path but does not grow it, while the larger child stumps cover all larger combinations. No valid request is discarded.

The user named two ways to realise this in silicon. Both already exist in the software, in two different subsystems:

Why the merge is a sort, and why that matters

In model (a) the units do not deposit their firings as they go; each writes its own record list, and a single-threaded per-block finalize step — the tail of phase 2, once the parallel units join — concatenates and sorts them by a total content key before applying. The sort is the whole trick: it makes the merged result a function of content, not of which unit found what first or how many units there were. So 2 cores and 200 cores produce byte-identical output — the runtime lever costs you nothing in reproducibility. (And because phase 2 wrote nothing to the block, bucket tasks may execute in any order with no partial state to clean up.)

How much it splits, adaptively

Every main-path burst runs to completion. At the end of an iteration, GL compares each LB's deterministic total submatch work with the balanced per-core share and a minimum setup threshold. A straggler is pre-split for the next iteration into up to logicalCores expression buckets; an LB that falls below the threshold returns to one part. A newly activated induction-zero LB takes the split path once immediately because no prior statistic exists. This spends parallelism where the completed work shows it can shorten the makespan, without a timing-dependent trigger. MPU 0.1 maps the current host's approximately 32 logical workers to 32 LB cores; more independent LBs and expression buckets remain queued in the flat phase-2 pool.

What feeds the cores — and the residual ceiling Cores are cheap; feeding them is the hard part. Every core does random accesses into the shared memory (§4), so the lever only works if the memory can serve thousands of those at once. That is precisely why the memory is many small SRAM macros, one per block (§7.1): each block is its own port, so aggregate bandwidth scales with core count. The residual limit is not raw bandwidth but a few hot cells (above all the root mail log, read by every block) plus the serial fractions (phase 3, the per-cycle mail barrier). So scaling is sub-linear, but the parallel phase-2 fraction — almost all the work — is what the SRAM fabric is built to feed.

6 · The MPU floorplan

Put the pieces together and the chip draws itself. The MPU is a fabric of 32 LB cores (§2) over an any-to-any memory network-on-chip to the shared RAM pools (§4); the resident window of the working set lives in SRAM — many small macros, one per block (§3) — the full multi-GB working set is far larger and streams from SSD — with a steward / cache controller paging blocks between the SRAM fabric and an SSD cold tier (§3), under a thin host interface that loads axioms and streams proofs out. Split (§5) is realised by giving each core several phase-2 compute lanes and/or by cloning a core's state across the fabric.

7 · Cost estimation

Here is the money. Two ground rules first. One: the numbers below are order-of-magnitude, dated, and concentrated in the constants appendix so they can be refreshed at release without touching the prose. Two: this section prices the N in value = (1 + N) × (is GL real?). It does not argue the second factor — that is what the FTA campaign is for. If GL is not real math automation, every dollar below buys nothing. If it is, every dollar buys a multiplier.

The cost has two axes and they are wildly unequal:

  • Memory dominates. GL's working set today is gigabytes (§3). Holding and moving that is essentially the entire cost.
  • Compute is nearly free by comparison. An LB core is an integer match-and-emit pipeline with an FNV unit and no FPU (§1–2). Cores are small; you can afford a great many of them.

7.1 · Memory — the cost driver: many small SRAMs

The measured peak working set (full pipeline) is ~1 GB for the named theorem batches and ~4–5 GB for the heaviest exploration batch — but that is what lives on SSD, not what must be in SRAM. The cores random-access SRAM only, built as many small macros, one per 256 KiB block (block == SRAM, §3): each block is its own port, so thousands of concurrent accesses serve the 32 cores at once and the runtime lever holds. And the SRAM holds the resident window of the deloadable Main pool plus the three never-deloaded pools (the cross-block mail log, the block-object store, and the goal registry — fixed, always resident); deload streams the rest of the Main pool from SSD, so the SRAM is far smaller than the whole working set. The window is a tunable knob; the never-deloaded floor is not.

The cold tier barely costs anything: a full run's deload images are well under a gigabyte today, and even an FTA-scale run's cold footprint is a rounding error against any SSD. That is the point of the memory lever — it converts a hard RAM ceiling into a cheap, deep SSD that is, for practical purposes, unlimited.

7.2 · Compute — small, and that's the good news

A single LB core is modest: an FNV-1a hasher (a pipelined multiplier and some XORs), int32 comparators, set-subset/membership logic, a small register file for statement lines, a control FSM, and one or more phase-2 lanes. There is no floating-point unit, no wide vector engine, no matrix array. In gate terms this is small — comparable to a simple integer core, not a CPU or a GPU shader. The consequence: on a memory-bound part you spend your silicon budget on memory and interconnect, and the cores come almost for free. That also argues for a mature, cheaper process node — bleeding-edge logic density buys little when logic isn't the bottleneck.

7.3 · NRE vs per-unit — staging the build

The fixed cost of a custom chip (mask set + design) is millions, and it only earns out at volume. So the build path is staged:

  • Prototype = FPGA (reduced config). A high-end FPGA proves the mapping and the determinism claim end to end — but on a reduced GL config that fits the FPGA's on-chip SRAM (tens-to-hundreds of MB of BRAM/URAM), running entirely from that SRAM with no spill to off-chip memory (which would void the very test). It cannot hold the full multi-GB working set and will not match an ASIC's core count; it answers "does the all-SRAM mapping work, deterministically?" for the price of a workstation-class board.
  • ASIC tape-out is a volume decision. The mask set (cheaper on a mature node, far pricier at the leading edge) is only worth it once you are making thousands to millions of parts. Below that, an FPGA fleet is cheaper than amortising a mask.

7.5 · The multiplier N — a range, and still optimistic

What acceleration does the MPU actually deliver? Two different kinds, and it is worth keeping them separate:

  • Memory axis = enablement, not speedup. The right number here is not "×" — it is "possible vs impossible." Runs that hit the heap ceiling on a workstation today cannot finish at all; with the SSD-backed hierarchy they can. For the problems that matter next (FTA and beyond), this is the difference between a result and no result. Call it ∞ in the impossible→possible sense — the architecture is built to make it literal for the ceiling cases, though no run today yet demonstrates an out-of-memory case completing via deload.
  • Runtime axis = a real, bounded speedup. Phase 2 — the dominant cost — is embarrassingly parallel across (block, part), with tens to hundreds of thousands of independent tasks available at the busy moments (§5). MPU 0.1 fields the same 32 cores GL runs on today, so its runtime win is per-core, not from more cores: a specialized integer/FNV datapath fed from SRAM — no FPU, no off-chip memory stalls, no OS/cache-miss overhead — should beat a general CPU thread on this random-access workload, plausibly a few× to ~10× per core (an unbenchmarked estimate). Adding cores is the documented lever beyond that (up to the ~10⁴–10⁵ the workload offers), but that is a bigger MPU, not 0.1. The many-small-SRAM memory (§7.1) is what makes this real — per-block ports give the bandwidth and low latency to feed the cores. The remaining caveats are stated: phase 3 is serial per block, there is a mail barrier every cycle (tens of cycles to converge on the heavy batch), the commit seam is single-threaded, and a few hot cells (above all the root mail log, read by every block) are contention points even in SRAM. So the speedup is sub-linear in total cores, but the parallel fraction (phase 2) is where almost all the time goes, and the SRAM fabric is sized to feed it.
So: is it worth building? The MPU turns "out of memory" into "spill to SSD" and "out of time" into "add cores," at a cost dominated by SRAM today and shrinking with GL. GL already works without it — that is the 1 — so the MPU's worth is the N it adds, times whether GL can reach mathematics at all. The FTA campaign sets the second factor. Everything here is the first factor, costed as carefully as we can.

8 · The verdict

What works — the wins are real

  • The prover is already silicon-shaped: fixed pools, virtual-offset addressing, a working-set pager, a byte-canonical deload format. We are not proposing a rewrite — we are reading out a layout that exists.
  • Integer-only datapath, no FPU on the proof path. Small, cheap cores.
  • Full determinism, including across hosts. No FP nondeterminism, no consensus to scale out, exact external re-checking.
  • Both levers are live in software today: SSD deload (memory) and LB split (runtime). Nothing here is a paper design.
  • Memory is all SRAM — many small macros, one per block — so memory bandwidth scales with cores (true parallelism); SSD is the cold tier that makes capacity effectively unlimited.

What's hard — stated plainly

  • The working set is multi-GB today, so even with deload the SRAM window plus SSD streaming has to keep the cores fed — a poor-locality batch can go SSD-bound. Sizing the window against SSD bandwidth is the real tuning problem. (An optional DRAM L2 deload-staging cache — §3, not in the current design — could hide that latency.)
  • The kernel's compute paths are heap-free — compiler-verified: a semantic call-graph inventory over the built binaries shows zero heap-using functions on the proof kernel's production paths; the only permitted kernel heap is the hashburst_trace.txt debug dump (off the compute path, not silicon-mapped). What remains on the ordinary heap sits outside the kernel: the compiled-definition (compiledMap) config tables — startup-loaded data behind zero-allocation read fences, ROM on silicon; the mail-string encoding at the single-threaded commit and load seams; and the global pool's recycle queue plus the compaction scratch (§3, bounded, outside any one LB).
  • An FPGA prototype is the intended first build — the 32 cores fit easily; its on-chip SRAM caps the window, so it would prove the mapping and determinism, not peak capacity.
  • The second factor is unproven: whether GL does real mathematics is decided by FTA, not here. Until then, N multiplies an unknown.

The shrink trajectory — why the destination is a cheap, pure-SRAM MPU

Every technology shrinks as it matures; it is the most reliable pattern in computing. GL is young and has specific, identified levers to shrink its per-block memory — chiefly removing the provenance/history that the proving logic never reads (it is process documentation, not a proof input) and finer LB split (smaller, more numerous blocks each holding less). The internal estimate — as yet unvalidated — is a 100–1000× reduction in per-block memory. If it holds, that is the number that would shrink the working set until it fits the SRAM window outright — no streaming at all:

Where it stands The MPU is a force multiplier. It removes GL's two ceilings — memory becomes an SSD-deep hierarchy, runtime becomes a parallel fabric — and both levers already run in software. Today it is an all-SRAM accelerator backed by SSD deload — the SRAM holds the working window, the SSD holds the rest — built as 32 LB cores, the 32 we have, on an FPGA prototype or a small cluster. The layout already runs in software, so this is a starting point you can build on, not a finished part: the cheap, ubiquitous, zero-streaming version is a shrink away, and GL has the levers to get there. None of it matters unless GL can do real mathematics — the question the FTA campaign answers. GL is the 1, the MPU is the N; FTA decides whether either counts.
The problems are real — and we are eager to engage them. The hard parts above are not hidden; they are the work. We would rather state the SSD-streaming dependency, the not-yet-static edges, and the unproven second factor plainly, and build the prototype that turns the argument into a measurement.
